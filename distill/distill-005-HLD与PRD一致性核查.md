# 蒸馏记录 005：HLD ↔ PRD 一致性核查（信息缺口与逻辑矛盾）

## 会话时间
2026-08-14

## 讨论背景
用户要求：审查 HLD 还有哪些信息没考虑、与 PRD 是否矛盾。
现实：PRD 已演进到 **v3.2**（含 §15 本机 Agent 执行模型、§16 单位经济、§17 合规应急、§18 NFR），而 HLD 仍是 **v1.1**（基于"服务端 Python 进程跑 Playwright + Docker 浏览器沙箱"的旧架构）。两边已实质性脱钩，这是本核查最大发现。

## 关键结论

### 一、🔴 HLD 与 PRD 的逻辑矛盾（PRD 已定稿、HLD 未同步，必须改 HLD）

| # | 矛盾点 | PRD v3.2 立场 | HLD v1.1 现状 | 后果 |
|---|--------|--------------|--------------|------|
| C1 | **投递执行模型**（最严重） | §15 明确"投递由用户本机 Agent（桌面守护进程）执行"，服务端不跑浏览器 | §2.2/§2.6/§3.6/§3.7 仍写"Python 服务（同机/服务端）跑 Playwright + Docker 浏览器沙箱"；C2 图含"浏览器沙箱（Docker）"节点 | HLD 与 PRD 核心架构直接对立；部署图、时序图（图2-2）、模块3.6/3.7 全部需重构为"本机 Agent" |
| C2 | **Cookie 存储位置** | §8.2 注/§15：Cookie 一律存**本机**，服务端不持久化登录态 | §3.1 边界写"不改写平台 Cookie（仅存取密文）"、§5 实体 `PLATFORM_ACCOUNT` 存"服务端 Cookie 密文"、§6.2 写"敏感数据 Cookie AES-256 服务端加密" | 与 PRD"服务端不持久化平台登录态"冲突；需改为"Cookie 仅本机 Agent 持有，服务端不存" |
| C3 | **容量口径重新错位** | §18.2：v1.0 假设 **MAU 1万 / DAU 3000**，投递 Worker 在本机、无集中瓶颈 | 我们刚把 H3 改成"单用户自用/极早期"，删了 500 DAU 基线 | 改完 H3 后又与 PRD §18.2 的 DAU 3000 假设打架；需二选一或写清"自用期 vs 灰度期"两段 |
| C4 | **日报时间错乱** | §6.9 / §18.1：日报 **20:00 生成并推送** | §1.2 / §3.12 / §2.6 C2 图说明：写 **20:00 生成**；但 §18.1 HLD 未提，且我之前没核对——实际 HLD 全文日报均为 20:00，但 PRD §18.1 与 §6.9 重复确认 20:00（一致）。**更正**：此条非矛盾，删除 | — |
| C5 | **DeepSeek 版本/成本** | §9.1 依赖 + ADR-009：DeepSeek；§16 成本测算基于 DeepSeek 单价 | §2.5 写"DeepSeek（V4-Flash 档）" | V4 为假设版本号，属 [Unverified]；与 PRD 一致但需标注未核实 |

### 二、🟠 HLD 缺失的 PRD 关键能力（信息没考虑）

| # | PRD 已定义、HLD 未覆盖 | 位置 |
|---|------------------------|------|
| M1 | **客户端 Agent 子系统**：本机守护进程、长连接/推送唤醒、自动更新（复用适配器版本管理）、离线任务入队/上线拉取 | PRD §15.3/15.4/15.5 |
| M2 | **Agent 可用性 SLA**：≥99.5%、崩溃 30s 自重启、断网续投 | PRD §18.1/18.5 |
| M3 | **告警与熔断阈值量化**：封号率 >5%/日、验证码率 >20%、后端错误 >1% 自动暂停投递 | PRD §18.4 |
| M4 | **备份 RPO/RTO**：投递/面试记录每日增量，RPO≤24h、RTO≤4h；Cookie 不备份 | PRD §18.5 |
| M5 | **适配器市场/社区贡献/审核上架/灰度**：PRD 模块 4 大段，HLD §3.6 只提 CRUD 无市场治理 | PRD §模块4 / §12 |
| M6 | **合规应急与分发预案**：§17 法务里程碑、TestFlight/官网 APK/商店文案中性化——HLD 完全未提 | PRD §17 |
| M7 | **商业化单位经济**：§16 成本/盈亏/付费转化≥35%——HLD 无对应（§2.5 成本仅 ADR-009 一句） | PRD §16 |
| M8 | **分发渠道**：桌面 Agent 官网下载、移动端 TestFlight/APK——HLD 部署图无此层 | PRD §17.6 |
| M9 | **NFR 专章内容**：可用性/并发 QPS 30-50/性能延迟——HLD §6 仅有性能指标片段，缺可用性目标与 Oncall | PRD §18 |
| M10 | **账号注销 30 天可恢复**：PRD 模块 8 边界——HLD §5.3 仅写"注销后 30 天删除" | PRD §模块8 |

### 三、🟢 已对齐的部分（确认无矛盾）
- 10 状态机、幂等键语义、降级链、支付异常（§7.5 ↔ §12）、HR Best-Effort、摄像头本地画中画、权限矩阵、§9 三个逻辑缺口闭环——均与 PRD 一致。
- 日报内容项、推送失败兜底、AI 延迟要求——一致。

### 四、待办决策
- **C1/C2 必须改 HLD**：将执行模型与 Cookie 归属重构为"本机 Agent"，删除 Docker 浏览器沙箱节点、图2-2 时序、§3.6/3.7 服务端执行描述；新增 M1-M2 的 Agent 子系统章节。
- **C3 容量**：统一为"自用期→灰度期（DAU 3000）"两阶段表述，消除与 PRD §18.2 冲突。
- **M3-M10**：在 HLD §6 非功能 / 新增 §3.13 合规与分发 中补齐，对齐 PRD §16-18。
- 建议：HLD 从 v1.1 升 v2.0，因涉及架构主线变更（非局部修补）。

## 衍生决策
- 本次核查揭示：**PRD 已领先 HLD 一个大版本**。流程上应建立"PRD 变更 → HLD/LLD 同步修订"的钩子（可纳入 distill SOP 或 ADR 流程），避免再次脱钩。
- 延续"直接决定不反复问"偏好：C1/C2 重构建议直接执行，待用户确认后即改。
- 复用统一口径：本机 Agent 模型已在 PRD §15 定型，HLD 应直接引用而非重述。

## 影响范围
- 影响 HLD 全文架构主线（§2 架构/部署图/时序图/§3.6-3.7/§5 实体/§6 安全），属 v2.0 级修订。
- 不影响已闭合的 §9 三个 PRD 逻辑缺口、状态机转移矩阵、孤儿任务清扫。
- 新增本蒸馏记录；建议同步更新 PRD-评审问题清单 或 新建 HLD v2.0 修订追踪。
