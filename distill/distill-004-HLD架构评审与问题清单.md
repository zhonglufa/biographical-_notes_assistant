# 蒸馏记录 004：HLD 架构评审与问题清单

## 会话时间
2026-08-14

## 讨论背景
用户以"资深架构师"视角要求对 `design/HLD-简历自动投递与面试模拟-概要设计.md`（v1.0）做评审。
评审结论：文档工程素养高（需求追溯矩阵、模块边界、降级链、PoC 前置门、§9 PRD 逻辑缺口闭环均到位），但存在 3 处硬伤（含 2 处文档自我矛盾）+ 若干落地风险。用户要求将"看问题+分析"的工作过程自动化记录进 distill。

## 关键结论

### 一、🔴 必须修的硬伤（进 LLD 前不闭环会埋雷）

| # | 问题 | 证据位置 | 影响 |
|---|------|---------|------|
| H1 | **数据库选型自我矛盾**：约束表/部署图/数据设计全程 MySQL 8.0，但 C2 容器图说明（约第 120 行）写"PostgreSQL 存储主业务数据" | §1.3 约束表、§2.2 C2 图、§5 | 模板图未替换；LLD 不知以哪个为准 |
| H2 | **Java/Python 共享库口径冲突**：§5.3 跨服务一致性、ADR-002 明确"不共享库"，但 §2.6 部署图第 205 行写"MySQL …（JDBC，Java/Python 共享）" | §2.6 第 205 行、§5.3、ADR-002 | 地基级决策：Python 直读写 MySQL（焊死双服务）还是只走 REST/MQ？必须二选一写死 |
| H3 | **容量模型算不平**：§1.3 容量基线"500 DAU"，§3.7 浏览器实例池"上限 3"，PRD 目标 80-100 份/天/人。粗算 500×90=4.5 万份/天，系统级 3 实例根本跑不完 | §1.3、§3.7 | 要么"3"是每用户/每节点限制（需横向扩展方案，HLD 缺失），要么本就是单人自用工具（500 DAU 基线应删） |

### 二、🟠 重点风险 / 缺口（影响落地可行性）

| # | 问题 | 建议 |
|---|------|------|
| R1 | **幂等键交给前端生成 UUID（反模式）**：页面刷新/重试生成新 UUID，崩溃恢复幂等丢失 | 改用自然业务键派生 `user_id+job_id+platform_id+resume_version`；表中 `uk(user_id,job_id,platform_id)` 已作兜底，正文口径需改 |
| R2 | **孤儿任务清扫器缺失**：Java 写 pending → MQ → Python 执行 → 结果 MQ → Java 推进。若 Python 在"已投递未回写"前崩溃，application 永远卡 `submitted/autofilling` | 补"定时扫 stale 状态 + 重投/标记失败"机制（现有"排队超 30min 过期"只覆盖排队态，未覆盖在途） |
| R3 | **10 状态机只列状态、缺转移矩阵**，且标"单向不可逆" | `submitted` 可能直接 `rejected`，`offer` 后要到 `closed`。补允许转移表，明确哪些边存在 |
| R4 | **C2 图 Redis "负责任务队列后端"** 与全文 RabbitMQ 队列冲突 | 统一口径，避免误判用 Redis 做队列 |
| R5 | **"事件溯源"名不副实**：状态存 application 表，application_event 仅同事务追加的审计日志，非从事件重建 | 术语改为"审计日志 + 状态表" |

### 三、🟢 做得好的（保留）
- 需求追溯矩阵（§1.2）逐条关联 PRD/验收。
- 每模块"职责单句 + 边界"声明清晰，依赖无环。
- 全场景降级链（§7.2）覆盖匹配/面试题/评估/ATS/简历/HR 感知/投递。
- PoC 作为高风险前置验证门（§8.2）务实。
- §9 对 PRD 三个逻辑缺口的显式决策（动态上限/语音权限/字段级控制）闭环到位。

### 四、待办决策
- 优先拍板 H2（共享库）—— 决定 Python 侧整个数据访问层。
- 同时修 H1（PostgreSQL 改 MySQL）、H3（容量口径）。
- 补 R3 状态机转移矩阵、R2 孤儿任务清扫。
- 可选：直接修订 HLD 文本 / 或先出独立《架构评审意见》文档。

### 五、修订落地（v1.0 → v1.1，由用户拍板"直接改 HLD"）
用户确认系统定位为**单用户自用/极早期小规模**（非多租户 SaaS）。已直接修订 `design/HLD-*.md` 与两张 SVG 图：
- H1：C2/部署图 PostgreSQL→MySQL 8.0，JDBC 5432→3306。
- H2：统一"仅 Java 直连 MySQL"；Python 经 REST/MQ 访问业务数据，不直连业务库（§2.6④、§5.3 对齐）。
- H3：容量基线改为演进触发线；实例池 ≤3 为单 Agent 进程约束（§1.3、§2.6 新增容量说明）。
- R4：Redis 改"缓存/锁/幂等"，队列归 RabbitMQ（§2.2、C2 图）。
- R2：新增孤儿任务清扫机制（§3.4）。
- R3：补 10 状态转移矩阵，明确无回退边/跨阶段直达终态（§3.4）。
- 新增 §9.5 修订记录表；R1、R5 留待 LLD 处理。
