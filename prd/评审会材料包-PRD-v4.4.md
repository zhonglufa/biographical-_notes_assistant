## 3. 分角色评审提问清单（会前预填 + 会上讨论）

### 3.1 产品 / PM
- §C.3「不确定就停」的 fail-closed 边界在哪些场景触发？是否可能误伤正常投递（如误判风控挑战为失效，见 §30.11）？
- §33 北极星指标与 §32 商业论证的因果链是否自洽？[X][Y][Z] 假设目标（付费转化 / D30 留存 / CAC 回收期）初值是否合理？
- §35.2 v0.9 验证计划的「关键假设回填」机制是否覆盖全部 [X][Y][Z] 占位？
- 半自动口径（批量确认队列 + 延迟执行，§29.5 睡眠补偿）与 §5.2 自动补投是否仍有一处张力？

### 3.2 研发 / 架构
- **HLD v1.1 仍写「服务端执行 / 服务端加密 Cookie」，与 PRD §15 本机 Agent 矛盾（C1/C2）。本次会议是否升 HLD v2.0 重构？**（🔴 唯一重大跨文档矛盾）
- §18.4 可观测性 + §27 多端是否齐备？SLI/SLO（§31.5）是否已定义量化目标？
- §23.5 minimum_supported_version + 灰度自动回滚 guardrail（§31.12）落地可行？
- §34.3 功耗预算「不得阻止睡眠」如何工程化约束（与 §29.5 唤醒调度如何协调）？

### 3.3 SRE / QA
- 五层防线（§23/§24/§28/§29/§30）是否有单点遗漏？break-glass 自动止血（§30.5）触发阈值？
- §24.7 状态页、§24.11 Game day 演练是否排期？
- §35.7 代码质量门禁（CI 强制卡点）与现有流水线是否兼容？
- §35.2 Beta 计划的**退出标准（exit criteria）**是否量化（如：连续 N 天零 P1、匹配度 κ≥0.6）？

### 3.4 安全
- §15 + §20.5 Cookie 本地加密不上云 + KMS 轮换，是否覆盖重装恢复（§21.3）？
- §30 Q1–Q12 最小化机制是否全部有 fail-closed 兜底？
- §35.1 OSS 许可证（Playwright / Chromium / Python）白名单 + 禁 AGPL 是否经法务签字？
- §35.8 竞品飞轮是否触碰其他站点 ToS（§C.4 红线）？

### 3.5 增长 / 商业化
- §32 TAM/SAM/SOM 与 §33 留存模型（D1/D7/D30/D90）假设是否可验证？
- §35.5 定价弹性实验设计是否避开 §v3.12 已修的「滑块 vs 套餐」混乱？
- §34.9 客服成本模型是否与 §16 单位经济闭合？

### 3.6 设计 / UX
- §34.5 帮助中心与错误可解释是否覆盖 fail-closed 时的用户安抚文案（如误停投递解释）？
- **无障碍（Accessibility）为何仍待定（§19）？是否影响应用商店审核（§17.6）？**

### 3.7 法务 / 合规
- §19 登记的 PIPL 三块（第 24 条自动化决策 / DSAR 全流程 / 威胁模型与漏洞管理）延后是否构成合规敞口？
- 建议书面确认延后范围与兜底（例如：MVP 默认关闭自动化决策相关功能，仅做人工确认投递）。

### 7.2 §C 核心设计约束（跨章统一锚点，讨论时务必守住）
- **C.1 本机 Agent 执行模型**：投递执行唯一放在用户本机，非服务端。
- **C.2 数据最小化与 PIPL 红线**：仅采集必要信息，默认不向第三方泄露。
- **C.3「不确定就停」保守默认原则**：任何不确定场景 fail-closed，先停后问。
- **C.4 ToS / 平台合规红线**：不触碰招聘平台禁用自动化条款。
- **C.5 Cookie / 凭证本地化与不上云**：本地加密存储，绝不上传云端。

### 7.3 评审会纪律建议
- 范围争议一律回到 §C 与 §5.3 Out of Scope 裁决，避免发散。
- 所有「待定 / 假设」项在本次必须给出：① 纳入 v1.0 ② 延后并书面登记 ③ 删除，三选一。
- 决策当场记 §5 + §6 模板，避免会后失忆。
