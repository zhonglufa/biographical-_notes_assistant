## 2. 需求背景

应届生和社招求职者每天需要在多个招聘平台之间切换，手动筛选和投递岗位，耗时 2-3 小时[假设，来源与验证见 §2.1]。投递后被动等待回复，收到面试邀请时往往准备时间不足。市场上已有的开源自动投递工具（GetJobs、JobClaw、Boss Batch Push）均停留在 CLI 脚本层面，无可视化界面、无智能匹配策略、投递后无面试准备联动。

不同平台覆盖的岗位类型各有侧重：BOSS 直聘覆盖互联网社招，应届生求职网和高校就业平台覆盖校招，国聘网覆盖央企国企，猎聘覆盖中高端岗位。求职者需要一套系统，能够统一管理所有这些平台的投递，并随着新平台的出现灵活扩展。

此外，移动端是求职场景中不可忽视的渠道——用户在地铁、课间、午休等碎片时间需要快速浏览岗位、查看投递状态、接收面试通知，甚至进行轻量级的面试准备。现有方案完全没有覆盖移动端。

### 4.2 竞品方法论提炼

所有开源投递工具均采用 Playwright 模拟真人浏览器操作，核心手段包括随机延迟（正态分布）、随机鼠标轨迹（贝塞尔曲线）、Cookie 持久化。共同结论是：**无公开 API，所有平台均需通过浏览器模拟实现投递**。

开源工具停留在"脚本"层面，商业产品（知页、超级简历）聚焦简历制作和面试题库，均未将"自动投递"作为核心功能。"智能投递策略 + 面试准备联动 + 移动端触达"是目前市场的明确空白。

### 5.2 核心使用场景

**PC 端场景**：

- **场景一：每日批量投递** — 用户早晨打开系统，查看 AI 已筛选的岗位列表，一键确认投递队列，系统自动按平台策略分发投递，实时查看进度
- **场景二：简历编辑与优化** — 用户在工作台编辑简历，切换模板，查看 ATS 评分和 AI 建议
- **场景三：投递后自动面试准备** — 投递成功后，系统自动分析 JD 生成面试预测题，推送到面试备战模块
- **场景四：深度面试模拟** — 用户在 PC 端进行完整 AI 面试模拟（含语音输入、摄像头等）
- **场景五：平台适配器管理** — 高级用户或开发者管理首期支持（计划首期 / 待上线，平台清单见 §6.2）的平台适配器

**移动端场景**：

- **场景六：碎片时间浏览** — 用户在通勤/课间打开手机，浏览今日推荐岗位和匹配度，标记感兴趣
- **场景七：投递确认与审批** — 收到投递队列推送，在手机上快速确认或调整后提交；指令下发至用户本机 Agent 异步执行（执行模型详见 §15；要求本机 Agent 在线）
- **场景八：状态通知与跟踪** — 收到 HR 查看、面试邀请等实时推送，查看投递状态看板
- **场景九：轻量面试准备** — 在手机上查看已生成的面试题，语音练习作答
- **场景十：简历快速调整** — 手机端进行简历基础信息修改，或选择投递所用简历版本
- **场景十一：每日日报自动推送** — 系统每天 20:00 自动生成当日投递日报，汇总投递数量、成功/失败统计、HR 查看记录、面试邀请、新增面试题等，通过移动端推送和邮件发送给用户
- **场景十二（端到端串联）：完整的求职日** — 早晨 8:00 收到 AI 筛选的岗位推荐推送 → 通勤途中在手机上确认投递队列 → 上午 PC 端配置投递策略 → 系统自动执行投递 → 下午陆续收到 HR 查看/面试邀请推送 → 投递成功后自动触发面试题生成 → 在面试备战模块查看和练习 → 晚上 20:00 收到当日投递日报推送

### 5.3 系统范围边界（Out of Scope）

**平台范围**：
- 本期不接入海外招聘平台（LinkedIn、Indeed、Glassdoor 等）
- 本期不接入垂直行业平台（如：医疗行业的丁香人才、金融行业的银行招聘系统）
- 本期不接入社交招聘渠道（如：脉脉、知乎招聘等）

**岗位范围**：
- 不自动投递实习岗、兼职岗、劳务派遣岗（用户可手动投递，系统不拦截）
- 不自动投递薪资范围不明确的岗位
- 不自动投递涉及敏感行业（如：成人内容、赌博、加密货币等）的岗位

**合规红线**：
- 系统不绕过验证码——触发验证码时立即暂停所有投递任务，通知用户人工处理
- 系统不违反各平台用户协议的核心条款——投递行为模拟真人操作，但不伪造身份、不批量注册、不爬取非公开数据
- 系统不存储用户在各平台的明文密码，仅存储加密后的 Cookie
- 系统不提供账号租赁、代投等灰色服务
- 系统不向第三方出售或传输用户数据

**功能边界**：
- 系统不提供简历代写服务（仅提供 AI 优化建议）
- 系统不提供职业咨询或求职规划
- 系统不提供薪资谈判建议
- 系统不提供企业内推渠道
- 系统不提供面试陪练真人服务

### 5.4 多端、多账号与多 OS 支持边界

- **操作系统**：v1.0 本机 Agent 支持 Windows 10+ 与 macOS 12+；Linux 列为后续（兼容性测试成本高）。移动端为确认 / 浏览壳，不执行投递。
- **多招聘账号**：v1.0 单用户绑定单套平台账号（各平台 1 个）；多账号切换 / 矩阵管理列为后续，且涉及平台多账号政策风险，需单独评估（§17）。
- **多设备**：同一用户可在 PC（Agent）+ 移动端（确认）协同；PC 离线时移动端仅可浏览与排队，投递待 PC 上线后执行（见 §18.1 可用性约束）。
- **数据同步**：投递队列、状态、日报在用户账号维度跨端同步（服务端），Cookie 仍仅存本机 Agent（§8.2 / §15）。
- 多端配置冲突的解决流程（并发修改、LWW、版本向量）详见 §23.10。

#### 模块 3：自动投递策略引擎

**架构总览**：

```
┌─────────────────────────────────────────────────────────────────┐
│                    预处理层                                      │
│  岗位采集 → AI 匹配打分 → 过滤规则链 → 优先级排序              │
└──────────────────────────┬──────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────────────┐
│                    调度层                                        │
│  平台路由 → 时段推荐 → 频率控制 → 限额管理 → 简历版本选择      │
└──────────────────────────┬──────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────────────┐
│                    执行层                                        │
│  浏览器模拟 → 防检测 → 状态记录 → 异常处理                     │
│  ┌──────────────────────────────────────────────────────┐       │
│  │  浏览器实例池：最多 3 个并发实例                       │       │
│  │  平台适配器 1 (BOSS) │ 适配器 2 (猎聘) │ ...         │       │
│  │  每个适配器实现: login / search / apply / checkStatus │       │
│  └──────────────────────────────────────────────────────┘       │
│  ┌──────────────────────────────────────────────────────┐       │
│  │  幂等性保障：每个投递任务生成唯一 idempotency_key    │       │
│  │  失败恢复：单个平台失败不影响其他平台投递             │       │
│  └──────────────────────────────────────────────────────┘       │
└──────────────────────────┬──────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────────────┐
│                    反馈层                                        │
│  投递报告 → 响应率跟踪 → 动态调优 → 策略学习                   │
└─────────────────────────────────────────────────────────────────┘
```

**预处理层**：
- AI 匹配打分：LLM 分析岗位 JD 与简历的匹配度
- 过滤规则链：排除外包/外派、培训公司、僵尸岗（HR 超 7 天未活跃）、薪资范围不符、重复投递
- 优先级排序：按匹配度降序 + 发布时间倒序排列

**调度层**：

| 时段 | 投递数量 | 策略说明 |
|------|---------|---------|
| 09:30-11:30 | 30-40 份 | HR 上午黄金时段 |
| 14:30-16:00 | 30-40 份 | 下午黄金时段，周三周四最佳 |
| 19:00-20:30 | 20-30 份 | 互联网/科技公司 HR 加班时段 |
| **每日合计（专业版及以上）** | **80-100 份**（**需 v0.9 灰度验证，见 §16.5**；免费版 30 份/天，见 §12） | 低于各平台上限，保留安全余量 |

限额策略：单次投递不超过 50 个，两次操作间隔 30 分钟以上；单平台日上限设为平台限制的 70%；同一岗位间隔至少 1 个月且有简历更新后可重新投递。

**执行层**：
- 防检测五重保障：随机延迟（正态分布，3-8 秒）、行为模拟（贝塞尔曲线鼠标轨迹、随机滚动、随机 User-Agent）、验证码检测暂停、Cookie 持久化加密存储、黑名单机制
- **浏览器实例池**：每用户本机最多 3 个并发浏览器实例（非服务端共享），各实例独立隔离；多用户通过各自本机 Agent 横向扩展，无集中式实例瓶颈（详见 §15）
- **幂等性保障**：每个投递任务生成唯一 `idempotency_key`，系统在投递前检查是否已执行，避免重复投递；投递中断后恢复时，通过 idempotency_key 查询实际状态，而非盲目重试
- **部分失败恢复**：单个平台投递失败不影响其他平台；失败任务进入重试队列，按指数退避策略重试（最大 3 次）
- 异常处理：限额已满→暂停该平台次日恢复；验证码触发→暂停所有任务通知用户；账号异常→停止所有任务；网络错误→重试 3 次后跳过

**反馈层**：
- 投递报告自动生成（成功数/失败数/原因/黑名单更新）
- 按平台统计 HR 查看率、回复率、面试邀请率，低于阈值则减少该平台投递量
- 每月复盘各平台响应率，响应率 < 10% 则减少投递频率并优化简历关键词

**策略配置面板**：

| 配置项 | 类型 | 默认值 | 说明 | PC | 移动端 |
|-------|------|-------|------|----|-------|
| 每日投递上限 | 滑块（20–150，实际可设上限受套餐约束：免费版 30 / 专业版及以上 100，见 §12） | 80（免费版受 30 上限） | 所有平台合计 | 完整 | 仅查看 |
| 匹配度阈值 | 滑块（40-90） | 60 | 低于此值不投递 | 完整 | 仅查看 |
| 投递时段 | 多选开关 | 早中晚全开 | 可单独关闭某时段 | 完整 | 开关控制 |
| 启用平台 | 多选开关 | 全部开启 | 可关闭特定平台 | 完整 | 开关控制 |
| 自动简历选择 | 开关 | 开启 | 自动选择匹配度最高的简历版本 | 完整 | 开关控制 |
| 投递后自动面试准备 | 开关 | 开启 | 投递后自动生成面试准备内容 | 完整 | 开关控制 |
| 平台扩展 | 管理入口 | — | 查看/添加/配置平台适配器 | 完整 | 仅查看状态 |

**全局异常场景（浏览器实例池）**：
- 实例池资源耗尽（OOM/内存高水位）：引擎暂停新任务入队，正在执行的投递任务允许完成；展示"资源占用过高，已暂停新任务"提示；监控告警触发后 5 分钟内自动重启空闲实例
- 实例崩溃恢复：崩溃后该实例上的投递任务标记为"执行中断"，通过幂等键 15 分钟内重试，不产生重复投递
- 排队任务超时：队列中任务等待超过 30 分钟标记"已过期"，用户收到通知并可手动重试

- 适配器版本冲突：新版本安装失败时自动回滚到上一可用版本，并提示安装错误原因

#### 模块 7：投递与面试准备联动

| 触发事件 | 联动动作 | 延迟 | 推送渠道 |
|---------|---------|------|---------|
| 岗位投递成功 | 后台分析 JD，生成面试题，标记"可查看"状态 | 投递后立即 | 静默后台 |
| 感知到 HR 已查看（尽力感知，可选增强） | 推送提醒"您的简历已被查看"，提示关注面试准备 | 轮询发现后 | 移动端推送 |
| 收到面试邀请 | 生成完整面试准备包（含公司背景、岗位深度分析、模拟面试题） | 实时 | 移动端推送 + 邮件 |
| 面试已完成 | 收集面试反馈，更新面试题库，优化后续预测 | 面试后 1 小时 | 静默后台 |

**联动数据流**：

```
投递成功 → 后台异步任务：
 1. 提取岗位 JD 全文
 2. 调用 LLM 分析 JD 关键词和技术栈
 3. 匹配用户简历中的对应经历
 4. 生成面试题列表（技术题 + 行为题）
 5. 存入面试备战模块，标记"可查看"状态
 6. 若感知到 HR 已查看或面试邀请 → 推送通知到移动端
```

**HR 已查看状态感知设计（消除歧义）**：外部平台不会向本系统推送"HR 查看了"事件，因此定义为**尽力感知（Best-Effort）能力**，不构成硬依赖：
- 感知通道 1：定时轮询平台"投递记录/沟通过"页面（由适配器实现 `getApplicationStatus()`），平台展示该状态时即可感知
- 感知通道 2：解析平台站内消息/通知页面中的进展事件
- 兜底策略：无法感知的平台，投递面试题在生成后直接标记"可查看"，不等待 HR 事件；HR 查看感知用于额外推送增强而非功能前提
- 状态机中的"HR 已查看"为可达但允许未知（unknown）的状态，未知时不阻塞任何流程

**面试题状态映射（改写）**：原"待完善 → HR 已查看 → 可查看"改为"生成中 → 可查看"；推送通知在感知到 HR 查看/面试邀请时额外触发，感知不到则正常使用。

**边界与异常**：
- 投递任务尚未完成时，面试题生成任务等待投递结果后再触发
- 投递失败时，不生成面试题，标记为"投递失败"状态
- JD 内容为空或无法解析时，生成通用面试题（基于简历和岗位名称）
- HR 状态感知失败时，不阻塞面试题生成流程，仅静默记录日志
- 推送通知发送失败时，下次用户打开应用时通过站内消息展示
- 联动任务队列积压超过 50 个任务时，触发告警并暂停新任务入队

#### 模块 8：用户系统与多端同步

**账号体系**：
- 邮箱/手机号注册登录
- 第三方登录（微信扫码）
- 多设备登录态管理

**数据同步机制**：
- 简历数据：服务端存储为主，PC 端编辑后实时同步，移动端编辑后自动同步
- 投递任务：本机 Agent 执行（状态由服务端回收并同步），PC 和移动端均可查看状态
- 面试题：服务端生成，按需同步到客户端缓存
- 离线支持：移动端缓存最近 50 条岗位和已生成的面试题，无网络时可查看

**冲突处理**：
- 简历编辑冲突：以最后保存版本为准，丢弃旧版本（展示冲突提示）
- 投递操作冲突：同一岗位不可同时从 PC 和移动端发起投递，后发者提示"已在投递中"
- 配置冲突：投递策略配置以 PC 端为准，移动端开关控制与其联动

**角色权限矩阵**：

| 功能域 | 免费用户 | 专业版用户 | 高级版用户 | 管理员 |
|--------|---------|-----------|-----------|--------|
| 简历编辑（自己） | 完整功能 | 完整功能 | 完整功能 + 多版本 | 不涉及 |
| 简历编辑（他人） | 无 | 无 | 无 | 查看（仅审核） |
| 岗位浏览 | 浏览 + 收藏 | 浏览 + 收藏 + 忽略 | 同专业版 | 管理（删岗位、处理举报） |
| 投递操作 | PC 端日上限 30 份，≤3 平台（移动端仅查看） | 日上限 100 份，全平台（移动端可确认/发起，实际执行在本机 Agent，见 §15） | 同专业版 | 管理（撤销错误投递） |
| 投递策略配置 | 查看 | 完整配置 | 完整配置 + 优先级 | 全局默认值管理 |
| 平台适配器 | 仅查看状态 | 安装 + 配置 | 安装 + 配置 + 优先支持 | 审核 + 上架 + 下架 |
| AI 面试模拟 | 每日 3 次 | 每日 10 次 | 无限次 | 不涉及 |
| 面试备战内容 | 查看 | 查看 + 语音练习 | 查看 + 语音练习 | 内容管理 |
| 用户数据导出/删除 | 完整 | 完整 | 完整 | 审计（不接触内容） |
| 账号管理 | 自身 | 自身 | 自身 + 备用账号（后续规划） | 全部（禁用违规号） |

> **账号范围说明**：v1.0 单用户仅绑定单套平台账号（各平台 1 个，见 §5.4）；本矩阵中"高级版用户：自身 + 备用账号"为**后续规划能力**，v1.0 不提供——v1.0 封禁应对以暂停+通知+引导解封为主（见 §17.7），不依赖备用账号。

**权限逻辑规则**：
- 数据隔离：所有用户仅能访问自己的简历、投递记录、面试记录；管理员按审计权限只读访问，不可修改用户数据
- 权限判定时机：每次接口调用时校验（服务端强制），前端仅做展示隐藏
- 会员降级处理：过期后自动降级为免费版，已存在的配置保留但不可修改，超出限额的进行中任务允许执行完毕

**"优先支持"定义（消除歧义）**：高级版用户在平台适配器相关的 SLA，具体化为 3 条可量化承诺：
- 适配器故障响应：高级版用户提交的问题 48 小时内给出处理方案（免费/专业版 7 天）
- 适配器更新发布：高级版用户可抢先使用新适配器 beta 版，正式版优先推送
- 新平台接入：高级版用户提名的新平台，排入适配器开发队列的最优先位置

**边界与异常**：
- 用户未登录时，仅展示引导页，不暴露任何业务数据
- 第三方登录失败时，回退到邮箱/手机号注册登录流程
- 多设备同时编辑简历时，以最后保存版本为准，弃用版本展示冲突提示
- 移动端离线状态下提交投递确认，待网络恢复后自动同步到服务端
- 账号注销后，30 天内可申请恢复，超期后数据彻底清除
- 会员降级后已存在的配置保留但不可修改，超限的进行中任务允许执行完毕

**功能描述**：

- 通过移动端推送和邮件发送给用户
- 用户可在「我的」页面自定义推送时间（默认 20:00）

**日报内容**：

| 数据项 | 说明 |
|-------|------|
| 今日投递总数 | 当日所有平台投递合计 |
| 投递成功/失败数 | 按平台拆分，含失败原因 |

| 新增面试题 | 投递联动生成的新面试题 |
| 累计趋势 | 近 7 天投递量、HR 查看率、面试邀请率趋势 |

**边界与异常**：
- 用户当日无投递活动时，生成"今日无投递活动"摘要，不发送空日报
- 推送发送失败时，下次用户打开应用时通过站内消息展示
- 邮件发送失败时，系统自动重试 3 次，仍失败则静默处理
- 用户未设置邮箱时，仅通过移动端推送发送，不发送邮件
- 日报生成任务异常中断时，15 分钟后自动重试 1 次，仍失败则跳过当日

### 6.3 异常处理与用户感知设计（失败 / 离线 / 封禁）

**投递失败**
- 单平台投递失败：任务进入重试队列（指数退避，最大 3 次），失败原因（验证码 / 限额 / 网络 / 账号异常）结构化记录并推送给用户；不影响其他平台。
- 用户感知：移动端 / PC 端投递报告清晰标注"成功 N / 失败 M / 原因"，失败项提供"重试"或"转手动"入口。

**PC 离线（本机 Agent 不可用）**
- 移动端确认后任务进入云端待执行队列，明确提示"PC 离线，将在电脑上线后自动执行"；不视为投递失败。
- PC 重新上线后，Agent 拉取待执行队列按 `idempotency_key` 续跑（§6.2 幂等），避免重复投递。

**账号被封 / 强验证**
- 触发封禁或验证码率突增（>20%）时，自动暂停该平台全部任务并通知用户（§17.2 / §18.4 告警）。
- 用户感知：明确告知"X 平台账号受限，已暂停投递，请按平台指引解封"，恢复前不自动重试、不自动换号。
- 提供"解封后恢复"一键操作，重新扫码后继续。

**兜底原则**：任何异常下，用户始终拥有"查看状态 + 手动接管"的退出通道，系统不替用户做不可逆决策。

### 6.4 通知中心与消息通道架构

> 本节约统一模块 7「投递联动推送」、模块 9「每日日报与推送」及 §6.3 异常的推送实现规范，避免各处重复描述、口径不一。

**双通道分离（关键架构约束）**
- **系统信令通道**：调度服务 ↔ 本机 Agent 之间的指令/状态传输（§15.4 长连接/推送），用于下发投递任务、回传状态，**不展示给用户**；失败走 Agent 断线重连与云端待执行队列（§6.3）。
- **用户通知通道**：面向用户的业务通知（状态、面试邀请、日报、系统告警）。两通道在代码与数据上完全隔离，禁止混用——例如"唤醒 Agent 的信令"不得误推送给用户造成骚扰。

**渠道矩阵与降级链**
| 渠道 | 适用 | 失败降级 |
|------|------|---------|
| 移动端推送（iOS APNs / 安卓 FCM + 厂商通道） | 主渠道，实时类 | 失败 → 站内信；L0/L1 额外补发邮件 |
| 邮件 | 重要事件兜底、日报 | 失败 → 标记待站内展示 |
| 站内信（通知中心） | 全量兜底，始终可达 | 无（本地存储） |
| PC 端本地通知（Agent toast） | PC 在线时同步提醒 | PC 离线则仅移动端/站内 |

默认路径：移动端推送 → 失败转站内信 → L0/L1 事件额外邮件兜底。

**消息分级**
- **L0 实时重要（免打扰豁免）**：面试邀请、账号封禁、验证码触发、登录态失效。立即推送。
- **L1 重要（免打扰豁免）**：投递失败需处理、平台适配器失效、续费失败进入宽限。
- **L2 普通（聚合推送）**：单份投递成功、HR 已查看。按频率聚合（见下）。
- **L3 营销（受免打扰约束）**：新功能、续费提醒、活动。

**频率聚合策略（防刷屏）**
- 投递成功：不逐条推送，按"每累计 10 份 或 每 2 小时"发一条摘要「今日已投递 N 份，成功 X / 失败 Y」；仅失败项单独推（L1）。
- HR 已查看：聚合为半日/每日摘要「今日 N 个岗位被 HR 查看」。
- 用户可在「我的」自定义聚合粒度（实时 / 每 N 份 / 每日）。
- 日报（模块 9）独立按设定时间（默认 20:00）推送，不参与上述聚合。

**免打扰与静默**
- 用户可设免打扰时段（默认 22:00–08:00）。
- L0/L1 豁免（可单独设"仅重要不打扰"关闭）。
- L2/L3 在免打扰时段延后，时段结束后批量补推。

**推送授权引导与拒绝挽回**
- 首次安装/登录引导开启推送（iOS 必需授权）；明确告知用途（投递状态、面试邀请）。
- 用户拒绝后：站内信始终可用兜底；在关键节点（首次投递成功、面试邀请）提供"去系统设置开启推送"引导，不阻塞核心功能。

**通知中心**
- 站内统一收件箱：已读/未读、多端已读同步（移动端已读 → PC 同步）。
- 保留 90 天，到期自动归档（呼应 §8.2 保存期限最小化原则）；支持一键全部已读 / 删除。
- 指标：通知中心打开率（补入 §10.2 跟踪）。

**重复去重**
- 同一事件按 `event_key` 去重：如"登录态失效"5 分钟内不重复推；同岗位"HR 已查看"仅首次推。
- 投递失败按平台+日期去重汇总，避免重复轰炸。

**隐私与敏感词规避**
- 通知正文不含身份证号、手机号等敏感字段；锁屏默认显示「你有新的求职动态」，具体岗位/公司名需解锁查看（用户可设"锁屏显详情"）。
- 文案规避平台 ToS 敏感字眼（如"自动投递"），统一用「简历投递助手 / 投递动态」表述（呼应 §17.4 免责）。

## 7. AI 产品专项

### 7.1 LLM 使用场景

| 场景 | 能力 | 输入 | 输出 |
|------|------|------|------|
| 岗位匹配度评分 | 语义相似度 + 关键技能匹配 | 岗位 JD + 用户简历 | 匹配分数 (0-100) + 匹配理由 |
| 面试题生成 | 基于上下文的生成 | 岗位 JD + 简历项目经历 | 题目列表 + 参考答案 + 难度标签 |
| 面试作答评估 | 多维度评分 | 作答文本 + 标准答案 | 各维度评分 + 改进建议 |
| ATS 简历评分 | 内容完整性 + 关键词密度 | 简历全文 | 综合评分 + 改进建议列表 |
| 简历内容优化 | 文本润色 + 改写 | 原始内容 + 目标岗位 | 优化后的简历文本 |
| 自我介绍生成 | 结构化摘要 | 简历全文 | 1 分钟 / 3 分钟版本 |

### 7.2 准确度定义与评估体系

**任务成功标准**：

| 场景 | 成功标准 | 质量维度 | 主观/客观 |
|------|---------|---------|-----------|
| 岗位匹配度评分 | 推荐岗位与用户实际投递意愿的吻合度 ≥ 80% | 正确性、相关性 | 可客观验证 |
| 面试题生成 | 题目覆盖 JD 中 80% 以上的技术关键词 | 完整性、相关性 | 半客观 |
| 面试作答评估 | 评估结果与资深面试官评分的偏差 ≤ 1 分 | 正确性、一致性 | 主观 |
| ATS 简历评分 | 评分与 HR 筛选结果的排序一致性 ≥ 70% | 正确性 | 可客观验证 |
| 简历优化 | 用户采纳率 ≥ 60% | 可读性、有效性 | 主观 |

> 口径区分：上表"吻合度 ≥ 80%"衡量"推荐岗位与用户意愿的对齐程度"（推荐质量）；§7.5 的"匹配度 > 60%"是**投递门槛阈值**（决定是否自动投递），二者概念不同、不冲突——吻合度高的岗位未必越过投递门槛，反之亦然。

**评估体系**：
- 离线评估：构建标准样本集（含边界样本和负样本），每轮模型更新后回归测试
- 人工复核：产品经理每周抽样评审生成结果，记录 bad case 并归因
- 在线反馈：通过行为指标（编辑率、复制率、采纳率、重新生成率、废弃率）和用户反馈（点赞/点踩、问题标签）持续监控

**Go/No-go 标准**：

| 维度 | 可上线标准 |
|------|-----------|
| 准确度 | 离线评估通过率 ≥ 90% |
| 体验 | 用户端响应延迟在 §7.4 规定的范围内 |
| 安全 | 不生成违规内容，不泄露用户简历数据 |
| 成本 | 单次 LLM 调用成本在预算范围内 |
| 运维 | 有降级方案和监控告警 |

### 7.3 回退机制

| 场景 | 首选项 | 降级 1 | 降级 2 |
|------|-------|--------|--------|
| 匹配度评分 | LLM 语义匹配 | 规则引擎关键词匹配 | 随机排序 |
| 面试题生成 | LLM 生成 + 题库 | 纯题库匹配 | 预设模板题 |
| 面试评估 | LLM 多维度评分 | 仅提供参考建议 | 不评分 |
| ATS 评分 | LLM + 规则综合 | 纯规则关键词评分 | 仅展示完整度 |
| 简历优化 | LLM 改写 | 提供多个版本 | 语法检查 |

**全局异常场景（LLM 服务不可用）**：
- LLM 全部实例不可用：所有 LLM 相关功能进入降级模式（按上表逐级回退），页面顶栏展示"AI 服务维护中"横幅，不阻塞非 AI 功能（简历编辑、岗位浏览、投递照常）
- 部分模型不可用：自动切换到可用模型，用户无感知；切换后响应延迟略有上升但只要在 §7.4 范围内即可
- 生成结果超时：单次调用超时后自动重试 1 次，仍失败按 7.3 表降级；进行中的面试对话保留上下文，恢复后可从断点继续
- Token 配额耗尽：非紧急任务（简历优化、面试题生成）降级为规则引擎处理，紧急任务（投递联动）标记优先配额

### 7.4 延迟要求

| 场景 | 最大可接受延迟 | 说明 |
|------|---------------|------|
| 匹配度计算 | 5 秒 | 同步展示，需快速响应 |
| 面试题生成 | 30 秒 | 异步后台任务 |
| 作答评估 | 3 秒 | 对话式交互，需及时反馈 |
| 简历优化 | 10 秒 | 用户点击 AI 生成按钮后等待 |
| 投递后联动 | 5 分钟 | 后台异步，用户无需等待 |

### 7.5 匹配度模型设计与评估

**目标**：对"简历 × 岗位 JD"输出 0–100 匹配度，并给出可解释标签，作为"是否投递（>60%）"与"面试准备"的依据。

**方法（v1.0 规则 + 模型混合）**
- 结构化解析：简历与 JD 解析为统一向量（技能栈、行业、城市、经验年限、学历）；技能重叠度用 Jaccard / 加权余弦。
- 规则层（可解释、零样本）：硬性过滤（城市不符、经验年限差距 >3 年、学历不满足硬性要求）→ 直接判低分并说明原因；软性加权（技能重合度、行业相关度、标题相关度）加权求和。
- 模型层（可选 v1.1）：用 LLM 做语义匹配与理由生成（见 §7.1），输出匹配度与"为什么匹配 / 不匹配"的自然语言解释。
- Prompt 版本管理与回归评测（保障匹配/prompt 不回归）见 §26.1。

**Ground Truth 与标定**
- 冷启动：无历史时先用规则层 + 产品默认权重（技能 40% / 行业 20% / 城市 20% / 经验 20%），并在 §2.1 灰度中采集用户"实际是否投递 / 是否收到面试"作为正样本回流。
- 评估：以"用户最终是否投递该岗"与"HR 是否查看 / 邀约"为标签，离线计算匹配度分桶与查看率 / 邀约率的相关性；目标高分桶（>60）查看率显著高于低分桶。

**可解释性（必须）**
- 每次匹配展示 Top-3 匹配点与 Top-1 不匹配点，用户可覆盖（"强制投递 / 排除"），覆盖行为回流为训练信号。

**准确度验收**：匹配度分桶与人工标注一致性（Cohen's κ）≥ 0.6；错投率（用户明确"不应投"占比）≤ 10%（验收见 §11）。

## 8. 平台合规性与数据安全

### 8.1 平台合规性

自动投递功能可能违反招聘平台的用户协议。应对策略：

| 风险 | 缓解措施 | 用户告知 |
|------|---------|---------|
| 违反平台 ToS | 投递行为模拟真人操作（随机延迟、鼠标轨迹、自然语言打招呼），降低被识别为脚本的概率 | 用户在首次使用前签署免责声明，明确知悉风险 |
| 账号被封禁 | 单平台日限额设为平台限制的 70%；Cookie 加密存储，避免多次登录触发风控；提供备用账号管理功能（**备用账号为 v1.0 后置能力；v1.0 封禁应对以暂停+通知+引导解封为主，见 §17.7，不自动换号**） | 用户自行承担账号风险，系统提供账号切换功能 |
| 平台协议变更 | 适配器版本管理，平台接口变更时适配器标记为"需更新"，暂停该平台投递 | 通知用户平台适配器需更新 |
| 法律合规 | 系统不存储用户在各平台的账号密码，仅存储加密后的 Cookie | 数据隐私政策中明确说明 |

### 8.2 数据安全

| 数据类型 | 存储方式 | 加密要求 | 保留期限 |
|---------|---------|---------|---------|
| 用户简历内容 | 服务端加密存储 | AES-256 | 用户主动删除或账号注销后 30 天 |
| 平台 Cookie | 本地加密存储 | AES-256，密钥与用户设备绑定 | 每次登录刷新，用户登出时清除 |
| 投递记录 | 服务端存储 | 传输加密 (TLS) | 保留 24 个月，到期自动匿名化归档；满 36 个月删除；用户可随时主动删除（PIPL 保存期限最小化，见 §8.3） |
| 面试记录 | 服务端存储 | 传输加密 (TLS) | 用户主动删除或账号注销后 30 天 |
| 移动端缓存 | 本地存储 | 沙箱隔离 | 随用户登出清除 |

> 注：平台 Cookie 一律存储于用户本机（客户端 Agent），服务端不持久化任何平台登录态。此设计与"投递由本机 Agent 执行"一致，详见 §15。

### 8.3 个人信息保护合规

- 用户可导出全部个人数据（简历、投递记录、面试记录）
- 数据保存期限最小化：投递记录保留不超过 24 个月，到期自动删除或匿名化归档，不永久留存（保留期限详见 §8.2）
- 用户可删除账号及全部关联数据
- 系统不向第三方机构传输用户简历和个人信息
- 隐私政策在首次使用时展示并获得用户确认
- 停服与数据迁移：若产品停止服务，提前 30 天通知，提供全部个人数据导出（标准格式），到期后删除服务端数据（详见 §19）；导出格式与字段 schema 详见 §23.11（含 PIPL 数据携带权一键导出）。

### 8.4 AI 数据处理与个人信息保护（LLM 委托处理）

简历含姓名、手机号、身份证号、教育 / 工作履历等个人信息，在匹配、面试题生成、简历优化等环节会进入 LLM 上下文，属《个人信息保护法》下的"委托处理"，须满足以下要求：

- **受托方协议**：与 LLM 提供方签署数据处理协议（DPA），明确"仅用于本产品功能、不留存、不训练"。优先选用支持"零数据保留 / 不用于训练"的企业版 API。
- **数据最小化与脱敏**：进入 LLM 前对身份证号、手机号等敏感字段做掩码 / 脱敏；仅传递完成任务所必需字段（如技能、行业、城市），不整份明文简历。
- **数据出境**：若使用境外 LLM（如 GPT 系列），触发 PIPL 第 38 条，须走安全评估 / 标准合同 / 认证任一项；v1.0 默认选用境内合规大模型（如通义 / 文心 / 智谱 / DeepSeek 等）以规避出境合规。
- **用户授权**：隐私政策与首次使用授权中明确"简历信息将用于 AI 匹配 / 生成，由本机或境内合规模型处理"，用户可关闭 AI 功能（降级为规则匹配）。
- **留存**：LLM 输入输出日志脱敏后保留 ≤7 天用于排障，不长期留存原文。

### C.1 本机 Agent 执行模型（唯一执行体）

## 15. 系统架构与执行模型决策

> 本章为解决原稿中"服务端执行投递"与"Cookie 本地存储"的矛盾而新增，并作为 §5.2、§6.2、§8.2 的权威定义。

### 15.1 核心决策：投递执行放在用户本机 Agent

经评审修订，明确采用 **客户端 Agent 执行模型**：

- 用户在本机（Windows / macOS 桌面）安装轻量 Agent（守护进程），负责持有平台 Cookie、运行 Playwright 浏览器实例、落地执行投递。
- Web 端（PC 浏览器）与移动端 App 为"瘦客户端"，仅做配置、确认、查看；实际投递由本机 Agent 执行。
- 服务端职责：账号体系、简历加密存储、岗位聚合与 AI 匹配、调度编排（下发投递指令）、状态回收、日报生成、推送。

**决策理由（直接消解原稿矛盾）**：

1. **数据安全**：Cookie 永不出本机，符合 §8.2"本地加密存储"，避免服务端集中存储海量用户 Cookie 的 PIPL 与单点泄露风险。
2. **反封禁**：各用户从各自 IP / 设备发起投递，避免服务端共享 IP 段被平台一次性识别封禁（集中式模型会让所有用户连带受灾）。
3. **合规**：本机执行更接近"用户本人操作"，责任边界清晰。
4. **成本**：浏览器实例池下沉到用户机器，服务端无需承担大规模浏览器集群算力。

### 15.2 被否决的备选：服务端集中式

- **方案**：服务端统一运行浏览器实例池，移动端"服务端执行"。
- **否决原因**：① 与 §8.2 本地存储直接矛盾；② 共享出口 IP 极易被平台风控团灭；③ 集中存储 Cookie 触发重大合规与单点泄露风险；④ 实例池"≤3"在海量用户下不可行。
- **备注**：若未来做"托管投递"增值服务，需独立评估合规并改用隔离容器 + VPC 出口，不在 v1.0 范围。

```
│ 浏览/确认/查看│   │ 配置/查看    │        │  API 网关                     │
└──────┬───────┘   └──────┬───────┘        │  ├ 账号/简历(加密)            │
       │                  │                │  ├ 岗位聚合 + AI 匹配         │
       └────────┬─────────┘                │  ├ 调度编排(生成任务/幂等键)   │
                │ 指令/状态                 │  ├ 日报生成 + 推送            │
                ▼                          │  └ LLM 服务接入              │
       ┌────────────────────────┐         └───────────────┬──────────────┘
       │   调度服务 ↔ 本机 Agent  │◄──长连接/推送─────────────┘
       │   (指令下发 / 状态回收)  │
       └──────────┬─────────────┘
                  │ 取 Cookie + Playwright
                  ▼
       ┌────────────────────────────────────┐
       │   本机 Agent（用户机器）              │
       │   浏览器实例池 ≤3 / Cookie 本地加密  │──► 各招聘平台
       └────────────────────────────────────┘
```

### 15.4 执行时序（移动端确认投递）

移动端确认 → API 网关 → 调度服务生成任务（`idempotency_key`）→ 长连接/推送通知本机 Agent → Agent 取本地 Cookie 执行 Playwright → 回写状态 → 服务端聚合 → 触发联动（模块 7）→ 推送结果。
**约束**：本机 Agent 需在线；离线时任务入队，Agent 上线后拉取执行（与 §6.2 边界一致）。

### 15.5 实例池与扩展

- 每用户本机 ≤3 并发实例（§6.2）。**注意**：此"3"指**本机浏览器并发实例数（资源上限）**，与 §12 免费版"≤3 平台"的**套餐权益（平台数量上限）**含义不同，二者不冲突。
- **多平台实例分配策略**：3 个本机实例在首期平台（BOSS / 猎聘 / 智联等）间按"活动任务数"动态分配，单平台至少保障 1 个实例；某平台长时间无任务则该实例休眠，资源让渡给其他有任务平台；高优先级任务（L0 实时，见 §6.4）可抢占空闲实例。
- 横向扩展由用户数自然分摊，服务端无浏览器算力瓶颈。
- Agent 自动更新机制复用适配器版本管理（模块 4）。

## 16. 商业化测算与单位经济（Unit Economics）

> 原 §12 定价为"建议方案，待校准"。本章补充成本结构与盈亏平衡测算，作为定价校准依据。

### 16.1 成本结构（单活跃用户 / 月估算，含假设）

| 成本项 | 估算逻辑 | 月成本（¥） |
|--------|---------|------------|
| LLM 匹配度评分 | 80–100 岗/日 × ~3k token ≈ 9M token/月，境内大模型（如 DeepSeek）~¥1–2/M | 9–18 |
| LLM 面试题生成 | 每日联动 ~20–40 岗 × ~2k token | 4–10 |
| LLM 简历优化 / ATS / 面试评估 | 按使用频次估算 | 2–7 |
| 基础设施 | 存储、API、推送、Agent 分发 | 2–5 |
| **合计** | | **≈ 17–40 / 活跃用户** |

- 免费版（30 份/天）占用约 30% 的 LLM 成本却零收入，需靠付费转化覆盖。

### 16.2 收入与盈亏平衡

- 定价：专业版 ¥19.9/月、高级版 ¥49.9/月（§12）。
- 假设付费结构 免费:专业:高级 = 70%:25%:5%，则 **ARPPU ≈ ¥7.2 / 总用户**。
- 单付费用户毛利：专业版 ¥19.9 − 成本（含免费用户摊薄）后偏紧，存在 **单位经济为负** 的风险敞口。

### 16.3 敏感性结论

- 若 LLM 单价下降 50%，或匹配改为"规则引擎为主 + LLM 兜底"（见 §7.3），成本可压至 ¥10–20，专业版转正。
- **付费转化率需 ≥35%** 才能覆盖含免费用户的混合成本。
- 当前定价在 LLM 成本高位下单位经济偏紧，建议：① 对免费 / 低活用户限制 LLM 调用频次；② 匹配度评分批量异步化 + 结果缓存；③ 上线后按真实成本刷新 §12。

### 16.4 待补充

- 上线后 30 天实测单用户 LLM token 消耗与 infra 成本，回填本节并校准定价。
- 投递记录保存期限（§8.2）与 PIPL 最小必要原则的一致性，在合规终审（§17.3）确认。

### 16.5 真实可行性与适配器维护成本（补全 §16 假设）

- **真实通过率假设需验证**：§16 单位经济建立在"自动投递可稳定跑通"上。需在 v0.9 灰度实测各平台真实投递成功率与日均可投上限（受反爬 / 验证码 / 限额制约），回填 §3 的"80–100 份 / 天"目标——若该值显著低于目标，单位经济与定价需重估。
- **适配器维护是持续成本**：主流平台 DOM / 风控频繁变动，单个适配器平均维护 0.5–1 人天 / 月（首期 4 平台 ≈ 2–4 人天 / 月；扩展至 10 平台后 ≈ 5–10 人天 / 月），须计入 §16.1 的"工程人力"，当前测算低估。
- **嵌入 / 向量与解析成本**：匹配与简历解析若引入向量库 embedding，按单用户日解析 ~100 份估算，embedding 成本约 ¥0.5–2 / 月，计入 §16.1 LLM / 推理项。

### 16.6 获客与 LTV / CAC（补全商业闭环）

- **CAC 假设（v1.0）**：应届生 / 求职群体获客以内容种草（小红书 / 知乎 / B 站）+ 校园渠道 + 口碑为主，假设 CAC ≈ ¥8–15 / 注册，付费转化 25% 下[CAC / 付费用户] ≈ ¥32–60。
- **LTV**：按 §16.2 ARPPU ≈ ¥7.2 / 总用户、付费用户月费 ¥19.9 × 留存（假设 12 个月生命周期）≈ ¥239 / 付费用户。
- **健康线**：LTV / CAC ≥ 3 才健康。当前粗略 LTV（¥239）/ CAC（¥32–60）≈ 4–7.5，表面可行，但**高度依赖 CAC 假设与付费转化**；若 CAC 升至 ¥30 / 注册 或 转化 <15%，则不打平。
- **结论**：§16 原测算只覆盖留存用户经济，补齐 CAC / LTV 后，商业成立性取决于获客效率，建议在 v0.9 灰度同步测 CAC 与付费转化，作为定价 / 投放决策输入。

## 17. 合规应急预案与最坏情况处理

### 17.1 风险重定性

原 §1 风险"中高"上调为 **高（可控级，非生存级）**：自动投递处于平台 ToS 灰区，叠加《反不正当竞争法》《个人信息保护法》潜在适用，任一主流平台采取法律 / 技术行动都可能冲击业务连续性。鉴于本产品定位为**半自动化投递（用户确认）+ 数据不上云**的求职者辅助工具（见 §32.1 / §32.4），平台风险由「生存级」下调为「可控级」：单平台受限即降级、不触发全域归零，极端情形下仍可保留简历管理与面试备战价值（§17.5）。个人信息泄露的法定通报流程（PIPL 第 57 条）专项见 §24.4。

### 17.2 最坏情况清单与预案

| 场景 | 概率 | 影响 | 预案 |
|------|------|------|------|
| 平台发律师函 / 停止函 | 中 | 极高 | 法务 48h 内响应；暂停涉事平台投递；准备"本机 Agent = 用户本人操作"申辩材料；公关口径统一 |
| 平台升级反爬 / 强验证（每次登录需短信） | 高 | 高 | 适配器快速迭代；Cookie 失效检测自动暂停；引导用户本机重新扫码；无法突破时该平台降级为"仅手动" |
| 账号批量被封 | 中 | 高 | 单平台日限额 70%（§6.2）；行为模拟；封禁后暂停并通知，不自动换号（**备用账号为 v1.0 后置能力，见 §5.4**） |
| 应用商店以"违反第三方 ToS"拒审 / 下架 | 中 | 高 | 分发改用官网 / TestFlight / 企业分发（详见 §17.6）；App 内不展示"自动投递"字眼，改用"简历投递助手"；准备合规说明 |
| 监管约谈 / 数据安全举报 | 低 | 极高 | Cookie 本机存储（§15）降低责任面；准备数据最小化与可删除证明（§8.3）；配合整改 |

### 17.3 法务评审里程碑（补入 §9.3 时间线）

- Day 3 法务合规初评（合规风险清单、免责声明框架、分发合规方案）
- Day 62 合规终审（上线前合规签字）
- 适配器重大版本更新触发合规复审（复用模块 4 版本管理）。

### 17.4 用户告知与免责

- 首次使用前签署免责声明（§8.1 已有），明确账号风险自担、平台政策变动可能导致功能受限。
- 产品内对"自动投递"字样做合规化表述，避免明示规避平台风控。
- 伦理声明：系统仅替用户向"用户本人账号"投递其真实简历，不伪造身份、不代写、不谎称"真人主动沟通"；面试准备中生成的作答仅为练习，不替代用户真实表达（避免对 HR 构成误导）。

### 17.5 业务连续性

- 单一平台失效不中断其他平台（适配器健康熔断，模块 4）。
- 若核心平台（BOSS / 猎聘）同时受限，启动"手动投递引导模式"，保留简历 / 面试备战价值，维持留存。

### 17.6 分发合规与替代分发预案

自动投递类 App 处于各应用商店审核的敏感区：Apple App Store 审核指南 5.2.3 / 各安卓商店规则通常禁止"绕过或破坏第三方服务条款""自动化操作第三方账户"，明示"自动投递"大概率被拒审或上架后下架。本产品执行模型（本机 Agent，§15）天然将核心能力放在桌面端官网分发，移动端仅做确认 / 浏览，可显著降低商店风险面，但仍需完备预案。

**预审合规化策略**
- 命名与文案：App 名称 / 商店描述使用"简历投递助手 / 求职管理"等中性词，不出现"自动投递""批量""爬虫"字眼；功能入口合规化表述（§17.4）。
- 材料准备：随包提交功能说明 + 合规声明，强调"操作发生在用户本人设备、使用用户本人账号、行为模拟真人、用户主动确认"。

**替代分发矩阵**

| 渠道 | 方案 | 适用阶段 | 限制 |
|------|------|---------|------|
| iOS TestFlight | 内部 100 / 外部 1 万名额，90 天有效期需重签 | 内测 / 早期用户 | 需邮箱或公开链接；有效期管理 |
| iOS 企业分发 | 企业开发者账号 In-House 分发 | B 端 / 内部团队 | 需 DUNS 资质，不可面向公众泛分发 |
| Android 官网 APK | 官网直下，用户开启"未知来源" | 全阶段 | 需引导安装信任；华为 / 小米等商店另走 |
| 安卓商店 | 华为 / 小米 / 应用宝等单独过审 | 合规沟通后 | 同 iOS 文案约束 |
| 桌面端 Agent | 官网下载 / 自更新（无商店限制） | 全阶段 | 天然规避商店审核，呼应 §15 本机执行模型 |

**灰度建议**：首期以"官网 + TestFlight + 桌面端官网"为主分发路径，应用商店作为 §17.3 合规终审通过后的补充渠道；若商店驳回，不阻塞发布，直接走替代矩阵。

**用户告知**：安装引导中明确"本应用来自官网 / TestFlight、操作对象为用户本人招聘账号、需自担平台政策风险"（呼应 §17.4 免责）。

### 17.7 账号封禁处置与客服 SLA

- **封禁处置流程**：账号被封 → 自动暂停该平台 → 推送通知用户 → 提供平台解封指引 → 用户解封后一键恢复；期间不自动换号、不自动重试。
- **客服响应 SLA**：封禁 / 无法投递类问题 P1，工作日 ≤4h 首次响应、≤24h 给出处置方案；普通咨询 ≤1 工作日。
- **责任边界**：账号风险由用户自担（§17.4 免责），平台封禁导致的求职机会损失不在赔付范围；产品提供"及时暂停 + 清晰告知 + 快速恢复"以降低损失。
- **运营手册**：封禁话术、解封指引、常见平台风控规则沉淀为运营知识库，随适配器版本更新。
- 用户申诉的工单载体、SLA 跟踪与审计关联详见 §23.13（客服工单系统）。

## 18. 非功能需求（NFR）

### 18.1 可用性目标

| 对象 | 目标 | 口径 |
|------|------|------|
| 本机 Agent 进程存活 | ≥ 99.5%（7×24 常驻，崩溃 30s 内自重启） | 投递能力可用性，依赖用户 PC 在线（§15 约束） |
| 后端 API / 调度服务 | ≥ 99.9% | 月度可用时间 |
| 每日日报推送准时率 | ≥ 99%（在用户设定推送时间 [默认 20:00] 后 30 分钟内送达） | 见模块 9 日报 |
| 移动端投递确认可达 | ≥ 99.9%（推送通道） | 依赖厂商推送通道 |

> 已知约束：投递依赖用户 PC 在线（本机 Agent 模型），PC 关机 / 离线时投递暂停，不视为服务不可用，但需在移动端明确提示"PC 离线，投递待执行"。

### 18.2 容量与并发预估

- **用户规模假设（v1.0）**：本产品定位为极早期 0-to-1，v1.0 实际为**小规模灰度**（内部 + 受邀用户，预计 DAU < 200）；下表 MAU 1 万 / DAU 3000 / 单用户日投递峰值 ~100 份为**演进目标**，用于 infra 容量规划上限，上线后以真实 DAU 回填并校准（见 §16.4）。
- **投递 Worker**：执行在本机 Agent，无集中式瓶颈，天然水平扩展；每用户本机 ≤3 并发实例（§6.2 / §15.5）。
- **后端并发参考**：按 DAU 3000 × 双峰系数（晨 8–9 点、晚 20–22 点，取 3×均值）估算，后端 QPS 峰值约 **30–50**（读多写少，投递任务异步）；据此选型，预留 2× 余量。
- **采集负载计入容量模型**：岗位采集（§21.1）每用户每 6h 增量 + 每日全量，估算每用户约 50–100 次/日采集读取；按 DAU 3000 折合约 5–10 QPS 峰值（与投递错峰），已纳入总容量评估，避免仅按投递 QPS 低估；上线后以真实采集日志回填（§16.4）。
- **扩容阈值**：DAU 突破 1 万 或 后端 CPU 持续 >70% 触发垂直 / 水平扩容评审。

### 18.3 性能与延迟

对齐 §7.4：匹配度计算 ≤5s、面试题生成 ≤30s（异步）、作答评估 ≤3s、简历优化 ≤10s、投递后联动 ≤5min。日报生成（模块 9）作为后台任务，目标在用户设定推送时间 [默认 20:00] 前完成，单次生成 ≤2min。

### 18.4 可观测性与监控

| 维度 | 要求 |
|------|------|
| 日志 | 结构化日志（JSON），投递任务含 `idempotency_key`（§6.2）、平台、状态、耗时；敏感字段（Cookie / 简历原文）脱敏 |
| 指标 | 投递成功率、单平台封号率、HR 查看率、面试邀请率、任务延迟 P50/P95、Agent 在线率（对接 §10 看板） |
| 告警 | 封号率突增（>5%/日）、反爬升级（验证码触发率 >20%）、Agent 离线率异常、后端错误率 >1% → 自动暂停相关投递并通知 |
| 链路追踪 | 关键链路（确认 → 唤醒 → 投递 → 联动）TraceId 贯通，便于定位失败 |
| Oncall | 封号 / 反爬类告警 P1 响应；值班与升级路径写入运维手册（事件分级 SEV 与升级路径详见 §24.1） |
| **监控自身失效（deadman's switch）** | 监控 agent / 采集管道失联、指标长期无更新即触发「无数据告警」，避免黑盒运营；关键看板（Agent 在线率、投递成功率）缺失数据本身作为 P2 告警，而非默认「正常」 |

### 18.5 安全与韧性补充

- Agent 进程自愈（崩溃自重启）、断网续投（恢复后按 `idempotency_key` 续跑，§6.2）。
- 投递幂等（§6.2）与部分失败隔离（单平台失败不影响其他，§17.5）。
- 数据备份：服务端投递 / 面试记录每日增量备份，RPO ≤ 24h、RTO ≤ 4h；Cookie 不备份（本机，§15）。

## 20. 系统核心实体与数据模型（草稿，供 LLD / 工程评审）

> 本节为工程交接提供核心实体与状态机草稿，非最终 DDL；字段以"必填 / 关键"为主，落地以详细设计为准。

### 20.1 实体与关系
- **User（用户）**：id、手机号（加密）、邮箱、注册渠道、创建时间、状态（active/disabled）。
- **Resume（简历）**：id、ownerId、版本号、原文/解析结果（加密）、embedding 引用、更新时间。
- **Job（岗位）**：id、来源平台、平台岗位 ID、标题、公司、JD 原文本、要求标签、解析时间、去重指纹（跨平台同岗合并）。
- **Application（投递记录）**：id、`idempotency_key`、userId、jobId、platform、status、attempts、failReason、createdAt、finishedAt。（保存期限见 §8.2）
- **DailyReport（日报）**：id、userId、日期、投递汇总、查看/邀请汇总、面试题清单、生成时间、推送状态。
- **Notification（通知）**：id、userId、`event_key`、level(L0–L3)、channel、content、read(bool)、createdAt、expireAt(90d)。
- **Subscription（订阅）**：id、userId、plan(free/pro/pro_max)、status、periodStart、periodEnd、graceUntil。
- **AdapterConfig（适配器配置）**：platform、version、enabled、healthStatus、lastCheck。
- **ConsentLog（同意留痕）**：userId、consentType（隐私政策 / AI 委托处理 / 推送授权）、version、scope、signedAt（PIPL 告知同意审计，§8.3 / §8.4）。

关系：User 1—N Resume / Application / Notification / Subscription；Job 1—N Application；User 1—1 DailyReport / 日。

### 20.2 关键状态机
- **Application**：`pending`（入队）→ `queued`（待本机 Agent 拉取）→ `running`（执行中）→ `success` / `failed`；`failed` 经重试（指数退避 ≤3，§6.3）可回到 `running`，超次置 `failed` 并推 L1。PC 离线时停在 `queued`（云端待执行队列，不计失败）。
- **Subscription**：`trial` → `active` →（`grace` 宽限 7 天，§12）→ `expired` → `downgraded`（回 free）；续费成功回到 `active`。
- **Notification**：`sent` → `read` / `deleted`；到期 `archived`。
- **AdapterConfig**：`enabled` ⇄ `disabled`（healthCheck 连续 3 次失败自动 `disabled`，§6.2）；平台协议变更标记 `need_update`。

### 20.3 配置与同意审计
- **UserConfig**：投递策略（日限额 / 平台偏好）、匹配阈值、推送时间、免打扰时段、聚合粒度（§6.4）；多端同步，存服务端、本机 Agent 拉取。
- **ConsentLog** 为合规强制：每次同意 / 授权变更留痕，支持监管核查与用户查询（§8.3 / §8.4）。

### 20.4 待细化（入 LLD）
- 索引与分库策略、embedding 存储选型、加密字段的密钥管理（Secrets，见 §16 成本项）、数据导出标准格式（§8.3 停服导出）。

### 20.5 密钥与凭证管理（Secrets）
- 服务端密钥（LLM API Key、推送证书 APNs/FCM 私钥、加密主密钥）统一经密钥管理服务（KMS）存储，**禁止硬编码 / 入代码仓库 / 打印日志**。
- 加密主密钥与数据加密密钥分离（信封加密），定期轮换；轮换不影响已加密数据的正常读取。
- 本机 Agent 的 Cookie 不离开用户设备（§8.2 / §15），不上云、不进 Secrets 管理。
- 证书 / 密钥泄露应急：支持远程吊销与秒级轮换（呼应 §18.4 告警与 §17 预案）。

## 21. 系统基建专项（采集 / 限流 / 灾备）

> 本章补齐前期评审遗漏的系统基建设计对象：岗位数据从哪来、服务端如何防滥用控成本、本机 Agent 失效如何恢复。均为 🔴 级工程必需项。

### 21.1 岗位采集与数据源策略

- **采集方式**：以平台内搜索结果页为主（经适配器 Playwright 抓取）+ 用户订阅关键词触发；主流招聘平台无公开官方 API，不依赖 API 渠道。
- **增量更新频率**：每用户任务每 6 小时增量刷新岗位列表（避开 HR 高峰时段），全量刷新每日一次；新岗位进入匹配队列（§7.5）。
- **跨平台去重**：Job 实体以「平台 + 岗位 ID」为自然键（§20.1）；同一集团跨平台重复发布通过「公司名 + 岗位名 + 城市」指纹去重，避免向同名岗位重复投递。
- **反爬耦合**：采集节奏与投递节奏统一纳入本机 Agent 的随机延迟与限额策略（§6.1），高频 / 同出口抓取会触发风控（§16.5），二者共用一套频控。
- **僵尸岗过滤**：HR 超 7 天未活跃岗位（见术语表）不进入投递队列。
- **新鲜度 SLA**：岗位展示标注采集时间；超过 48 小时未刷新的标记为「可能失效」并提示用户二次确认，不直接投递。

### 21.2 服务端限流与配额

- **用户级调用限流**：服务端对用户 API 调用采用令牌桶限流（默认 10 req/s，突发 20），防止单客户端异常打满后端。
- **调度信令限速**：服务端调度器对「唤醒本机 Agent」的信令下发做全局平滑（按用户分桶），避免瞬时大量推送压垮 APNs / FCM（渠道见 §6.4）。
- **套餐配额**：免费版 / 专业版 / 高级版的日投递配额见 §12 定价；超限返回 429 并提示升级，不影响已在途任务。
- **防滥用**：单账号异常高频（如 1 分钟内数百次匹配请求）触发风控拦截 + 二次验证，防止凭证被盗用刷接口。
- **LLM 配额**：LLM 调用设每日 token 预算上限（按套餐），超限降级为规则匹配（§7.5），保证单位经济可控（呼应 §16）。
- **深化**：运行时成本护栏与风控细节（实时双闸 / 投递速率熔断 / 发布门禁）见 §28。

### 21.3 本机 Agent 灾备与恢复

- **不备份原则**：Cookie、本机在途投递进度不落服务端（§8.2 / §15 / §20.5）。
- **PC 损坏 / 重装恢复路径**：
  - 新设备重装 Agent 后，通过账号登录拉取**非敏感配置**（匹配阈值、投递时段、订阅关键词、通知设置），云端同步（§20.3）；
  - Cookie 需用户在新设备重新登录各平台（安全约束，不可云同步），Agent 引导式重新授权；
  - 投递记录 / 日报历史由服务端持有（§8.2 保留 24 个月），登录即可恢复查看，无需重投。
- **幂等保恢复**：重装后未完成任务以 `idempotency_key`（§6.2 / §20.2）去重，避免重装导致重复投递。
- **进程自愈**：Agent 崩溃自重启；本地任务队列持久化到本机磁盘（非内存），断网恢复后按 key 续跑（§6.2）；重启不丢任务。
- **本地库 corruption 检测与恢复（补充，防磁盘坏道/异常断电致 SQLite 损坏）**：
  - **检测**：Agent 每次启动与周期性（如每 30 分钟）对本地库做 `PRAGMA integrity_check`；写入采用 WAL + 原子事务，降低半截写入损坏概率。
  - **快照**：本地库每日做一次轻量快照（仅结构 + 任务状态 + 去重 key，不含 Cookie/简历原文），存于独立文件；损坏时从最近完好快照重建，而非整库丢弃。
  - **损坏时 fail-safe**：检测到 corruption 且快照不可用 → 进入 §23.2 受限安全模式 + 显式弹窗「本地数据异常，已暂停自动投递，请重装或联系支持」，**绝不静默放行**；Cookie 本地加密损坏等同失效，引导用户重登（安全约束，不可云恢复）；在途任务去重状态丢失时，宁可「重登后重新确认队列」也**不自动续投**，避免丢失去重 → 重复投递（呼应 §6.2 / §20.2 idempotency_key）。
- **降级边界**：用户长时间无可用 PC（离线），投递暂停并通知（§6.3），**不自动转服务端执行**（与 §15 执行模型一致）。

## 22. 系统缺口补足（环境 / 支付 / 审计 / 缓存 / 资源 / 容量）

> 本章补齐评审末轮（v3.5）盘点仍缺失的 6 项 🔴 级系统必需设计：多环境隔离、支付对账与掉单、操作审计日志、缓存策略、本机 Agent 本地资源限流、采集容量与容量模型。均为"无则产品上不了线 / 出事难追责"的硬需求。

### 22.1 多环境隔离（dev / staging / prod）

- **环境严格隔离**：dev、staging、prod 三套环境的后端、数据库、Secrets（KMS 域）、消息通道相互隔离，配置与凭证按环境分域，prod 凭证不进 dev / staging。
- **本机 Agent 环境标识**：Agent 构建时注入环境 tag，仅 **prod 版 Agent** 连接 prod 后端与真实招聘平台；dev / staging 版连接沙箱，禁止触碰真实平台。
- **防误投硬约束**：非 prod 环境（含本地调试）**一律禁止连接真实招聘平台**，统一使用 mock 适配器或平台沙箱账号；CI / 自测触发投递任务时，目标平台校验环节拦截真实域名。
- **灰度用户数据隔离**：受邀灰度用户归入 prod 独立租户标签，其采集 / 投递行为可单独观测与回滚，不影响全量。

### 22.2 支付对账与掉单

- **订单状态机**：待支付 → 已支付 → 已开通 → 已过期 → 已退款（升级 / 降级 / 退订均经此流转，与订阅实体 §20.3 对齐）。
- **掉单处理（高·可控级，非生存级）**：支付商回调可能因网络丢失未达后端。定时对账任务每 15 分钟拉取支付商流水，与本地订单比对，差额自动补单（支付成功未开通）或发起退款（重复扣款），并通知用户；兜底为「原路退回 + T+3 到账」（见下方「退款 SLA」），不产生不可逆资损，与 §1 / §17.1 / §32.1 统一风险定级一致。
- **自动续费失败**：扣款失败（卡过期 / 余额不足）进入 **3 天宽限期**并提醒；宽限期满未恢复则降级为免费版（不立即停服、不删数据），用户补款后即时恢复权益。
- **发票与税务**：经用户确认不涉及企业报销 / 专票场景，发票税务细化暂不展开（见 §19「已排除」）；本节仅保留基础退款对账（原路退回、T+3 到账，见上「退款 SLA」）。
- **退款 SLA**：功能不可用或 7 天无理由退款，原路退回，T+3 内到账。

### 22.3 操作审计日志（非同意类）

- **与 ConsentLog 区分**：§20.4 的 ConsentLog 记录"用户授权同意留痕（PIPL）"；本节记录**操作溯源**——谁、在什么时间、对什么对象、做了什么。
- **记录范围**：策略变更、投递任务触发、封禁 / 解封处置、账号绑定 / 解绑、权限变更、配置导出、关键通知发送。
- **不可篡改**：append-only（WORM）写入，保留期与 §8.2 一致（24 个月，满 36 个月删除）；敏感字段（Cookie / 简历原文）脱敏。
- **用途**：纠纷举证、安全溯源、合规配合、封禁申诉核验（呼应 §17.7）。
- **用户可见**：用户在"账号 → 安全"中可查看自己的关键操作日志，透明度对齐隐私承诺。

### 22.4 缓存策略

- **岗位列表缓存**：TTL 6h，与采集频率（§21.1）对齐，降低重复抓取与反爬风险，同时减少 infra 读取成本。
- **匹配结果缓存**：按「简历版本 + 岗位 ID + 匹配阈值」维度缓存；简历更新 / 阈值变更即失效，避免用旧结果错投。
- **UserConfig 缓存**：本机 Agent 内存 + 磁盘双缓存，变更即时失效，保证策略实时生效。
- **缓存层级**：本机 Agent 本地缓存（低延迟）+ 服务端 Redis（跨端共享 / 多端同步）。
- **一致性**：采用写失效（write-invalidate），杜绝脏数据导致错投；命中率目标 ≥ 80%，以降低 LLM / 采集调用（控单位经济，呼应 §16）。

### 22.5 本机 Agent 本地资源限流

- **资源上限（默认）**：单 Agent 进程 CPU ≤ 15% 单核持续 / 峰值 ≤ 40%；常驻内存 ≤ 300MB；采集 / 投递网络吞吐 ≤ 2Mbps，且与用户前台操作错峰。
- **实例隔离**：单浏览器实例 OOM / 卡死不影响其他实例，超时自动回收（呼应 §6.1 实例池）。
- **用户可调**：低端机可在设置中下调并发实例数（< 3），以保系统流畅；默认取 ≤3。
- **不打扰用户**：Agent 后台进程设为低优先级，用户前台高负载时主动让出 CPU / 带宽，避免拖垮用户电脑（本机 Agent 模型的核心体验承诺，见 §15）。

### 22.6 采集容量与容量模型

- **采集端限流**：每用户采集任务并发 ≤ 2（与投递实例错峰），失败按指数退避重试（最大 3 次）；单用户采集 QPS 受 §21.2 全局限流约束。
- **容量并入总模型**：岗位采集负载已计入 §18.2 容量（每用户约 50–100 次/日读取，DAU 3000 约 5–10 QPS 峰值），与投递 30–50 QPS 叠加后总峰值约 **35–60 QPS**，据此选型并预留 2× 余量。
- **成本联动**：采集读取计入服务端 infra 与（若用 LLM 解析岗位 JD）token 成本，已纳入 §16 单位经济；高采集频率用户触发 §21.2 LLM 预算降级。
- **回填机制**：上线后以真实采集 / 投递日志回填 §18.2 与 §16.4，校准容量与成本假设。

## 23. 系统韧性、兼容与安全专项（S1–S13）

> 本章补齐"本机 Agent 架构 + 多端协同"特有、且前稿未正式设计的系统层缺口。S1–S6 为 🔴 真缺口（从未设计、对本机 Agent 架构致命）；S7–S13 为 🟠 需深化项（在既有章节基础上补全机制）。

### 23.1 三端版本兼容与契约管理（S1）

本产品存在三个独立演进的组件：**本机 Agent（A）**、**移动端壳（M）**、**后端 API（S）**。用户未必及时更新 Agent/移动端，版本必然不同步，需显式契约管理。

- **版本号规则**：三端各自语义化版本（MAJOR.MINOR.PATCH）；另设独立的 **API 契约版本（contract_version）**，由后端定义并向客户端声明。
- **向后兼容承诺**：后端 API 保证对 **最近 2 个主版本** 的旧客户端向后兼容；破坏性变更必须经由"双写/双读过渡 ≥ 1 个发布周期"完成，禁止直接断旧。
- **版本协商握手**：Agent / 移动端启动时上报 `client_version + contract_version`；后端返回 `negotiated_capabilities`（能力集），客户端据此裁剪可用功能。
- **落后降级策略**：
  - 落后 ≤ 2 个主版本 → 功能裁剪降级（如新匹配模型不可用则回退 §7.5 规则匹配；新通知类型降级为通用提示）。
  - 落后 > 2 个主版本 → 强制弹窗提示更新，**过渡期内仅允许查看 / 手动操作，禁止自动投递**（安全红线，防止旧逻辑与新风控/新契约冲突导致错投或误封）。
- **移动端壳**：更新经应用商店，落后时隐藏新功能入口，不展示未实现能力。
- **契约测试**：CI 接入 consumer-driven contract test（Pact 类），后端变更自动校验不破坏已发布旧客户端，作为发布门禁。

### 23.2 本机 Agent 自身安全模型（S2）

前稿只防"招聘平台风控"，未防"Agent 自身"。Agent 是用户机器上的持久进程，需独立威胁模型。

- **威胁模型**：本地提权 / 沙箱逃逸、简历 / 岗位内容注入（本地渲染 XSS）、Playwright / 浏览器二进制供应链投毒（SBOM）、Agent 被远程滥用为跳板 / C2。
- **沙箱与最小权限**：Agent 以**普通用户权限**运行，不请求管理员；文件系统仅限自身目录（如 `~/Library/Application Support/ResumeAgent` 或 `%APPDATA%/ResumeAgent`）；网络出向**白名单**（仅招聘平台域名 + 后端域名 + 配置中心域名），其余拒绝。
- **内容注入防护**：岗位 / 简历文本渲染走纯文本或受控组件，**禁止 `innerHTML`**；JD 内链接默认不自动打开；解析走隔离解析器，避免恶意 HTML 在本地渲染执行。
- **供应链安全**：Playwright / 浏览器二进制**固定版本 + 哈希校验（SBOM）**；自动更新须经签名校验；禁止加载任意远程脚本 / 第三方脚本。
- **防远程滥用**：Agent 仅执行用户**明确确认**的任务；远程信令通道（§6.4 / §15）只能"唤醒"，投递指令须用户侧二次确认，**不可被远程强制注入**（呼应 §15 执行模型与 §17.4 伦理）。
- **自校验**：启动时校验自身二进制 / 配置完整性（签名 + 哈希），异常则拒绝运行并提示官方渠道重装。

### 23.3 Schema 演进与数据迁移（S3）

运行期字段变更的迁移机制，§8.3 仅覆盖"停服导出"，运行期零停机迁移需单独设计。

- **版本标记**：所有持久化表带 `schema_version`；迁移脚本版本化、幂等、可回滚。
- **双写过渡**：字段变更先双写（新旧字段并存）≥ 1 个发布周期，数据校验一致后切读，再择机删除旧字段。
- **在线迁移**：大表分批（batch）迁移并限流，避免影响投递任务 QPS（§18.2 / §21.2）。
- **历史回填工具**：提供 `backfill` 脚本并支持 `dry-run`；迁移期间旧 Agent（§23.1）仍可读旧 schema，保证兼容窗口。
- **回滚**：迁移失败可一键回滚至上一个 `schema_version` + 数据快照，不丢投递 / 面试记录。

### 23.4 服务端 DR 演练与故障切换 + Agent 降级（S4）

§18.5 已有备份 RPO/RTO，但缺跨区域切换、演练机制与"后端宕机时 Agent 行为"。

- **多可用区**：后端核心无状态服务跨 AZ 部署；有状态（DB）异步复制，RPO 对齐 §18.5（≤ 24h）。
- **故障切换**：自动健康探测 + 人工确认切换；**切换 RTO 目标 ≤ 30min**（高于数据 RTO，含服务拉起与流量切回）。
- **DR 演练**：每季度一次 chaos / 故障注入演练（关停单 AZ、杀 DB 主、断网分区），记录实测 RTO 并纳入 §18.5 复盘。一般生产事故的"人的响应流程"演练（Game day）见 §24.11。
- **后端宕机时 Agent 行为（关键）**：本机 Agent 必须能**纯本地降级运行**——已确认投递任务照常执行（本地队列，§21.3），仅"查看 / 同步 / 推送"受损；**不卡死、不重复投递**（幂等键 §6.2）；后端恢复后经 §6.4 信令通道增量重连同步。此降级是 §15 本机模型的核心韧性承诺。

### 23.5 配置中心与远程下发（S5）

§9.4 提了 Feature Flag 概念但未定平台与 Agent 拉取方式。

- **平台**：采用配置中心（Nacos / Apollo / 自研 KV），与 Feature Flag（§9.4）共用同一通道。
- **可热更项**：限流阈值（§21.2）、匹配权重（§7.5）、熔断开关、采集频率（§21.1）、推送文案（§6.4）。
- **Agent 拉取**：启动时拉全量 + 长连接 / 轮询增量（≤ 5min 生效）；**本地缓存配置，后端不可达时用最后已知配置，不阻塞投递**（与 §23.4 降级一致）。
- **灰度发布**：配置支持按用户标签灰度（如 5% 用户先吃新权重 / 新文案）。
- **安全**：配置传输加密 + 签名校验，防中间人篡改限流 / 熔断导致滥用或误封。

### 23.6 连接管理：弱网 / 代理 / 离线队列上限（S6）

§6.4 提了信令通道心跳但未展开弱网 / 代理 / 离线边界。

- **心跳与重连**：长连接心跳 30s、连续 3 次丢失判定断线、指数退避重连（最大间隔 5min）；重连加 **jitter** 防惊群。
- **弱网**：请求超时与指数退避重试；重要操作（确认投递）**先本地落盘再异步上报**，网络恢复后补推。
- **代理 / VPN**：本机 Agent 支持用户配置系统代理；公司网络屏蔽招聘平台时提示用户切换网络，**不自动翻墙**（合规红线，§17）。
- **离线队列上限**：本机未确认 / 未上报任务队列上限 **500 条**；超限丢弃最旧非关键项（如浏览埋点），关键投递任务优先保留并提示用户。

### 23.7 压测与混沌工程（S7，深化 §18.2 / §18.5）

- **上线前压测**：按 §18.2 容量模型（DAU 3000 峰值 35–60 QPS）做 **1.5× 压测**，验证 P99 延迟与错误率门禁。
- **混沌注入**：后端宕机（§23.4）、DB 延迟、Agent 崩溃自愈（§21.3）、网络分区（§23.6）。
- **发布门禁**：压测 / 关键混沌不过不发布；季度 DR 演练（§23.4）复用同一套混沌用例。

### 23.8 日志留存与 trace 采样成本（S8，深化 §18.4）

- **留存期**：应用日志 30 天、审计日志 24 个月（§22.3）、分布式 trace 7 天。
- **采样**：trace 默认 **10% 采样、错误 100%**；高成本日志（LLM 请求体）默认不记全文，仅记 token 计数，控 §16 成本。
- **成本预算**：日志 / 监控成本计入 §16 单位经济，超预算触发降采样（先降非关键日志）。

### 23.9 缓存击穿 / 雪崩防护（S9，深化 §22.4）

- **随机过期**：TTL 加随机抖动，避免同批 key 同时失效。
- **击穿**：热点 key（如热门岗位列表）单飞（singleflight）回源，防并发击穿 DB。
- **雪崩**：多级缓存（本地 + Redis），Redis 不可用降级本地并限流；与 §22.4 写失效联动，防错投。

### 23.10 多端配置冲突解决（S10，深化 §5.4）

- **权威源**：服务端为配置权威（§5.4）。
- **冲突检测**：客户端上报本地版本号 + 修改时间戳；服务端按 **最后写入获胜（LWW）+ 版本向量** 防乱序覆盖。
- **并发冲突**：PC 与移动端同时改 → 服务端以带时间戳的后者覆盖，并推送"配置已更新"通知（§6.4）让另一端刷新，**不静默**。
- **用户可感知**：冲突解决后两端一致，必要时弹"配置已被其他设备更新"提示。

### 23.11 数据导出 schema 细化（S11，深化 §8.3）

- **格式**：JSON（主，含嵌套） + CSV（投递记录子集），UTF-8，zip 打包。
- **字段**：Resume（脱敏后）、Application（平台 / 岗位 / 状态 / 时间）、DailyReport、InterviewRecord、ConsentLog。
- **PIPL 数据携带权（第 45 条）**：用户在"隐私 → 导出我的数据"一键生成，**≤ 24h 内可下载**；与 §8.3 停服导出共用同一 schema，保证格式一致。

### 23.12 A/B 实验框架（S12，深化 §10）

- **用途**：匹配权重（§7.5）、推送文案（§6.4）、日报模板迭代的科学归因。
- **机制**：用户级随机分流（按 `user_id` hash）；实验配置走 §23.5 配置中心灰度。
- **归因**：指标口径对齐 §10.3；实验组 / 对照组对比，显著性检验通过后全量。
- **护栏**：实验不影响核心安全——自动投递开关仍需用户确认（§15 / §17.4）。

### 23.13 客服工单系统（S13，深化 §17.7）

- **入口**：App 内"帮助 → 联系我们"、封禁通知内一键申诉（§17.7）。
- **载体**：轻量工单系统（自建或接入 SaaS），与通知中心（§6.4）联动推送处理进度。
- **SLA**：P1（封禁 / 支付）≤ 4h 首响、≤ 24h 给出处置方案，P2 ≤ 1 工作日，P3 ≤ 3 工作日（与 §17.7 一致）。
- **举证**：工单与操作审计（§22.3）关联，纠纷时一键拉取时间线。

## 24. 事件响应与韧性运营（P1–P11）

本章补足"生产事故发生后的响应体系"——§17 是合规最坏情况预案、§23.4 是基础设施 DR 演练，二者均属"预防 / 降级 / 合规"片段；本章补全"事故真的发生后如何分级、谁响应、怎么止血、怎么对外说、怎么复盘"，是本产品上线运营的必备能力。

### 24.1 事件分级与 Oncall 体系（P1）

将"生产事故 SEV"与"用户支持 P1–P3"**明确区分**：后者是服务台工单分级（§23.13），前者是工程 / 运营事故分级，混用会导致响应错位。

| 级别 | 定义 | 典型场景 | 响应时限 | 升级路径 |
|------|------|---------|---------|---------|
| **SEV1（致命）** | 影响大量用户核心功能或触碰合规 / 法律红线 | 误投超量全网、Cookie / 密钥泄露、PIPL 数据外泄、支付多扣、配置中心推错权重致全网异常 | 5 分钟内确认，15 分钟内止血 | 当班 Oncall → 技术负责人 → 业务负责人 / 法务（并行） |
| **SEV2（严重）** | 单平台 / 单区域核心功能受损，有降级方案 | 某平台适配器大面积失效、Agent 坏更新（部分用户）、推送通道中断 | 15 分钟内确认，1 小时内止血 | 当班 Oncall → 技术负责人 |
| **SEV3（一般）** | 局部 / 非核心功能受损，用户无感或弱感 | 日报延迟、某非核心指标异常、缓存命中率下降 | 30 分钟内确认，当日处理 | 当班 Oncall 自行闭环 |

- **Oncall 轮值**：7×24 轮值，单一故障域至少 2 人备份；告警路由与静默策略见 §18.4。
- **事故指挥（IC）**：SEV1/SEV2 须指定唯一事故指挥（Incident Commander），负责决策、对外口径、升级，避免多头指挥。
- **内部沟通渠道**：专用事故群 / 桥，所有动作留痕（对接操作审计 §22.3）。

### 24.2 事故响应 SOP / Runbook（P2）

通用处置流程（所有 SEV 适用）：

```
发现 → 定级(§24.1) → 止血(优先) → 诊断 → 恢复 → 用户告知(§24.7) → 复盘(§24.6)
```

针对本产品**最致命专属事故**的标准 Runbook（按图处置，避免临场拍脑袋）：

| 事故类型 | 止血动作（第一优先） | 恢复动作 | 关联章节 |
|---------|-------------------|---------|---------|
| 误投 / 超量投递 | 全局暂停投递队列 + 触发撤回（§24.3） | 定位异常策略 / 坏配置，修正后小流量验证 | §6.2 幂等、§24.3 |
| 坏更新全网（Agent 二进制） | kill switch 回滚到上一稳定版（§24.5） | 修复构建 + 灰度重推 | §9.4 回滚、§24.5 |
| 密钥 / Cookie 泄露 | 远程吊销密钥 + 强制用户重新登录（§20.5） | 轮换 + 排查泄露面 | §20.5、§24.4 |
| 支付多扣 | 暂停计费 + 触发对账补单 / 退款（§22.2） | 修复计费逻辑 + 用户补偿 | §22.2、§24.8 |

- Runbook 须随版本更新，纳入 onboarding 与 Game day（§24.11）演练。

### 24.3 误投 / 过量投递事后止血与撤回（P3）

**本产品最致命事故**：直接损害用户求职利益，且触及"伪造操作"合规红线（§17.4）。§6.2 幂等是"防"（防重复），§12 手动撤销是"用户自助"，但**事故级的批量撤回 + 告知 + 补偿**此前缺失。

- **事故级止血**：
  1. 立即全局暂停投递队列（§6.2 / §24.2），停止一切新投递；
  2. 按 `idempotency_key`（§6.2）+ 时间窗圈定受影响投递范围；
  3. 对已发出请求：平台支持撤回的（如 BOSS 直聘部分场景）调用撤回接口；不支持的标记"异常投递"并置顶用户提醒。
- **用户告知**：受影响用户在 App 内 + 推送（L0，免打扰豁免，§6.4）收到标准化通知（模板见 §24.7），含"发生了什么 / 影响范围 / 已采取动作 / 如何申诉"。
- **责任与补偿**：区分成因（见 §24.8）——若系**产品 bug 导致**，提供补偿（如延长会员、免费额度、协助向平台说明）；若系**用户误设策略**，引导用户自查并承担后果；若系**平台行为**，协助申诉但不担责。
- **合规兜底**：撤回动作本身须留痕（操作审计 §22.3）并遵守平台 ToS，不得为撤回而伪造身份。

### 24.4 个人信息泄露应急（PIPL 第 57 条）（P4）

**法律硬要求**（非工程优化）：发生或可能发生个人信息泄露、篡改、丢失，须立即采取补救、通知主管部门、告知个人。§17 合规预案此前缺专门"数据泄露通报"流程。

- **触发**：任何敏感数据（Cookie / 简历原文 / 手机号 / 身份证）疑遭未授权访问、泄露、丢失。
- **立即补救**（≤1h 启动）：吊销凭证（§20.5）、隔离受影响系统、封堵泄露路径、评估影响面（哪些字段、多少用户）。
- **告知义务**：
  - 主管部门：按规定向网信部门报告（PIPL 第 57 条），含事件概要、影响范围、处置措施、补救方案；
  - 个人：及时告知受影响用户"发生了什么 / 可能危害 / 已采取 / 用户自护建议"，不得隐瞒。
- **记录**：泄露事件与处置全过程入事件档案与审计（§22.3），供监管核查。
- **演练**：纳入 Game day（§24.11），验证通报链路时效。

### 24.5 坏更新 / 坏配置全网止血（kill switch）（P5）

§9.4 有回滚机制、§23.5 有配置中心，但缺**"全网紧急止血"决策通道与权限**。

- **紧急止血通道（kill switch）**：
  - **Agent 二进制**：配置中心（§23.5）下发"冻结自动更新 + 回滚至上一稳定版"指令，Agent 启动自检（§23.2）失败即进入受限安全模式（本机 Agent 安全模型见 §23.2），仅保留手动操作、暂停自动化投递。
  - **远程配置**：配置中心支持"一键熔断"——将限流阈值、匹配权重、采集频率回退到上一已知良好快照（§23.5 本地缓存兜底）。
  - **投递开关**：全局或单平台投递急停（与 §24.3 误投止血共用）。
- **决策权限**：kill switch 仅限 **SEV1 事故指挥（IC，§24.1）+ 技术负责人双授权**触发；触发动作入审计（§22.3），事后复盘（§24.6）。
- **恢复**：止血后须小流量灰度验证（§9.4）方可全量放开。

### 24.6 事故指标与复盘（MTTR / MTTD / 错误预算 / postmortem）（P6）

- **核心指标**：
  - MTTD（平均发现时长）、MTTR（平均恢复时长），按 SEV 分档设定目标（SEV1 MTTR ≤ 1h、SEV2 ≤ 4h、SEV3 ≤ 1 工作日）；
  - 事故数 / 复发率 / 自动化止血率。
- **错误预算（Error Budget）**：以可用性目标（§18.1）为基线，月度错误预算 = (1 − 目标可用性) × 时长；超出预算则冻结非必要变更、强化变更评审。
- **复盘机制**：SEV1/SEV2 强制 **blameless postmortem**（对事不对人），产出"时间线 + 根因 + 改进项 + 责任人 + 期限"，改进项入 backlog 跟踪，避免"同样的事故犯两次"。
- 注意：§23.4 的"复盘"仅针对 DR 演练，本 §24.6 覆盖**一般生产事故**。

### 24.7 状态页与事故透明沟通（P7）

- **外部状态页**：独立状态页（status.example.com），展示核心依赖（后端 / LLM / 推送 / 支付）实时状态；无依赖第三方 SaaS 也可用静态页。
- **应用内横幅**：事故期 App 内顶部横幅统一播报（区别于 §7.3 的"AI 服务维护中"单一 LLM 横幅），含影响范围与预计恢复。
- **定时播报**：SEV1/SEV2 每 30 分钟在事故群 + 状态页更新进展，直至恢复。
- **对外口径**：统一由 IC / 公关口径发布，技术细节不外泄；用户告知模板用于误投（§24.3）、泄露（§24.4）。

### 24.8 责任边界三维细化（P8）

§17.7 仅言"账号风险用户自担"，过粗。补偿与告知政策须按成因区分：

| 成因 | 责任归属 | 告知义务 | 补偿政策 |
|------|---------|---------|---------|
| **产品自身 bug 导致**（误投 / 多扣 / 坏更新） | 平台 | 主动告知（§24.3 / §24.7） | 担责：延长会员 / 退款 / 协助向平台说明 |
| **用户操作导致**（误设策略 / 误确认） | 用户 | 引导自查，不强告知 | 不补偿，提供自助撤销（§12） |
| **平台行为导致**（封禁 / 限流 / 改版） | 第三方 | 告知现状 + 规避建议 | 不担责，协助申诉（§17.7） |

- 边界判定以操作审计（§22.3）+ 配置版本（§23.3）+ 通知日志（§6.4）为证据链。

### 24.9 第三方依赖中断统一升级（P9）

各依赖已有降级（LLM 宕 §7.3、推送宕 §6.4、支付宕 §22.2），但缺**统一 outage 分级与对外口径**。

- **统一分级**：依赖中断纳入 SEV 体系（§24.1）——影响核心功能即 SEV1/SEV2。
- **对外统一口径**：通过状态页（§24.7）+ 应用内横幅统一播报，不逐个依赖各自发声，避免用户困惑。
- **降级联动**：依赖恢复后自动解除降级（§7.3 的 AI 降级、§6.4 的推送降级、§22.2 的支付降级均有回切逻辑）。

### 24.10 故障域隔离与依赖拓扑（P10）

- **依赖拓扑图**（HLD 必含，§15）：标注后端 API / LLM / 推送网关 / 支付 / 本机 Agent / 招聘平台适配器的依赖关系与故障传播路径。
- **Blast Radius 分级**：
  - 后端宕 → 本机 Agent 纯本地降级（§23.4），不卡死；
  - 单平台适配器失效 → 隔离该平台，不影响其他平台（§15.5 实例隔离）；
  - 单用户 Agent 异常 → 不影响其他用户（天然隔离）。
- **故障域清单**：明确哪些组件共享、哪些独立，便于事故时快速判定影响面与止血范围。

### 24.11 Game day / 事件响应演练（P11）

区别于 §23.4 的"基础设施 DR 演练"（练的是系统切换），Game day 练的是**人的响应流程**。

- **频率**：SEV1 关键剧本每季度至少 1 次；新 Runbook 上线后 1 个月内首练。
- **形式**：桌面推演（不触真实平台）+ 必要时可控注入（如推一个测试坏配置验证 kill switch §24.5）。
- **覆盖剧本**：误投超量（§24.3）、密钥泄露（§24.4）、坏更新 kill switch（§24.5）、支付多扣（§22.2）。
- **产出**：验证 Oncall 升级（§24.1）、Runbook 可用性（§24.2）、通报时效（§24.4/§24.7），复盘入 §24.6。

## 25. 新手激活与产品细节补全

本章补齐上一轮评审梳理、且用户确认需落地的产品细节缺口（G1/G3/G4/G8/G10/G11/G12）。未成年人保护（PIPL 第 31 条）与发票税务细节经用户确认不涉及，已列入 §19「已排除」。

### 25.1 账号连接引导流（Connect Flow，G1）

§13 仅一句"引导登录各平台并授权 Cookie"，但本机 Agent 产品的首次接入是**激活最大摩擦点**，必须独立设计。完整流程：

1. **唤起登录**：Agent 启动后弹出平台选择 → 对所选平台调用其登录页（在受控浏览器上下文内打开，非系统浏览器，避免凭据外泄）。
2. **安全抓取回写**：登录成功后 Agent 抓取会话 Cookie，经本地信封加密（§20.5）写入本机密钥库；**不上云、不展示明文**（呼应 §8.2 / §15）。
3. **常驻授权请求（仅 PC Agent）**：首次引导明确请求"开机自启动 + 后台常驻"权限，并说明这是投递执行的前提（**仅适用于 PC 端 Agent**；移动端为壳，不请求常驻，仅开启推送通知用于唤醒与状态提醒，职责边界见 §31.1）。
4. **预期管理（关键）**：引导页用醒目文案告知——**"投递在您本机执行，PC 离线 / Agent 未运行期间投递暂停"**（与 §15 执行模型、§21.3 灾备一致），避免用户误以为"装了就全自动"。
5. **连接健康检查**：连接成功后做一次轻量握手（读用户昵称/头像），失败则给出"Cookie 失效 / 风控拦截"分因指引，不静默卡死。
6. **多平台串联**：支持一次引导连多个首期平台（§6.4 计划状态），每平台独立成功/失败状态，单平台失败不阻断其他。

> 接入引导的文案与流程图应在 §13 新手体验中引用本节，确保"装 → 连 → 首投"一气呵成。

### 25.2 高级版"多简历版本"落地（G3）

§12 定价表高级版明确写"多简历版本"，但 §20.1 的 Resume 实体与模块 1 此前按单版本设计，需补齐：

- **实体扩展**：`Resume` 由单文档改为 `ResumeVersion[]`，每个版本含 `version_id / name / target_role / created_at / is_default`。
- **创建与切换**：支持从模板克隆、差异编辑；可在"简历管理"页设默认版本。
- **按平台 / 岗位分配**：`AdapterConfig`（§20.1）增加 `preferred_resume_version` 字段，可针对某平台或某岗位类型绑定特定版本（如国企岗用"稳重型"、互联网岗用"极简型"）。
- **权益边界**：免费版 / 专业版单版本；高级版允许多版本 + 平台级绑定。**定价承诺与设计在此对齐**，评审不再有"承诺落空"疑问。
- **投递时取用**：投递任务生成阶段按 `AdapterConfig` 选定的版本取简历原文，记入 `Application.resume_version_id` 便于追溯（§20.2）。

### 25.3 简历导入解析质量与边界（G4）

简历是投递原料，解析失败直接影响投递，属高频事故源，需定义质量边界：

- **支持格式**：PDF / DOCX / TXT；图片简历（扫描件）走 OCR 降级，OCR 不可用时提示用户上传可编辑文本版。
- **乱版式容错**：表格型 / 多栏型简历采用布局解析 + 规则兜底，缺失字段标记为"待补"，不臆造。
- **解析失败兜底**：解析置信度低于阈值时，引导用户**手工补全关键字段**（姓名 / 联系方式 / 工作年限 / 技能），不阻断使用；解析结果可预览编辑。
- **质量 SLA（目标）**：结构化字段填充率 ≥ 95%、关键信息（联系方式 / 教育 / 工作）准确率 ≥ 98%；该 SLA 需 v0.9 灰度实测回填。
- **成本计入**：解析（尤其 OCR / 多模态）token 或调用成本计入 §16.4 单位经济，避免漏算。

### 25.4 退款 / 试用 / 退订政策（G8）

§22.2 解决了"支付掉单补偿"，但商业侧的用户退出政策此前缺失：

- **免费试用**：专业版 / 高级版提供 7 天试用，试用期内未达套餐日投递上限的 50% 可随时退。
- **不满意退款**：付费后 7 天内、且自动投递完成量 < 10 份（因产品问题导致），支持无理由退款；超量使用按天折算。
- **取消续费**：订阅页提供"关闭自动续费"入口，到期前 3 天推送提醒（复用 §6.4 通知）；到期后权益收缩至免费版，用户数据保留（§8.2 期限）。
- **降级处理**：高级版降专业版，多简历版本超出的版本冻结（可重新激活），不删除。
- **与对账衔接**：退款经 §22.2 对账通道执行，记录 `Refund` 状态机，避免掉单 / 重复退。

### 25.5 本机 Agent 本地存储膨胀与清理（G10）

§22.5 只约束运行时资源（CPU / 内存 / 带宽），不含磁盘生命周期：

- **存储分类与上限**：岗位缓存（≤ 500MB，TTL 7 天自动淘汰）、投递 / 面试记录（按 §8.2 保留 24 个月，满 36 个月删）、运行日志（≤ 200MB 环形缓冲，30 天）、临时解析文件（任务完成后即清）。
- **自动清理**：Agent 启动时与每日空闲时段执行清理；磁盘占用超阈值（如 1GB）触发主动回收并通知用户（§6.4）。
- **用户手动清理**：设置页提供"清理缓存 / 清理日志"按钮；**Cookie 不在清理范围内**（§8.2，需重新连接）。

### 25.6 数据携带权主动入口（PIPL 第 45 条，G11）

§23.11 是"停服导出"，但用户**随时**导出个人数据的主动入口缺失：

- **入口**：设置 → "我的数据" 提供一键导出，复用 §23.11 定义的 JSON + CSV + zip schema。
- **范围**：简历（含多版本）、投递记录、面试记录、配置；**不含 Cookie / 密钥**（§20.5，不离开本机）。
- **频率限制**：同账号 ≤ 1 次 / 24h，防滥用；导出包本地加密、可设访问口令。
- **与删除权衔接**：同页提供"注销账号并删除全部数据"入口（§8.3）。

### 25.7 用户协议关键条款清单（G12）

§17.4 提隐私政策展示，但协议必须明示的条款此前未列，建议协议含：

- **自动投递风险告知**：账号被平台限制的风险由用户自担（呼应 §17.4 免责）。
- **禁止账号共享 / 转售**：同一账号不得多人共用或用于经营代投，违者封号（与 §12 / §17.7 一致）。
- **AI 建议 disclaimer**：AI 匹配 / 面试评估 / 话术建议**不替代专业判断**，用户需自行核实（呼应 §17.4 伦理）。
- **数据使用授权**：简历经脱敏后用于 LLM 匹配（§8.4），用户可关闭 AI 降级为规则模式。
- **免责边界**：因平台政策变动、网络、用户自身操作导致的投递失败，平台不承担责任（与 §24.8 责任三维一致）。

## 26. AI 产品细节补全

本章补齐 AI 能力侧的工程化与可信细节（G5/G6/G7/G13），避免"AI 功能看起来有、实则缺质量保障"。

### 26.1 Prompt 版本管理与回归评测（G5）

§7.5 定义了匹配度模型，但 prompt 自身的工程化缺失：

- **版本化**：所有面向用户的 prompt（匹配、面试题生成、评估报告、话术）入库版本管理，记录 `prompt_version / author / changelog / 生效时间`。
- **回归评测**（eval harness）：维护 golden set（标注好的"岗位—简历—应得匹配度"样本对），每次 prompt 变更跑回归，匹配度 κ 与错投率不得劣于上一版本（阈值见 §7.5）。
- **发布门禁**：回归不达标禁止发布；可与 §23.12 A/B 实验结合做小流量验证。
- **可观测**：线上 prompt 版本号随 `Application` 记录，便于问题追溯（§20.2 / §22.3 审计）。

### 26.2 面试评估报告 rubric 透明性与可申诉（G6）

模块 6 生成评估报告，但评什么、怎么评、能否质疑需透明：

- **公开 rubric**：评估维度（表达清晰度 / 技术准确度 / 结构化 / 岗位匹配度）与权重在报告内可见，不黑盒。
- **打分依据**：每条评分附关键引用（哪句回答触发该分），提升可解释性（呼应 §7.5 可解释性要求）。
- **可申诉 / 重测**：用户可对单题申请"换角度重问"或标记"评估偏差"，反馈进入评测样本库（§26.1 golden set）持续校准。
- **伦理边界**：评估报告为练习辅助，不构成任何录用结论（呼应 §17.4）。

### 26.3 语音 ASR 供应商与降级（G7）

模块 5/6 的语音练习依赖 ASR，但供应商与降级未定：

- **供应商**：默认接入国内合规 ASR（如讯飞 / 火山引擎），音频在本机采集、仅必要片段上传转写，敏感内容不留存。
- **成本**：ASR 调用成本计入 §16.4 单位经济（按练习分钟数估算）。
- **降级**：ASR 不可用或用户关闭麦克风时，自动降级为**文本输入模式**（§6.2 模块 5 / 6 已提"切文本"一笔，此处明确为默认降级路径），不阻断练习。

### 26.4 LLM 输出内容安全 / 价值观对齐（G13）

面试模拟产品，建议质量即安全，需内容安全层：

- **过滤规则**：输出经内容安全审核，拦截政治敏感、违法、歧视、骚扰类内容；面试话术不鼓励造假 / 夸大（呼应 §17.4 伦理）。
- **价值观对齐（可测口径）**：面试题与反馈不输出歧视性（性别 / 年龄 / 地域）表述；以 §26.1 golden set 中"歧视性表述抽检命中率 = 0"为验收标准；"中立 / 专业 / 鼓励性"作为设计取向而非硬指标（主观不可度量，不纳入验收）。
- **审核失败处理**：触发审核的内容不展示，提示"内容不可用，请换种问法"，并记审计（§22.3）。
- **与 LLM 委托处理衔接**：内容安全在 §8.4 的脱敏 / 授权框架内执行。

## 27. 增长、可观测性与多端细节

本章补齐增长闭环与多端细节（G16/G17/G18/G19），并收口此前分析中的剩余项。

### 27.1 多设备同账号 Agent 任务调度冲突（G16）

§23.10 解决"配置冲突"，但用户 2 台电脑都装 Agent 时**投递任务重复**是新问题：

- **任务锁**：投递任务以 `idempotency_key`（用户×平台×岗位×日期，§6.2）为唯一键，服务端协调；同一 key 仅允许一个 Agent 认领执行。
- **主从选举**：同账号多 Agent 在线时，由后端按"最后心跳 + 设备权重"选主，非主 Agent 仅做状态同步不抢任务。
- **冲突兜底**：若两 Agent 同时认领（脑裂），以 `idempotency_key` 幂等保障不重复投递（§6.2 / §24.3）。

### 27.2 向量库选型与相似度检索成本 / 延迟（G17）

§16.4 / §20 提 embedding 引用，但选型未定：

- **选型**：v1.0 采用**本地向量存储**（随 Agent 或后端 SQLite + 向量扩展），避免简历向量上云（PIPL，§8.4）；跨用户语义检索量小，无需独立向量服务。
- **检索延迟预算**：岗位—简历匹配检索 ≤ 500ms（单用户规模），计入 §18.3 性能目标。
- **成本**：embedding 调用成本计入 §16.4；本地检索零边际成本。
- **更新**：简历 / 岗位变更触发增量重算，避免全量（§21.1 采集节奏一致）。

### 27.3 限流提示可解释性（G18）

用户看到"今日已达上限"时需分清原因，否则误以为是 bug：

- **文案区分**：套餐日上限（如免费版 30 份）→ 提示"今日免费额度已用完，升级专业版解锁 100 份/天（§12）"；平台侧 70% 安全线（§6.2）→ 提示"平台今日投递上限已近，明日可继续"。
- **进度可视化**：投递页展示"今日已投 X / 上限 Y（套餐）"，并标注平台侧余量。
- **边界处理**：免费版请求投 >3 平台时明确拦截并引导升级（§12 权益）。

### 27.4 激活 / 留存 / 付费转化漏斗埋点（G19）

§10.2 有行为埋点，但增长漏斗覆盖需补全：

- **激活漏斗**：安装 Agent → 连接首个平台（§25.1）→ 完成首次投递，三步转化率单独追踪，定位激活流失点。
- **留存 cohort**：按周 / 月看 DAU 留存（与 §18.2 DAU 口径一致），区分免费 / 付费。
- **付费转化**：试用激活 → 付费转化 → 续费，漏斗对接 §16.6 LTV / CAC。
- **归因**：结合 §23.12 A/B 实验，区分功能改动与运营活动对漏斗的影响。

## 28. 生产事故预防补全（N4 / N6 / N7 + 发布门禁）

> 本章聚焦"不出现生产事故"：把 §21.2 已有的 LLM 配额 / 防滥用一句话描述，深化为**运行时护栏**；并新增"发布变更门禁 + 异常检测"的预防闭环，与 §24 的事故响应形成"事前防、事后救"双层。法律合规三块（PIPL 第 24 条自动化决策、DSAR 全流程、安全威胁模型与漏洞管理）按用户决策延后，见 §19。

### 28.1 LLM 运行时成本护栏（深化 §21.2「LLM 配额」）

LLM 是主要可变成本（§16），单用户 bug 或恶意调用即可把成本打爆，属财务型生产事故。§21.2 仅设"每日 token 预算上限 + 超限降级"，需补运行时双闸：

- **实时双闸**：单用户设「实时调用速率 + 日预算」双限制；单用户 LLM 调用 > 阈值次/分钟触发临时限流（QPS 级熔断），不止依赖日上限的事后降级。
- **预算告警**：日预算消耗达 70% / 90% 分别触发内部告警（运营 / Oncall，呼应 §24.1），达 100% 自动降级规则匹配并通知用户（呼应 §21.2）。
- **防循环 / 防薅**：单次会话（如一场面试模拟）设最大 LLM 调用轮次上限，超出截断并提示；识别"同一输入反复重试"模式并限流，防 Agent 死循环烧钱。
- **全局成本看板**：实时总 token 消耗 / 金额，较昨日同时段突增（如 +300%）自动告警（呼应 §18.4 可观测 / §24.6 事故指标）。

### 28.2 反滥用与风控（深化 §21.2「防滥用」）

§21.2 仅对"1 分钟数百次匹配"做拦截。需补账号共享、黑产、以及最关键的**投递速率熔断（防失控）**：

- **账号共享 / 多设备异常**：同账号在 > N 台设备短时高频操作、或设备指纹 / 登录地突变，触发二次验证或临时冻结（呼应 §27.1 多设备调度）。
- **黑产 / 刷量信号**：机器人式固定间隔调用、Cookie 批量异常、海量匹配请求，接入风控评分；高危直接拦截 + 人工复核。
- **投递速率熔断（防失控）**：本机 Agent 对某平台连续投递失败 / 平台返回风控时，**自动暂停该平台投递并进入冷却**，而非无限重试导致用户账号被封（呼应 §17.7 封禁处置 / §24.3 误投止血）。
- **平台反爬升级自我保护**：平台风控策略变更导致大面积失败时，Agent 自动全局降速 + 暂停新投递，等待适配器更新（呼应 §21.1 反爬耦合 / §17）。

### 28.3 诈骗 / 虚假岗位预警（降低客诉 / 品牌事故，邻接 N7）

自动投递若批量命中诈骗 / 虚假岗，会引发集中客诉与品牌事故。属用户安全，但直接影响运营稳定性，故纳入预防：

- **投递前风险标注**：识别收费岗（要求交费）、虚假 / 高薪异常岗、疑似诈骗岗（薪资与要求明显背离、要求私下转账等特征），对岗位打风险标签。
- **高风险拦截 + 确认**：高风险岗位默认不自动投递，需用户二次确认 / 显式授权；标注来源与理由，用户可申诉。
- **批量联动止血**：若同一来源被批量识别为诈骗岗，触发 §24.3 的批量撤回 / 标记流程，避免事故扩大。

### 28.4 发布变更门禁与异常检测闭环（预防先于响应）

§24 是"发生后怎么救"，本节补"怎么让它不发生"：

- **发布门禁**：任何涉及投递逻辑 / 限流 / 配置中心（§23.5）的变更，须过灰度门禁（§9.4）+ 自动化回归（§26.1 eval harness）+ 配置校验；未过门禁禁止进 prod。kill switch（§24.5）是兜底，本条是"门"。
- **业务异常检测**：对投递量突增/突降、错误率、成本（§28.1）、Cookie 失效率、平台封禁率 设**动态基线告警**（非仅静态阈值），异常自动升 SEV（呼应 §24.1 分级）。
- **预防—响应闭环**：本节"检测 / 熔断 / 门禁"为事前预防，§24 为事后响应，二者通过 统一告警 → Oncall（§24.1）→ Runbook（§24.2）衔接，确保"不发生"优先、"发生了快止血"兜底。

## 29. 本机 Agent 事故预防专项（A–F）

> 本章补 §28 未覆盖的"本地守护进程特有"事故向量。§23/§24/§28 已兜住云端韧性、事故响应与成本/风控预防，本节聚焦**跑在用户机器上的 Agent 自身失控、凭证失效、更新失败、本地溯源、睡眠调度**等用户侧事故面。设计哲学统一为 §29.6"不确定就停"。

### 29.1 Agent 看门狗与强制终止（防"变砖"，A）

§22.5 有资源限流、§23.2 有安全模型，但缺"限流失效 / 进程 hang 死 / 自愈失败"的兜底：

- **看门狗存活自检**：Agent 内置心跳 + 关键线程健康检查，超时无响应自动重启子模块或整体自愈。
- **资源限流失效兜底**：若 §22.5 的资源上限被突破且持续（CPU 持续超阈值 / 内存泄漏），看门狗强制降级或终止该实例，不让其拖垮用户机器。
- **用户一键强杀**：系统托盘 / 设置提供"立即终止 Agent"入口，进程须以普通权限可被用户随时结束（不得设防杀机制）；强杀后可一键重启。
- **启动环境校验**：Agent 启动做 OS 版本 / 依赖 / 磁盘空间自检，不达标则拒绝运行并提示，而非带病运行。

### 29.2 凭证失效与重试风暴防护（B）

Cookie 过期 / 被平台踢线时，拿失效会话猛刷会加速封号。需明确闭环：

- **失效检测**：每次请求前校验 Cookie / 会话有效性（过期、被踢线、风控挑战），命中即判定失效。
- **立即停 + 引导重登**：失效后**立即停止对该平台的所有重试与投递**，推送"需重新登录"提示（复用 §25.1 连接健康检查），不在失效会话上继续请求。
- **防重试风暴**：对连续 401/403/风控响应设退避上限（指数退避 + 最大重试次数），超次转"待人工"状态，避免猛刷加速封号（呼应 §17.7 / §28.2 熔断）。
- **批量失效保护**：同一平台大面积会话失效时，全局暂停该平台并告警，等待用户重登或适配器确认。

### 29.3 Agent 自更新失败回滚（C）

推新版本到用户机器，若新 Agent 起不来，自动投递会静默停摆：

- **自更新机制**：Agent 二进制更新走"下载 → 校验签名 → 保留上一版本 → 切换"，始终留一个可用旧版。
- **启动失败自动回滚**：新版本启动自检（§29.1）失败自动切回上一版本并上报，用户无感；连续失败则停留旧版并提示。
- **错峰更新窗口**：更新推送避开用户高频使用时段、分批灰度（呼应 §9.4 / §23.5），避免同一时刻大面积更新失败。
- **更新不丢任务**：更新过程中本地已排队任务由恢复后版本继续执行，不丢任务（呼应 §20.2 Application `queued` 状态）。

### 29.4 本机侧操作留痕与防篡改（forensic，D）

§22.3 是服务端审计，但 Agent 在用户机器上"实际投了什么、何时"需本地可追溯：

- **本地动作日志**：Agent 关键动作（每次投递尝试/成功/失败、配置变更、重登）写入本地 append-only 日志，含时间戳 + 平台 + jobId + 结果。
- **防篡改**：日志文件只读 + 校验和（或轻量签名），防止进程异常或误改导致记录失真；与 §22.3 服务端审计互为补充（服务端看信令，本机看执行）。
- **事故溯源**：误投 / 过量 / 封禁排查时，本地日志可还原"实际投了什么、何时、用哪个会话"，直接支撑 §24.3 / §24.6 复盘。
- **隐私约束**：本地日志不含明文 Cookie / 密钥（呼应 §20.5），仅记录动作元数据。

### 29.5 睡眠 / 唤醒调度补偿（E）

笔记本合盖 / 睡眠时定时投递会错过：

- **错过检测**：Agent 检测到因系统睡眠 / 合盖 / 关机导致的定时任务未执行，记录错过的调度窗口。
- **唤醒补投**：唤醒后进入补投窗口，对错过且仍在有效期内的投递任务重新排队执行（与 §20.2 `queued` 状态衔接）。
- **去重**：补投前按 `idempotency_key`（§6.2 / §27.1）去重，避免睡眠期间重复投递。
- **上限保护**：补投任务计入当日限额（§12 / §21.2），不因补投突破日投递上限；超量则顺延至次日。

### 29.6 "不确定就停"保守默认原则（F）

- **核心原则**：Agent 在任意不确定场景（平台行为异常、凭证状态不明、配置冲突、适配器降级）下，**默认暂停并提示用户，而非盲目重试或继续自动操作**。
- **统一哲学**：本条串联 §28.2 投递速率熔断、§29.2 凭证失效停手、§23.4 后端宕机本地降级，作为所有自动化决策的安全兜底。
- **用户可覆盖**：保守暂停后允许用户显式授权"仍要继续"（如高风险岗位 §28.3），但默认姿态是停。

## 30. 生产事故最小化专项（机制级兜底，Q1–Q12）

> 本章不修描述、只补机制——解决 §23/§24/§27/§28/§29 已写但"姿态/兜底不到位"的事故面。目标是把生产事故压到最小：把"默认放行 / 兼容保活 / 本地时钟 / 双授权卡死"等隐性风险，改成显式的安全姿态。HLD 架构对齐（C1/C2）属于独立跨文档事项，不在本章范围。

### 30.1 配置中心改为 fail-closed（修正 §23.5）

§23.5 写"后端不可达时用**最后已知配置**"，这是 **fail-open** 姿态，与 §29.6"不确定就停"自相矛盾：一旦配置缺失/损坏/被中间人篡改（限流阈值或熔断开关被改），Agent 会按最松配置猛跑，可能驱动误投或加速封号。

- **fail-closed 默认**：本地配置校验失败 / 缺失 / 签名不符时，**默认套用最严限流（套餐下限）+ 暂停自动投递**，而非沿用旧值或放行。
- **校验先于执行**：每次读取配置先验签名 + schema + 阈值合理性（如限流值不得为负、熔断开关不得整体关闭），异常即拒绝并告警（呼应 §23.5 安全）。
- **恢复路径**：仅当后端可达且下发配置通过校验，才恢复自动投递；不可达期间保持暂停并提示"网络恢复后自动继续"，不静默放行。

### 30.2 安全最低版本 minimum_supported_version（修正 §23.1）

§23.1 承诺"最近 2 个主版本向后兼容"，但**未定义安全下线**。若某旧版 Agent 被发现重试风暴/误投 bug，该兼容承诺会让它保活数月、无法远程禁用其自动投递。

- **最低支持版本**：后端下发 `minimum_supported_version`；低于该版本的 Agent，**后端拒绝其自动投递信令**（仅允许手动 / 查看），强制走安全更新。
- **安全更新通道**：命中安全下线时，Agent 弹窗"该版本存在安全风险，请更新后继续自动投递"，并优先推送 §29.3 的签名更新包。
- **与兼容承诺不冲突**：正常落后（≤2 主版本）仍走 §23.1 功能裁剪降级；仅当**安全红线**触发才硬禁用自动投递，二者分层。

### 30.3 日限额与定时以服务端 UTC+8 为准（修正 §29.5 / §21.2）

§29.5 的"当日限额""补投"、§21.2 的日预算都依赖**本机时钟**。本地时钟漂移 / 跨时区会导致：本地计数漏算 → 实际突破平台 70% 安全线被封；或定时在平台非活跃时段猛投触发风控。

- **权威时钟**：日限额计数、日预算结算、定时调度窗口**以服务端 UTC+8 为准**；本机时钟仅作参考展示。
- **偏差熔断**：本机时间与服务端偏差 > 阈值（如 5 分钟）时，暂停自动投递并提示"系统时间异常，请校正后继续"，避免错算。
- **时区无关性**：与 §17"不翻墙"不冲突——时区是用户本地设置，不影响服务端按 UTC+8 计日；海外用户仍按服务器日界结算，策略面板明示。

### 30.4 后端宕机时多设备锁不失效（修正 §23.4 ↔ §27.1 冲突）

§27.1 的任务锁/主从选举"**由后端协调**"，但 §23.4 又说后端宕机时 Agent 纯本地降级。宕机窗口内两台电脑的 Agent 都以为自己是主，可能双投——只靠 `idempotency_key` 在后端恢复后兜底，宕机期内平台侧可能已重复受理。

- **本地离线锁**：后端不可达时，同账号多 Agent 走**本地选举 + 单设备自动投递**模式——仅"最后心跳设备"允许自动投递，其余设备本地标记"后端不可达，已暂停自动投递"。
- **恢复后收敛**：后端恢复后，按 §27.1 重新协调主从，离线期锁元数据上送对账，发现冲突以 `idempotency_key` 幂等去重（呼应 §6.2 / §24.3）。
- **不靠事后兜底**：把"不双投"从"恢复后去重"前移到"宕机期间就限制单设备"，降低事故窗口。

### 30.5 break-glass 自动止血（修正 §24.5 双授权真空）

§24.5 要求 kill switch 须 **SEV1 IC + 技术负责人双授权** 触发。深夜/周末无人响应时，双授权卡住，全网误投的止血被延迟。

- **预设自动触发（break-glass）**：定义可量化的自动止血条件（如全网误投率 > X%、同版本崩溃率 > Y%、成本突增 > Z 倍，见 §28.1/§28.4 动态基线），命中即**自动 kill + 全网暂停自动投递**，无需等人工授权。
- **事后补授权 + 审计**：自动触发动作入审计（§22.3），并立即拉起 Oncall（§24.1）事后确认与复盘（§24.6），对事不对人。
- **与双授权并存**：人工双授权仍保留用于"需人判断"的止血；break-glass 专治"无人响应"真空，二者互补而非替代。

### 30.6 强杀级联回收 + OS 级看门狗（深化 §29.1）

§29.1 的"一键强杀"若没级联回收 Playwright 浏览器子进程，会泄漏进程持续占 CPU/带宽；且缺 OS 级独立看门狗保证 Agent 不彻底失联。

- **级联回收**：强杀时先向 Agent 发 SIGTERM、回收其派生的 Playwright / 浏览器子进程树、释放端口与临时文件，确认全进程退出再返回 UI。
- **OS 级看门狗**：注册系统级守护（macOS launchd / Windows 任务计划 / Linux systemd），监控 Agent 主进程存活；Agent 彻底失联（非用户主动退出）时由 OS 级进程拉起或至少上报状态，避免"静默死亡"。
- **与防杀不冲突**：用户主动退出/强杀始终优先且无障碍（§29.1），OS 看门狗仅兜底"异常崩溃未被用户控制"的场景。

### 30.7 回滚也失败兜底 + 更新密钥吊销（深化 §29.3）

§29.3 回滚到上一版，但若**同一批构建的旧版也有同样启动 bug**，会陷入"新版起不来→回旧版也起不来"死循环，静默停摆且无提示；更新密钥泄露也无吊销列表。

- **回滚失败兜底**：连续回滚 N 次仍启动失败时，进入 §23.2 受限安全模式 + 显式报错弹窗（"自动更新异常，请手动重装/联系支持"），并将错误上报，绝不让"静默停摆"发生。
- **更新密钥 CRL**：更新签名密钥设撤销列表（CRL），泄露密钥立即吊销、旧构建拒绝加载（呼应 §23.2 签名校验）。
- **构建隔离**：同一发布批次的"新旧两版"须来自不同构建产物校验，避免"同源 bug 同时中招"。

### 30.8 LLM 单次输出硬上限 + 调用硬超时（深化 §28.1）

§28.1 有速率/日预算/会话轮次护栏，但没约束**单次返回长度**和 **provider 调用硬超时**——畸形 prompt 或模型异常可返回超长内容，既烧钱又撑爆上下文。

- **max_tokens 硬上限**：单次 LLM 调用设 `max_tokens` 硬上限（按场景分级：匹配 < 512、面试题 < 1024、评估报告 < 2048），超限截断并告警。
- **调用硬超时**：每次 provider 调用设总超时（如 15s）+ 重试上限（≤2 次，指数退避），超时即降级规则匹配（§7.5）或返回"服务暂不可用"，不卡死等待。
- **异常体熔断**：连续命中超时/超长/异常返回时，对该场景临时熔断（§28.2），避免单点模型抖动拖垮全链路。

### 30.9 脱敏强制拦截层（深化 §18.4 / §22.3 / §29.4）

§18.4/§22.3/§29.4 都说"敏感字段脱敏/不含明文 Cookie"，但**仅声明、无拦截层**。任一代码改动误打明文 Cookie/简历到日志，既违 PIPL 又成泄露事故（呼应 §24.4）。

- **强制拦截**：日志写入路径统一经脱敏过滤器——正则/字段级匹配 Cookie、token、身份证、手机号等，命中即**自动掩码**后再落盘，而非靠"约定不打印"。
- **PII 扫描告警**：对落盘日志定期扫描（或实时采样），发现明文 PII 立即告警 + 定位来源（呼应 §18.4 可观测 / §24.6）。
- **与本地日志兼容**：§29.4 的本地 append-only 日志同样走该过滤器，确保本机侧也不留明文（呼应 §20.5）。

### 30.10 诈骗识别误杀兜底（深化 §28.3）

§28.3 高风险默认不投，若模型误判正常岗 → 用户错失机会；批量误拦 → 投递沉默、用户以为坏了。

- **误判率口径**：诈骗识别模型设误判率上限（如正常岗被拦 ≤ 0.5%）并纳入 §10.3 指标，超阈值回退规则+人工抽检。
- **用户强制覆盖**：被拦截岗位用户可"仍要投递"（显式授权，呼应 §29.6 用户可覆盖），并采集"用户反馈=误杀"样本反哺模型。
- **静默≠停摆**：拦截后明确提示"X 个岗位因风险被拦截，点此查看/放行"，不让用户疑惑为何投递量变少。

### 30.11 凭证"真失效" vs "风控挑战"判别（深化 §29.2）

§29.2 把 401/403/风控都当失效停手。但平台常是临时滑块/短信验证（非真失效）——全停→用户以为坏了；硬闯→封号。缺"待人工验证"状态闭环。

- **状态分流**：请求失败分三类——①真失效（明确过期/账号注销）立即停 + 引导重登；②风控挑战（滑块/短信/人脸）转"待人工验证"暂停该平台、提示用户去 App 完成验证；③网络/限流临时失败按 §28.2 退避重试。
- **待验证闭环**："待人工验证"状态在用户完成验证或手动跳过前不自动重试，验证通过后恢复（不计入 §29.2 退避上限，避免误伤）。
- **不混淆**：三类状态在 §29.4 本地日志与用户界面区分展示，用户清楚"是坏了还是等验证"。

### 30.12 前台高负载资源感知（深化 §22.5）

§22.5 说"用户前台高负载时主动让出"，但**怎么感知前台高负载**标准模糊（如用户正在视频面试/开会），易拖垮体验或被滥用为停摆借口。

- **可量化感知**：以 CPU 占用率、前台活跃进程（视频会议/录屏/全屏应用）、电源状态（笔记本仅电池且低电量）、用户"勿扰/会议"模式 为输入，判定"用户高负载"。
- **主动让出**：命中高负载时自动降速或暂停非紧急采集/投递，结束后自动恢复；紧急项（用户显式触发的投递）不阻断。
- **可预期**：感知逻辑与阈值对用户透明（设置页可见"低负载时更积极"开关），不暗中静默停摆。

## 31. 系统工程补充专项（可行性校验，R1–R12）

> 本章补齐 §23–§30 尚未正式设计的系统机制（非描述问题、非姿态兜底）。每条方案均附**可行性判断**：标注所采用的成熟工程做法、工作量量级与主要风险，确保不是愿景而是可落地设计。HLD 架构对齐（C1/C2）属独立跨文档事项，不在本章范围。

### 31.1 移动端职责澄清：壳 + 推送唤醒，非执行体（修正 §25.1 隐含矛盾）

§15 / §6.1 已定"移动端只确认/发起、执行在 PC Agent"，但 §25.1 的"开机自启动 + 后台常驻"未显式限定 PC，易被误读为移动端也要常驻守护进程——而 iOS / Android 系统**禁止后台常驻**，做不到。

- **显式界定**：PC Agent 是唯一执行体（可常驻，靠 launchd / 任务计划）；移动端仅为"壳"——查看状态、确认 / 发起投递、接收推送唤醒，**不能在后台自动执行投递或看门狗**。
- **已修 §25.1**：第 3 步"常驻授权请求"已限定为"仅 PC Agent"，移动端引导改为"开启推送通知（用于唤醒与状态提醒）"，不请求常驻。
- **预期管理**：移动端文案补充"实际投递由您电脑上的 Agent 执行"，避免用户以为手机也能自动投（呼应 §25.1 第 4 步）。

- **可行性**：纯文档澄清 + 移动端引导文案调整，**零技术风险**，与 §15 / §21.3 完全一致；工作量极小（小时级）。

### 31.2 通用离线数据同步与冲突解决（offline-first 同步引擎）

§27.1 / §23.10 只解决"投递任务锁"与"配置冲突（LWW）"。但**简历多版本、收藏岗位、面试记录、设置**等用户数据，离线改后与服务端双向冲突未设计，会导致覆盖 / 丢失。

- **同步模型**：每条用户数据带 `version + updated_at + device_id`；采用**字段级 LWW + 版本向量**解决多数冲突；简历多版本设计为**不可变快照、仅"哪个为 active"可变**，active 切换冲突用 LWW + 用户合并提示（呼应 §23.10 用户可感知）。
- **同步通道**：本地变更入"待同步队列"（复用 §23.6 离线队列机制），恢复后 delta 同步；服务端为权威（§23.10）。
- **冲突可视化**：合并时弹"X 在手机改了、Y 在电脑改了，请选择 / 已保留两者"，不静默覆盖。

- **可行性**：字段级 LWW + 版本向量是笔记 / 协作类 App 的成熟做法（如 Obsidian Sync、Notion）；**工作量中等**（需写同步层 + 冲突 UI）。**风险与降级**：首版可仅"设置 / 收藏"走双向同步，简历编辑强制单设备编辑以避免冲突面，降低首版复杂度。

### 31.3 第三方依赖专项韧性（支付 / 推送 / 招聘适配器）

§28.1 只管 LLM。支付商 outage、APNs / FCM 推送失败、招聘平台 DOM / 接口变更导致**适配器失效**的检测—降级—热修没专门写。

- **支付**：除 §22.2 对账外，加"支付状态双源校验"——下单后轮询 + 接收 webhook，超时未确认转"待确认"、**不重复扣**；主支付商故障按 §22.2 降级手动支付。
- **推送**：APNs / FCM 有 delivery 反馈与 feedback 服务；加"推送健康监控"——按 §6.4 渠道矩阵统计各通道送达率，跌破阈值切备用通道（站内信 / 邮件，§6.4 已有）。
- **招聘适配器**：适配器健康分 = DOM 解析成功率；失败率超阈值（如 > 20% 持续 5min）自动告警 + 该平台降级为"暂停自动投递待适配"；**选择器 / 规则走配置中心（§23.5）热更**，无需发版即可修 XPath / CSS 选择器。

- **可行性**：支付双源校验、推送送达率监控均为成熟方案；**关键可行点**是"适配器热修走配置"——把平台 DOM 选择器外置为配置而非硬编码，是防反爬升级事故的核心手段。**工作量中等**（需前期抽象层）。风险：配置化适配器需设计抽象层，首版可先硬编码 + 事后配置化。

### 31.4 API 层安全与鉴权模型

§21.2 是"产品功能限流"，但后端 API 自身的**鉴权（令牌颁发 / 刷新 / 吊销、并发会话）、API 滥用防护、WAF** 未写。本机 Agent 持长期凭证调 API，凭证泄露 = 全域风险。

- **鉴权**：本机 Agent 与移动端用 **OAuth2 客户端凭证 + 短期 access token（如 15min）+ 可轮换 refresh token**；每设备一会话，单账号并发设备数受限（呼应 §27.1）。
- **吊销**：refresh token 支持服务端吊销列表（类比 §30.7 CRL），泄露即废；access token 短命降低泄露窗口。
- **网关**：API 网关统一限流（补充 §21.2）、WAF、bot 防护；Agent ↔ 服务端可选 mTLS 加强。

- **可行性**：OAuth2 / JWT + API 网关是标准企业实践，**工作量中等、风险低**。注意：长期凭证（Cookie）仍本地（§20.5），API token 仅用于信令 / 同步，分层清晰，不混淆两类凭证。

### 31.5 SLI / SLO 体系与合成监控

§18.1 有可用性目标、§24.6 有错误预算，但**无正式 SLI / SLO**，也无法度量"本机 Agent 实际可用性"。

- **SLI 定义**：API p99 延迟、API 可用性（成功 / 总）、错误率、队列积压深度、Agent 心跳存活率。
- **SLO**：分组件定目标（如 API 可用性 99.9%、匹配评分 p99 ≤ 5s）；错误预算接 §24.6。
- **合成监控**：服务端定时经推送通道（§6.4）向 Agent 发探活 probe，期望 X 内 ack；超时未响应标记 Agent 降级——这是度量"用户侧实际可用"的唯一可行手段（§23.6 心跳是被动，需主动探测）。

- **可行性**：SLI / SLO 是 SRE 标准（Google SRE Book），合成监控复用现有推送通道即可实现，**工作量小–中**。风险：probe 频率需控，避免打扰用户 / 耗电（呼应 §30.12 资源感知），建议低频（如 15–30min）+ 仅活跃用户。

### 31.6 存储扩展与归档 / 冷热分离

§20 数据模型、§23.3 迁移、§8.2 24 个月保留有，但**分库分表、读写分离、归档、备份恢复演练**未写。

- **起步**：单主 + 只读副本（读写分离），热数据在主库。
- **扩展**：用户规模上来后按 `user_id` 哈希分片；`Application` / `DailyReport` 等时序表按时间分区。
- **归档**：> 24 月数据按 §8.2 匿名化后转入对象存储冷层（如 COS / S3 Glacier），降成本；在线仅保留索引。
- **演练**：每季度**备份恢复演练**（非仅 §23.4 的 DR 切换），实测 RTO / RPO，纳入复盘。

- **可行性**：读写分离 + 时间分区是数据库标配；分片按 `user_id` 是常规水平扩展；冷归档接对象存储成熟。**工作量分阶段**（首版只需副本 + 分区）。风险：分片是后期大改，需在 §20 schema 预留分片键（`user_id`），否则后期迁移成本高。

### 31.7 密钥轮换与泄露全量吊销工程

§14 定义 KMS / 信封加密，§20.5 / §21.1 提 KMS 存储，但**轮换周期、泄露吊销时效、HSM / 版本化**未写（§30.7 仅覆盖 Agent 二进制签名密钥 CRL，非后端 Secrets 层）。

- **轮换**：KMS 主密钥自动轮换（如 90 天），数据密钥（信封加密，§20.5）版本化——旧版可解密历史数据、新版加密新数据。
- **吊销**：泄露时吊销该数据密钥版本 → 对该版加密数据重加密至新版本；服务端 Secrets（LLM Key / 推送证书，§21.1）即时轮换并废止旧值。
- **HSM**：高敏感主密钥可选 HSM 托管（合规加分，呼应 §14）。

- **可行性**：KMS 自动轮换 + 信封密钥版本化是云厂商标准能力（AWS KMS / 阿里云 KMS），**工作量小、风险低**，前提是 §20.5 已定的信封加密落地。

### 31.8 测试体系（桌面端 E2E + 环境保真）

§26.1 LLM eval、§23.7 混沌有，但**桌面 Agent E2E、staging 能否真连平台、回滚信号**未写。

- **桌面 E2E**：用 Playwright（本产品已用于平台自动化，§23.2）驱动 Agent 自身 UI，跑"连接 → 匹配 → 投递 → 撤回"全链路冒烟。
- **平台 Mock**：建**录制 / 回放层**——录制真实平台 DOM 为 fixtures，E2E 与适配器回归对 mock 跑，避免依赖真实平台（且规避 ToS 风险，§17）；适配器改动先过"选择器回归"比对 fixtures。
- **回滚信号**：接 §31.12 guardrail，CI 含 E2E 门禁（呼应 §23.7 发布门禁）。

- **可行性**：Playwright 驱动自家 UI + 录制回放 mock 是可行且主流的桌面 E2E 方案；**关键价值**是"不依赖真实平台也能回归适配器"。**工作量中等**（需建 mock 层）。风险：mock 与真实 DOM 漂移需持续维护，建议适配器改动必须同步更新对应 fixture。

### 31.9 容量自动扩缩容与成本联动

§18.2 是静态容量模型（DAU3000 峰值 35–60 QPS），**自动扩缩容、预测性扩容**未写。

- **弹性**：无状态服务上 K8s + HPA（按 CPU + 自定义 QPS 指标扩缩）；有状态（DB）纵向扩容 + 只读副本（§31.6）。
- **预测性扩容**：秋招峰值（9–11 月）用**定时扩容预案**（scheduled scaling）提前扩容，避免瞬时打满。
- **成本护栏**：扩缩上限接 §16 单位经济预算，超预算预警（呼应 §28.1 全局成本看板）。

- **可行性**：HPA + 定时扩容是 K8s 标准能力，**工作量小–中**。风险：突发（如某平台爆职位）仍需 HPA 反应时间，靠 §23.9 缓存 + §21.2 限流兜底；预测扩容依赖历史数据（上线后回填 §18.2 / §16.4）。

### 31.10 分析数据隐私（防重识别）

§8.4 脱敏、§30.9 日志脱敏有，但**聚合统计如何防重识别（k-匿名 / 差分隐私）**未写，尤其"投递成功率 / 岗位分布"太细可被反推个人。

- **Cell Suppression**：聚合报表中小组（如某城市 < k = 50 人）直接抑制不展示，防反推个人。
- **差分隐私（可选）**：对小计数值加 Laplace / Gaussian 噪声（ε 可控），允许统计趋势又不暴露个体。
- **默认不产细粒度 per-user 统计**；确需时走上述两法。

- **可行性**：cell suppression 零成本、最稳；差分隐私有成熟库（如 Google DP、OpenDP），**工作量小**。风险：噪声影响精度，仅用于对外 / 分析报表，不影响用户个体数据。

### 31.11 数据删除可验证性（被遗忘权工程化）

§8.3 / §25.6 有注销入口，但"删除完成"如何向用户 / 监管**证明**、审计例外如何保留且不被篡改未写。

- **删除证明**：注销 / 单条删除完成后，系统生成**签名删除凭证**（含删除记录 ID 哈希 + 时间戳 + 服务端签名），用户可下载作为"已删除"证明。
- **审计保留**：操作审计（§22.3）保留最小元数据（谁 / 何时 / 删了什么类型），不含被删内容明文，满足 PIPL 第 57 条留存例外且不泄露。
- **级联**：删除触发 §20 关联数据（投递记录 / 面试记录）级联清理 + 本地 Agent 清除（§25.5 / §29.4 日志不含明文）。

- **可行性**：签名删除凭证是标准合规实践（类似 GDPR erasure confirmation），**工作量小**，前提是 §22.3 审计已结构化。

### 31.12 灰度发布回滚决策信号（guardrail）

§9.4 灰度、§24.5 kill switch 有，但"什么指标异常该**自动回滚**"阈值未写。

- **自动回滚 guardrail**：错误率 > 2% 持续 5min、p99 延迟 > 基线 2 倍、误投率 > 0.1%、成本突增 > 3 倍（接 §28.1）、Agent 崩溃率 > 1% → 自动回滚至上一已知良好版（§23.5 / §24.5），无需等人工。
- **与 break-glass 协同**（§30.5）：guardrail 触发自动回滚，事后复盘（§24.6）。
- **信号来源**：§31.5 的 SLI + §28.4 动态基线。

## 32. 商业论证与可持续性（v4.1 新增）

> 本章补全「产品商业成立性 + 可持续性」论证。所有市场数字与转化假设均为**产品假设**，须在 v0.9 灰度期以真实数据回填（呼应 §2.1 假设驱动声明）。法律合规细节（PIPL 自动化决策等）按用户决策延后，不在本章展开，见 §19 待定。

### 32.1 产品定位重申与风险定级
本产品为**求职者辅助工具**，核心能力三步：① 收集信息（简历 / 意向 / 账号本地化）② **半自动化投递**（候选岗位经 AI 匹配后，**由用户显式确认 / 发起**执行，非全自动无人值守脚本）③ 通知服务（投递结果 / 面试邀约 / 风险预警推送）。
- **「半自动」口径界定**：用户确认的是「策略 + 投递队列」（批量确认），Agent 在已确认队列范围内自动执行；睡眠唤醒补投（§29.5）、后端不可达时的单设备自动投递（§23.4）均属「已确认队列的延迟执行」，不构成新的发起动作，与 §5.2 / §15 本机执行模型一致。
- **能力闭环**：三步之外含**面试模拟闭环**（§7 / §26），提供「投递 → 备战 → 复盘」完整求职助手价值，亦为差异化卖点（见 §32.3）。
- **合规姿态**：执行以用户主动确认为前提，平台容忍度显著高于全自动模拟器；§17 合规应急中「账号封禁」是按最严情景设定的极端预案，对本产品实际主要表现为**单平台风控挑战 / 误伤**（已由 §17.5 降级引导 + §28.2 投递速率熔断 + §29.2 凭证失效保护覆盖）。
- **与「全自动脚本」的核心区别**：本机 Agent + 用户确认 + Cookie 不上云（§C），不构成对平台服务的替代性滥用，故不存在「单一平台封杀即全域归零」的灭顶风险。

### 32.2 市场论证（TAM / SAM / SOM，假设驱动）
| 层级 | 定义 | 测算框架（首年假设，待 v0.9 回填） |
|------|------|------|
| **TAM** 总市场 | 中国年度活跃求职人群 | 城镇新增就业 + 存量流动求职 + 应届生 ≈ 数千万 / 年（引用国家统计局 / 教育部公开口径，取保守值） |
| **SAM** 可服务市场 | 使用数字化求职工具、有付费意愿的细分 | TAM × 数字化求职渗透率(~60%) × 付费意愿(~15–25%) |
| **SOM** 可获取市场 | 首年靠获客预算可触达并转化的用户 | SAM × 首年渠道触达率（按获客预算 ÷ 预计 CAC 反推） |

- 所有数字标注「假设」，v0.9 灰度以真实投放 + 问卷校准（§32.5）。

### 32.3 护城河 / 差异化结论（导出自 §4 竞品）
- **差异化锚点**：本机隐私 Agent（数据不上云，§C.5）+ 半自动可控（用户确认，非盲投）+ 面试模拟闭环（§7 / §26）——竞品多为「纯信息聚合」或「违规全自动」，两不占。
- **招聘平台不自建的理由**：平台定位为双边市场，不做「帮用户绕过 / 自动化投递」的第三方工具（合规与中立性冲突），且不碰用户隐私托管。
- **大厂复制成本**：垂类招聘投递 know-how + 合规姿态 + 本机架构（非服务端爬虫），复制需重构数据归属模型，非简单功能拷贝。

### 32.4 平台规则适配与降级预案（非灭顶）
- 单平台规则 / 反爬变化 → 适配器配置热修（§31.3）+ 投递速率熔断（§28.2），不阻断其他平台。
- 多平台同时受限（极端）→ 维持「简历管理 + 面试备战」价值（§17.5 手动投递引导模式），产品核心价值未归零。
- **结论**：本产品可持续性风险主要来自**长期获客成本与留存**（见 §33），而非平台封堵。

### 32.5 用户研究证据汇总（汇总自 §2.1）
- 探索期：少量用户访谈 n<10（§2.1 来源标注），结论用于假设生成，证据等级**低**。
- 验证期：v0.9 灰度计划招募 ≥30 名真实求职者采集对照（§2.1）；待补：结构化问卷（付费意愿 / 痛点强度）、用户旅程地图(CJM)、分群焦点小组（§33.3）。
- **立项提示**：当前证据不足以独立支撑「强付费意愿」结论，须在 v0.9 前补问卷数据。

## 34. 资深 PM 工程补充：上线前具体因素（评审遗留补全）

> 本章汇总前序评审中尚未落地的**具体工程 / 运营 / 增长因素**。均为「上线前必须有人拍板」的硬因子，非愿景；凡含量化目标者标注「待 v0.9 实测回填」。

### 34.1 桌面 Agent 被安全软件误报（分发信任 blocker，High）
- **问题**：本机 Agent 会驱动浏览器自动操作（Playwright，§15/§29），极易被 Windows Defender / 360 / 火绒 等判为木马 / PUA / 自动化风险，导致安装被拦、用户信任崩塌。这是桌面自动化工具头号分发事故。
- **方案**：① 代码签名采用 **EV 代码签名证书**（比普通签名更易过 SmartScreen）；② 上线前跑各主流安全软件云查杀加白流程，留存加白工单号；③ 误报响应 SOP：用户报误报 → 1 工作日内提交样本复核 + 官网「为何被报毒」说明页。
- **可行性**：成熟做法，工作量小–中；唯一风险是部分国内软杀无正式加白通道，需以「官网数字签名 + 说明」兜底（呼应 §29.3 自更新签名 / §31.1 本机执行）。
- **关联**：§29.3 自更新签名、§31.1 移动端职责澄清（仅 PC 执行体）。

### 34.2 LLM 主备切换与可用性 failover（High）
- **问题**：§28.1 只管**成本护栏**（速率 / 预算 / 超时），但主 LLM 供应商（境内合规大模型，§8.4/§9.1）**不可用时的可用性 failover 完全没设计**——一旦主供应商宕机 / 限流，匹配度、面试题、评估全线降级或停摆。
- **方案**：① 配置 **1 主 + 1–2 备用**境内供应商，主不可达（超时 / 5xx 比例超阈值）自动切备；② 切换时 prompt 适配层做供应商差异归一（模板参数化，§26.1）；③ 切备后跑 **golden set 质量回归**（§26.1）确认评分一致性，偏差超 κ 容差则降级为规则匹配（§7.3）。
- **可行性**：成熟，工作量中；核心是 prompt 模板参数化 + 回归门禁（§26.1 已有）。
- **关联**：§28.1 成本护栏（补可用性维度）、§7.3 回退、§26.1 回归门禁。
- **附**：招聘平台自身在金三银四 / 秋招高峰期会**反向限制**调用频率（非我方负载），Agent 应识别平台侧 429 / 限流并主动避让退避（与 §28.2 投递速率熔断 / §29.2 失效保护同源），避免被平台误判滥用。

### 34.3 功耗与电量硬预算（Medium-High，桌面守护进程头号投诉）
- **问题**：§22.5 约束 CPU / 内存 / 带宽，§29.5 把「仅电池且低电量」作为资源感知输入，但**没有明确的功耗预算目标值**——桌面守护进程最易被骂「耗电 / 让电脑发烫 / 阻止睡眠」。
- **方案**：设硬预算——空闲态 CPU < [X]%、内存常驻 < [Y] MB、磁盘 I/O 限流；**绝不阻止系统睡眠**（投递任务改为唤醒后补投，§29.5）；仅电池且电量 < [Z]% 时暂停非紧急采集。目标值待 v0.9 实测回填。
- **可行性**：成熟，工作量小；关键是把「不得阻止睡眠」作为硬约束写进 §22.5。
- **关联**：§22.5 资源限流、§29.5 睡眠唤醒补偿、§29.1 看门狗。

### 34.4 浏览器 / OS 兼容支持矩阵与终止支持策略（Medium）
- **问题**：§29.5 仅做「启动 OS 版本自检」，但**没定义支持范围**——用户机器 Chrome/Edge 版本碎片化、Win10/11 与 macOS 各版本、Playwright 支持上限，哪些是「受支持」、哪些「不保证」？无策略则支持成本失控、兼容 bug 无边界。
- **方案**：发布**兼容矩阵**——支持 Windows 10 22H2+ / Windows 11 / macOS 12+；浏览器内核 Chromium 110+（Chrome/Edge 同核）；Playwright 绑定版本随 Agent 发布。对 EOL 系统提前 [N] 月公告并停止新功能（保留旧版冷修）。
- **可行性**：成熟，工作量小；属产品支持范围声明，无技术风险。
- **关联**：§29.5 启动自检、§31.1 本机执行。

### 34.5 用户端自助帮助中心与错误可解释（Medium，直接影响客诉成本）
- **问题**：§17.6 有**内部**运营知识库，§25 有新手激活，但**用户侧自助排障 / 错误码解释 / FAQ / 报错文案**没专门设计。Agent 报错（登录失效、平台改版、网络异常）若只弹「失败」，用户只能找客服，推高 §23.13 工单量。
- **方案**：① in-app 错误码 → 帮助中心文章映射；② 高频场景（Cookie 失效、平台验证码、网络异常）一键排障指引；③ 空状态 / 失败态文案说人话 + 下一步动作。
- **可行性**：成熟，工作量中（内容产出为主）；与 §25 激活、§23.13 工单 SLA 衔接。
- **关联**：§17.6 运营知识库（内部）、§25 激活、§23.13 客服工单。

### 34.6 流失预警与挽回闭环（Medium，增长模型补完）
- **问题**：§33.2 有留存分层（D1/D7/D30/D90）但**只有度量、没有干预**——识别到用户要流失却不动作，留存模型价值减半。
- **方案**：定义 at-risk 信号（如 D7 未激活 / 连续 [N] 天 0 投递 / 通知全关）→ 触发干预（召回推送 / 限时权益 / 新功能提示）；干预本身计入北极星（§33.1）与 §28.4 异常检测，避免骚扰。
- **可行性**：成熟，工作量中；依赖 §6.4 通知 + §33.2 分层数据。
- **关联**：§33.1 北极星、§33.2 留存模型、§6.4 通知。

### 34.7 AI 产出内容版权与归属声明（Medium，产品 / 用户预期澄清）
- **问题**：简历优化建议、面试反馈由 AI 生成（§7/§26），但**产出内容权属、用户能否商用、用户上传简历的授权范围**从未声明。法律三块虽延后（§19），但「版权归属与使用授权」是**用户侧产品预期**，不声明易生纠纷。
- **方案**：在用户协议中明确——AI 产出内容**仅供参考、版权归用户、平台不主张权利**；用户上传简历 / 素材授予「为提供服务所必需的处理授权」，不转授权第三方。
- **可行性**：纯文案 + 法务一句话确认，工作量极小；不触碰延后的 PIPL 三块（那是合规控制，非版权声明）。
- **关联**：§26.4 AI 可信、§17.4 伦理免责。

### 34.8 LLM 供应商 ToS 与合理使用边界（Low-Medium）
- **问题**：用 LLM 做简历优化 / 面试模拟，个别供应商 ToS 可能限制「代写 / 自动化决策」类用途（§8.4 只管数据合规，未管供应商 ToS）。
- **方案**：上线前逐一核对主备供应商 ToS 的「允许用途」条款；若受限，切到允许的生产力用途供应商（§34.2 备用链直接复用）；产品定位「辅助建议、非代写」（§26.4/§17.4）本就降低风险。
- **可行性**：工作量小（合规核对）；风险低。
- **关联**：§8.4 AI 数据处理、§34.2 备用链、§26.4。

### 34.9 客服人力与成本模型（Low-Medium，单位经济闭合）
- **问题**：§23.13 有工单系统 + SLA，§16 有单位经济，但**客服人力成本 / 单工单成本 / 自助分流目标**没进模型——这会直接吃掉 §16 的毛利。
- **方案**：首年设人效目标（如 1 客服 / [M] 活跃付费用户）、自助分流率 ≥ [K]%（靠 §34.5 帮助中心）、单工单成本计入 LTV 扣减（§16.6）。目标值待 v0.9 实测。
- **可行性**：成熟，工作量小；属财务建模，无技术风险。

### 35.1 开源许可证合规（🔴 High，分发 blocker）

- **问题**：本机 Agent 重度依赖开源组件——Playwright（驱动浏览器，MIT）、捆绑 Chromium（BSD 类）、Python 运行时（PSF License）、requests / pyinstaller 等打包依赖。若任一依赖为 **GPL / AGPL 等 copyleft** 并随产品再分发，可能触发「源码公开义务」与产品闭源许可冲突；同时各组件 EULA / 专利条款需确认与商业分发兼容。§23.2 提到 SBOM，但**未覆盖许可证合规**。
- **方案**：① 上线前跑 **SBOM + 许可证扫描**（如 pip-licenses / FOSSA / ScanCode）产出许可证清单；② 建立**白名单**——仅允许 MIT / BSD / Apache-2.0 / PSF 等 permissive 许可，LGPL 隔离使用，**禁止 AGPL 与未声明许可证组件**进入分发包；③ 对 pyinstaller 打包的 Chromium / Playwright 单独确认分发授权（经 Playwright 官方渠道获取，保留 NOTICE）；④ 法务在 v0.9 前出具「开源合规确认」结论。
- **可行性**：成熟，工作量小（扫描工具现成）；主要风险是 pyinstaller 打包 Chromium 的体积与许可携带，需提前验证（呼应 §23.2 SBOM / §34.1 分发信任）。
- **关联**：§23.2 本机 Agent 安全模型（SBOM）、§34.1 安全软件误报（同属分发信任）。

### 35.2 正式 Beta 用户测试与 v0.9 验证计划（🔴 High）

- **问题**：§2.1 / §3 把全部量化基线标为「假设、待 v0.9 灰度验证」，但 PRD 始终**没有一份正式的 Beta 测试与验证执行计划**——谁来测、测多久、准入 / 退出标准、关键假设如何逐一回填、问题如何分级闭环（§11 是验收标准，不等于测试执行计划）。
- **方案**：定义 **v0.9 Beta 计划**：① 招募 [N] 名代表性用户（覆盖应届 / 社招、Win / macOS、首期 5 平台）；② 准入标准（完成 §25 激活、至少 [M] 天使用）、退出标准（关键假设回填达标——HR 查看率 / 面试邀请率取得首样数据、错投率 ≤10% 验证、误报加白完成、崩溃率 < [X]%）；③ 假设回填清单（映射 §2.1 / §3 / §16 的每一条假设 → 验证方式 → 负责人）；④ 缺陷分级与 triage SLA（接 §23.13 工单）；⑤ 数据隐私与知情同意（Beta 数据用于优化，见 §8.3 / §8.4）。
- **可行性**：成熟（标准 Beta 管理），工作量中（招募 + 执行）；属发布治理，无技术风险。
- **关联**：§2.1 假设声明、§3 需求目标、§11 验收标准、§25 激活、§23.13 工单。

### 35.3 VoC 闭环（🟡 Medium，产品迭代飞轮）

- **问题**：§23.13 有客服工单系统、§34.5 有用户侧帮助中心，但**「用户之声」从收集 → 归并 → 排优先级 → 落入路线图 → 闭环告知**的全链路没设计——分散在工单 / 应用商店评论 / 社群的反馈若不结构化，无法驱动 §33.4 冷启动与 §25 激活迭代。
- **方案**：① 统一 VoC 入口（应用内反馈、工单、应用商店评论、社群）汇聚到单一看板；② 按主题聚类 + 严重度标记，周会过会排期；③ 已采纳 / 已修复的反馈**闭环告知**提交者（接 §6.4 通知）；④ 季度输出「VoC 洞察报告」反哺 §4 竞品与 §32 商业论证。
- **可行性**：成熟，工作量小–中（看板 + 流程）；依赖 §23.13 工单与 §6.4 通知。
- **关联**：§23.13 客服工单、§34.5 帮助中心、§6.4 通知、§4 竞品、§32 商业论证。

### 35.4 分析数据管道与 BI（🟡 Medium，指标落地的数据底座）

- **问题**：§10.2 定义了埋点、§10.1 / §33 定义了指标与北极星，但**「埋点事件 → 采集 → 数仓 → 看板 / BI」的数据管道完全没设计**——指标没有可观测的底座，§10 / §33 的口径只能靠人工统计，无法实时驱动 §34.6 流失干预与 §28.4 异常检测。
- **方案**：① 埋点事件经 SDK → 消息队列 → 数仓（分层 ODS → DWD → DWS），指标在 DWS 层物化；② BI 看板覆盖 §10.1 核心指标 + §33.2 留存分层 + §16.6 单位经济；③ 隐私合规（§31.10 抑制 / 差分隐私 + §8.3 最小化）嵌入管道；④ 管道自身有 SLA 与数据质量监控（接 §18.4 可观测性）。
- **可行性**：成熟（标准数据栈），工作量中；重点是 §10.2 事件 schema 先行冻结（呼应 §20 数据模型）。
- **关联**：§10 数据与指标、§33 北极星、§31.10 分析隐私、§18.4 可观测性、§16.6 单位经济。

### 35.5 定价弹性实验（🟡 Medium，定价不是一次性决策）

- **问题**：§12 给出了固定档位定价（免费 / 专业 / 高级），但**没有「价格是否最优」的验证机制**——转化率、付费意愿、价格敏感度（PSM / Van Westendorp）从未测过，§16.6 的「付费转化 ≥35%」健康线是假设。
- **方案**：① 用 §23.12 A/B 实验框架跑**定价弹性实验**（不同档位价、年付折扣、首月优惠）；② 结合定性（付费意愿访谈，接 §35.3 VoC）与定量（PSM 模型）确定价格带；③ 实验设护栏（§31.12 自动回滚 guardrail）防收入异常；④ 结论回填 §12 / §16。
- **可行性**：成熟，工作量中；依赖 §23.12 实验框架与 §35.4 数据管道。
- **关联**：§12 定价模式、§16.6 LTV / CAC、§23.12 A/B 实验、§31.12 回滚 guardrail、§35.4 数据管道。

### 35.6 危机公关预案（🟡 Medium，品牌级而非技术级）

- **问题**：§24 是**技术**事件响应（误投 / 坏更新 / 泄露），但**品牌 / 舆情级危机**——如大规模被安全软件误报（§34.1）、媒体负面报道、数据泄露传闻、竞品抹黑——没有对外沟通预案，易从小事故升级为信任崩塌。§24.7 状态页是透明沟通，但非对外 PR。
- **方案**：① 定义危机分级（与 §24.1 SEV 对应但面向公众）与**唯一发言人**机制；② 预置 **holding statement 模板**（误报、数据传闻、服务中断各一套）；③ 明确对外渠道（官网公告 / 状态页 §24.7 / 社媒）与审批链；④ 与 §24 技术响应联动：技术定级 → 对外口径同步；⑤ 不承诺未验证信息（呼应 §17.4 告知与免责）。
- **可行性**：成熟，工作量小（模板 + 流程）；属品牌治理，无技术风险。
- **关联**：§24 事件响应（技术侧）、§24.7 状态页、§34.1 安全软件误报、§17.4 告知与免责。

### 35.7 代码质量门禁（🟢 Low-Medium，测试策略的强制化）

- **问题**：§31.8 定义了测试体系（桌面 E2E + 平台 Mock 录制回放），但**没有「质量门禁」——CI 里强制卡点**（lint 不通过不让合、单测 / 集成覆盖率阈值、安全扫描、E2E 冒烟必过）。「有测试」≠「合入门禁」，质量靠自觉会泄漏。
- **方案**：① CI 流水线设分级门禁——静态检查（lint / 类型）+ 单测覆盖率 ≥ [阈值]% + 集成 / E2E 冒烟（§31.8）+ 依赖与密钥扫描；② 主干保护（trunk 强制 review + 门禁通过方可合入）；③ 门禁失败阻断发布（接 §24.5 kill switch / §28.4 发布门禁）；④ 覆盖率 / 门禁指标纳入 §18.4 可观测性看板。
- **可行性**：成熟（CI 标准实践），工作量小；风险是初期阈值过严误伤，首版宽松后收紧。
- **关联**：§31.8 测试体系、§28.4 发布门禁、§24.5 kill switch、§18.4 可观测性。

### 35.8 竞品监测飞轮（🟢 Low-Medium，差异化护城河维护）

- **问题**：§4 是**静态**竞品调研（一次性），但招聘辅助工具赛道变化快（新玩家、平台政策变动、AI 能力迭代），**没有持续监测机制**——§32.3 的护城河结论会随时间失效。
- **方案**：① 建立**季度竞品雷达**：功能 parity 矩阵、定价变动、用户口碑、平台政策（如反爬升级 §21.1 / §28.2 自我保护）跟踪；② 差异化监控（我们 vs 竞品在「本机执行 / 半自动确认 / 隐私」上的相对优势是否仍在，导出自 §32.3）；③ 输出季度简报反哺 §32 商业论证与路线图。
- **可行性**：成熟，工作量小（情报收集）；属战略运营。
- **关联**：§4 竞品调研、§32.3 护城河差异化、§21.1 平台采集策略、§28.2 反滥用与风控。
- **关联**：§16.6 单位经济、§23.13 客服 SLA、§34.5 帮助中心。
