# ADR-016 CI/CD 与测试策略

## 状态

已采纳

## 背景

产品包含 Java 与 Python 两套服务，需要自动化构建、测试与部署流程，确保代码质量与交付效率。独立开发者时间有限，需要一套"零手工、高可靠"的 CI/CD 流水线，同时以合理的测试分层保障代码质量。

## 决策

采用 **GitHub Actions + Docker 镜像构建 + 三环境（dev/staging/prod）部署** 的 CI/CD 体系，测试分三层：

| 测试层 | 工具 | 目标 |
|--------|------|------|
| 单元测试 | JUnit 5（Java）/ pytest（Python） | 覆盖全部业务逻辑，行覆盖率 ≥ 80% |
| 集成测试 | Testcontainers（Java）/ Docker Compose（Python） | 验证数据库、Redis、MQ 等外部组件交互 |
| E2E 测试 | Playwright | 覆盖核心用户流程（注册→完善简历→投递→查看状态） |

CI 触发条件：向 main 分支或 release/* 分支推送代码时自动运行全部测试。

## 理由

1. **免费额度充足**：GitHub Actions 免费版每月 2000 分钟，对本项目当前规模足够使用。
2. **Docker 保证环境一致**：Java 与 Python 服务均构建为 Docker 镜像，确保 dev/staging/prod 环境一致，消除"在我的机器上能跑"问题。
3. **三层测试覆盖全场景**：单元测试快速反馈代码逻辑问题，集成测试验证外部依赖交互，E2E 测试保障核心流程无故障。
4. **GitHub 生态集成**：GitHub Actions 与 GitHub 仓库原生集成，PR 自动触发测试，代码审查与 CI 状态联动。

## 候选方案

1. **Jenkins 自建 CI/CD**：优点是灵活可控；缺点是维护成本高，需要独立部署、配置插件、持续维护，对独立开发者不划算。
2. **自行搭建 GitLab Runner**：优点是自托管、无时长限制；缺点是同样需要维护服务器，且 GitLab CI 配置复杂度高于 GitHub Actions。

## 竞品参考

（该决策主要基于开源免费工具链的成本考量；多数中小型 SaaS 团队使用 GitHub Actions 或 GitLab CI 搭配 Docker 构建部署，三层测试策略为行业通用实践。）

## 对开发的影响

1. 所有测试必须能独立运行，不依赖外部真实服务（使用 Testcontainers 或 Mock），禁止测试依赖 staging 环境数据。
2. GitHub Actions 的 workflow 配置文件中，Java 与 Python 服务分别配置独立的构建与测试 Job。
3. 每次提交到 main 分支自动构建 Docker 镜像并推送至阿里云镜像仓库，staging 环境自动拉取最新镜像部署。
4. E2E 测试在 staging 环境执行，通过 Playwright 模拟用户操作，失败时自动截图并上传至 Actions Artifacts。
5. 生产环境部署**必须手动触发**（通过 GitHub Actions workflow_dispatch），禁止自动部署到 prod 环境。
