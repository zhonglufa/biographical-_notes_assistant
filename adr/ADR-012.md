# ADR-012 简历版本对比机制

## 状态

已采纳

## 背景

用户在使用 AI 优化简历功能时，会反复修改简历内容。每次 AI 优化后用户可能局部调整、也可能整体替换，需要能够回顾历史版本并与当前版本对比查看改动。版本管理的核心诉求是：恢复简单、对比直观、对非技术人员友好。

## 决策

采用**快照式版本管理**方案：

- 每次用户保存简历（手动保存或 AI 优化后自动保存）时，生成一份完整的 JSON 快照存入数据库快照表。
- 版本对比时，后端取出两份快照 JSON，使用**结构化 diff 算法**逐字段对比（字段级而非全文级），前端以高亮方式展示增、删、改三类差异。

## 理由

1. **快照恢复简单可靠**：每份快照为独立完整 JSON，恢复任意版本只需读取该快照写入当前表，无需复杂的增量反推操作。
2. **结构化 diff 比纯文本 diff 更准确**：简历是结构化数据（个人信息、教育经历、工作经历、项目经历等字段），逐字段对比能精确定位到"某段经历中的某条描述"的改动，而非纯文本的行级对比。
3. **用户体验好**：高亮展示增删改、支持一键回滚，非技术人员无需理解 Git 概念即可操作。
4. **存储成本可控**：JSON 快照体积小（单份约 2-5KB），即使每人 100 个版本，存储成本也极低。

## 候选方案

1. **增量存储**（仅存储每次变更的 diff patch）：优点是可以节省存储空间；缺点是恢复版本时需要逐次回放 patch，过程复杂、易出错，且回放出现错误时数据不可恢复。
2. **Git 式存储**（使用 Git 仓库存储简历 JSON）：优点是版本管理能力强；缺点是用户需要理解 Git 概念、操作门槛高，且与产品非技术用户定位冲突。

## 竞品参考

Google Docs 的版本历史提供"查看所有版本"与"恢复此版本"功能，展示方式为全文高亮；Grammarly 的改动高亮展示了逐条修改建议的接受与否。本项目参考二者，结合简历结构化数据特征，采用结构化字段级 diff 展示。

## 对开发的影响

1. 每次保存简历（包括自动保存）必须生成快照，快照与用户 ID + 简历 ID 关联，不可删除（用户主动清理除外）。
2. 结构化 diff 算法需覆盖简历全部字段类型（文本、列表、嵌套对象），确保对比无遗漏。
3. 前端高亮展示需区分三种颜色：绿色（新增）、红色（删除）、黄色（修改），并支持按字段折叠展开。
4. 版本列表按时间倒序排列，最新版本置顶，支持"恢复此版本"一键回滚操作。
5. 快照表需定期归档（如 180 天前的版本压缩存储），避免单用户版本过多影响查询性能。
