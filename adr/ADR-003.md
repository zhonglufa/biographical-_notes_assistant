# ADR-003 数据库选型

## 状态

已采纳

## 背景

产品核心数据以关系型为主（用户、简历、岗位、投递记录、订单），实体间关联紧密且有强一致性与事务需求；同时，投递任务、分布式锁、幂等控制等场景需要高性能的缓存与临时存储。需要确定主数据库与缓存组件的选型。

## 决策

采用**MySQL 8.0 主从架构（读写分离）+ Redis 7** 组合：

- **MySQL 8.0**：主库承担写入，从库承担读，承接全部业务关系数据。
- **Redis 7**：承担缓存（热点岗位、会话）、分布式锁、幂等令牌、以及轻量级消息队列辅助功能。

## 理由

1. **MySQL 支撑中小规模足够**：C 端用户规模在万人量级时，MySQL 主从读写分离可稳定支撑，运维经验普及、故障处理资料丰富。
2. **Redis 一专多能**：同时覆盖缓存、分布式锁、幂等令牌、排行榜等场景，一套组件解决多个问题，减少中间件数量。
3. **国内云厂商支持完善**：云数据库 MySQL + Redis 为国内云厂商标准产品，备份、监控、扩容开箱即用。
4. **团队技能匹配**：MySQL/Redis 是后端开发者普遍掌握的技术，降低上手成本。

## 候选方案

1. **PostgreSQL**：优点是功能更强（JSONB、全文检索、扩展丰富）；缺点是团队现有经验以 MySQL 为主，迁移成本高，国内云厂商实例成本略高。
2. **MongoDB**：优点是文档模型灵活；缺点是本项目业务以强关系型数据为主，事务支持与关系查询能力弱于 MySQL，且无实际需求支撑引入。

## 竞品参考

主流 SaaS 产品普遍采用"MySQL/PostgreSQL + Redis"的组合，多数国内招聘与简历类产品使用 MySQL 主从 + Redis 缓存，实践验证充分。

## 对开发的影响

1. 所有写操作走主库，读操作走从库，ORM 层需显式区分读写路由，禁止未加路由的模糊查询。
2. 涉及强一致的读必须强制走主库（如支付回调后的订单查询）。
3. 分布式锁与幂等令牌统一使用 Redis 实现，禁止在业务代码中自行推进多次获取。
4. 大字段（简历快照 JSON、文件元数据外链）不得存入 MySQL 主力业务表，避免拖慢主从同步。
5. 所有表必须包含 `created_at`/`updated_at` 字段并建立索引规范，为后续分库分表预留条件。
