# ADR-004 消息队列选型

## 状态

已采纳

## 背景

批量投递、AI 优化、面试录音处理等均为耗时任务，必须异步化执行；同时，投递任务存在"延迟执行"（如指定时间投递）与"失败重试/死信"（如平台风控、网络异常）诉求，需要消息队列提供延迟队列、死信路由与幂等消费能力。

## 决策

采用 **RabbitMQ** 作为消息中间件，承担任务编排、延迟队列、死信路由与消费重试能力。

## 理由

1. **Spring AMQP 原生支持**：Spring Boot 对 RabbitMQ 支持完善，与 Java 业务服务无缝集成，开发成本低。
2. **延迟队列成熟**：通过 TTL + 死信交换机即可实现延迟消息，满足投递定时执行需求，无需额外组件。
3. **运维简单**：RabbitMQ 单机即可满足当前规模，管理界面直观，Docker 一键部署，符合独立开发者运维能力。
4. **路由灵活**：交换机/绑定机制支持按队列分流（如投递队列、AI 队列、通知队列），便于任务编排。

## 候选方案

1. **Kafka**：优点是吞吐量极高、日志型存储适合大数据流；缺点是吞吐能力在本项目规模下严重过剩，无延迟队列原生支持，运维复杂度高。
2. **RocketMQ**：优点是延迟消息原生支持、功能强大；缺点是独立部署与运维成本高于 RabbitMQ，社区与云厂商支持在国内虽好但整体偏企业级，对独立开发者偏重。

## 竞品参考

（该决策主要基于团队技术栈与任务特性的工程判断，未刻意对标特定竞品；同类型 SaaS 产品普遍采用 RabbitMQ 或云厂商消息队列处理异步任务。）

## 对开发的影响

1. 所有消费者必须实现幂等消费：以业务唯一键（如投递记录 ID）在 Redis 中做消费去重。
2. 消息必须携带 `trace_id`，便于串联全链路日志。
3. 延迟任务统一使用延迟交换机（TTL + DLX）实现，禁止在业务代码中自行 sleep 或定时轮询代替。
4. 死信队列必须配置告警与人工处理通道，死信消息保留原始业务参数以便重放。
5. 消息体只放业务最小必要字段（业务 ID + 参数摘要），大对象通过 ID 回查数据库获取。
