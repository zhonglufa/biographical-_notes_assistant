# ADR-008 投递状态机

## 状态

已采纳

## 背景

投递是产品的核心业务实体，从用户发起投递到最终投递结果（offer / 拒绝 / 关闭），期间经历多个中间状态，每个状态需要对应不同的用户操作与系统动作。状态定义过粗则无法支撑精细化运营，过细则增加用户理解成本与开发复杂度，需要确定一个合理且闭环的状态流转模型。

## 决策

采用 **10 状态投递状态机**，定义如下状态与流转路径：

| 状态 | 说明 |
|------|------|
| `pending_confirm` | 等待用户确认投递 |
| `autofilling` | 系统正在自动填充表单 |
| `submitted` | 已提交投递 |
| `viewed` | 简历已被 HR 查看 |
| `contacting` | HR 已联系/沟通中 |
| `interview_invited` | 已收到面试邀约 |
| `interview_done` | 面试已完成 |
| `offer` | 已获得录用 |
| `rejected` | 已被拒绝 |
| `closed` | 用户主动关闭/放弃 |

流转方向单向推进，不可逆；`rejected` 和 `closed` 为终态。

## 理由

1. **覆盖完整生命周期**：从投递前到终态，全链路闭环，不遗漏关键状态。
2. **每个状态可触发对应动作**：如 `interview_invited` 触发面试备战，`rejected` 触发推荐相似岗位。
3. **用户可清晰感知投递进展**：10 个状态语义明确，无歧义，用户一看即懂、便于操作。
4. **为后续数据统计提供粒度**：各状态转化率（如 submitted→viewed 转化率）是产品核心指标，状态粒度足够才能支撑。

## 候选方案

1. **5 状态精简模型**（投递→面试→offer→拒绝→关闭）：优点是简单；缺点是丢失了"自动填充""查看""沟通中"等关键中间态，无法精细化运营。
2. **15 状态精细化模型**（增加"初筛通过""HR 电话面""技术面""HR 面"等子状态）：优点是细致；缺点是对用户操作要求高，用户维护成本高，且多数用户不会主动更新过度细化的状态。

## 竞品参考

Huntr 使用 Kanban 看板式状态管理，提供 6 列看板（Wishlist / Applied / Phone Screen / Interview / Offer / Rejected），本项目参考其看板状态设计但做了适当细化和扩展。

## 对开发的影响

1. 状态机逻辑必须封装在独立模块内，禁止在业务代码中直接硬编码状态数字或字符串，必须通过状态机接口转换。
2. 状态流转为单向不可逆，除 `closed` 外不允许从后续状态回退到前序状态。
3. 每个状态变更必须记录变更日志（谁、何时、从哪状态到哪状态、原因），便于审计与用户申诉。
4. 状态变更时需触发对应的事件（如通过 RabbitMQ 广播），供其他模块（通知、AI 备战、推荐）监听。
5. 前端需根据状态渲染不同的操作按钮与文案，前后端状态列表需通过 API 契约统一维护。
