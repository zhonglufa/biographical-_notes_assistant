## 图 SEQ-1 · 投递主链路时序（本机 Agent ↔ 服务端 ↔ 适配器 ↔ 平台）

### 参与者（泳道）
- **UA**：用户（本机 Agent 桌面守护）
- **AG**：本机 Agent（投递编排，本机侧）
- **SVC**：服务端 Java（投递状态机 §3.4 / 策略 / 用户权限）
- **ADP**：平台适配器（浏览器自动化，本机侧，仅适配器模块调用）
- **PF**：招聘平台（boss / liepin / zhaopin / 51job / lagou）

### 消息顺序（自上而下）
1. AG → SVC：`POST /apply/tasks`（携带策略快照 + 目标岗位）—— 策略由 §3.5 拉取，权限 A03 强制判定。
2. SVC → SVC：投递状态机 `created → submitted`（ADR-008，幂等四元组 user/platform/job/attempt 去重，R2 孤儿清扫）。
3. SVC → AG：`accepted`（RPC 信封 `ApplyTask.Deliver`，含 idempotencyKey）。
4. AG → ADP：`open(platform)` + `fill(form)` + `submit()`（浏览器自动化，**仅在本机 Agent 侧**，红线：服务端绝不持有浏览器/平台 Cookie 明文，I2）。
5. ADP → PF：提交投递（平台侧动作，平台视为用户本人操作）。
6. PF → ADP：投递结果页（成功 / 需验证码 / 限流 / 账号风控）。
7. ADP → AG：回写 `crawler.result`（B10/B11，采集触发端点）—— 失败时带 `reason`（login_expired / rate_limited / captcha）。
8. AG → SVC：`b07-task-result`（taskId + idempotencyKey + status/outcome）—— 按幂等键覆盖首次结果。
9. SVC → SVC：状态机 `submitted → succeeded|failed`；失败进 `pending_retry`（限流重试 ≤N，指数退避）。
10. SVC → MQ：`apply.status.changed`（投递状态事件，信封见 §4.6）→ 触发通知 §3.11（L1/L2）。

### 红线（HLD 强制）
- 浏览器自动化**只在本机 Agent 侧**；服务端无浏览器沙箱（旧图错绘，已废）。
- 投递行为须 fail-closed：验证码/风控挂起 → 闭环不盲目重试（§6.14.4）。
- 单平台失效（DOM 解析成功率 <20% 持续 5min）→ 自动降级该平台，不全局停摆（§31.3）。

## 图 SEQ-2 · 支付回调时序（平台支付 → 服务端 → 对账 → 权益）

### 参与者
- **PF-Pay**：支付渠道（微信/支付宝/Stripe）
- **SVC-Pay**：服务端支付模块（§25.4 / LLD-支付模块）
- **SVC-ORD**：订单状态机（五态：`created→paid→refunded|renewing|grace`）
- **SVC-USER**：用户与权限模块（C5 权益激活）
- **MQ**

### 消息顺序
1. 用户 → PF-Pay：发起支付（订单 `orderNo`）。
2. PF-Pay → SVC-Pay：`POST /payments/callback`（异步回调，含 `orderNo` / `tradeNo` / `status` / 签名）—— **验签 + 幂等**（同 `orderNo` 重复回调覆盖，R-04 资损级）。
3. SVC-Pay → SVC-ORD：状态机 `created → paid`；失败/异常 fail-closed 不放大权限。
4. SVC-Pay → SVC-Pay：异步**对账**（T+1 比对渠道流水 vs 本地订单，差异告警）。
5. SVC-ORD → MQ：`member.plan.changed`（C5：`{userId, plan, effectiveAt, orderNo}`，按 `orderNo` 去重，强一致，失败阻塞重试）。
6. MQ → SVC-USER：`member.plan.changed` → 权益矩阵实时生效（下一次调用即时生效，不主动查订单）。
7. SVC-USER → SVC-USER：权限判定 fail-closed（来源不确定按免费版，§3.1）。

### 红线
- 回调**必须验签 + 幂等**，禁止重复入账（R-04 资损级，零容忍）。
- 退款 / 续费宽限 / 退订工作流状态机闭环（§25.4），不得静默丢状态。

## 图 SEQ-3 · 通知分发时序（业务事件 → MQ → 多渠道 → 降级 → 触达统计）

### 参与者
- **PROD**：业务生产者（投递状态机 / 面试 / 适配器 / 支付）
- **MQ**：RabbitMQ（事件 `apply.status.changed` / `interview.invited` / `hr.viewed.detected` / `adapter.health.degraded` / `member.plan.changed` / `daily.report.generated`）
- **NTF**：通知推送模块（服务端 Java，§3.11）
- **CH**：渠道（APNs / FCM+厂商 / 邮件 / 微信模板 / WebSocket / 站内信）
- **DB**：通知表（触达统计回写）

### 消息顺序
1. PROD → MQ：发布业务事件（信封 §4.6，含 `dedupKey`）。
2. MQ → NTF：消费事件 → 模板渲染 + 分级（L0–L3）+ 聚合/免打扰判定（§3.11 §2/§3）。
3. NTF → CH：按渠道矩阵分发（主渠道 APNs/FCM → 失败转站内信 → L0/L1 补邮件）。
4. CH → NTF：渠道回执（送达 / 失败）；失败按降级链重试 ≤3 次（指数退避），再失败入 **DLQ**（死信）。
5. NTF → DB：触达统计回写（`sent → read/deleted`，到期 `archived`）。
6. NTF → UA：L0/L1 实时（免打扰豁免）；L2/L3 聚合/延后补推。

### 红线
- 通知通道与**系统信令通道物理隔离**（ADR-007 / I3）—— 信令不得误推用户。
- at-least-once 投递 + `dedupKey` 去重（见 通知推送 LLD §8 投递语义形式化）；投递失败不得静默丢失（DLQ 兜底）。
- 正文不含身份证/手机号；锁屏默认隐详情（§6.4）。
