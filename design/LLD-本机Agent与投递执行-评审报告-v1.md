# LLD 评审报告：本机 Agent 与投递执行模块

> 评审对象：`LLD-本机Agent与投递执行-模块设计.md` v1.0（2026-08-15）
> 评审依据：LLD 交付标准（IEEE 1016-2009 / GB-T 8567 / Amazon LLD / 中文详细设计模板共识）；上游 HLD v3.10、PRD v4.5
> 评审立场：独立复核（非作者自评），重点抓**与上游矛盾的正确性问题**、**标准未达标项**、**虚假自检项**
> 评审日期：2026-08-15

---

## 1. 评审结论（Verdict）

**有条件通过（Conditional Go）—— 结构达标，但 3 处正确性问题必须在编码前修复。**

本 LLD 的**文档形态**已达到交付级：类设计带类型化签名（§2.2）、状态机带守卫（§4）、算法带前置/后置/边界（§5）、错误码分类 + 恢复矩阵（§6）、表 DDL + 索引（§8）、可追溯性矩阵（§11）、PoC 验证门（§10）齐备，且正确承接了 HLD §6.14.8 密钥派生与反封号命门。

但评审发现 **3 处与 HLD/PRD 直接矛盾的正确性问题（F-1 / F-2 / F-3）**，若不修，编码后会出现：重复投递（数据完整性）、误触发 break-glass（可用性事故）、状态语义错乱（服务端状态误报）。这三类不是"写得不够细"，是"写错了方向"，必须闭环后才能进全量开发。

---

## 2. 评审发现（按严重度）

### 🔴 必须修复（编码前阻断）

#### F-1 幂等键模型与 HLD 四元组矛盾（数据完整性 / 重复投递风险）
- **LLD 现状**：§8.2 DDL `task` 表仅 `idempotency_key TEXT UNIQUE NOT NULL`，§7.1 校验 `idempotency_key(UUID, 唯一)`；§11 声称"task/task_event 持久化 → §4.6/§6.14.7 → §4.6 幂等"。
- **上游真相**：HLD §6.13.2（行 1047、1546）明文规定幂等键为 **`(user_id, platform, job_id, apply_date)` 四元组**，`Application` 表以此建唯一索引，"**禁止任何全局自增 id 式替代，必须显式携带四维度**"。
- **矛盾**：LLD 用单个 UUID 替代四元组，既未建模四维度，也未在 DDL 建四列复合唯一索引。
- **后果**：若服务端按四元组去重、本机按 UUID 去重，二者口径不一 → 跨端重复投递或漏去重；且 LLD 的"幂等"实际退化为"本机任务 id 唯一"，未实现 HLD 要求的跨维度去重。
- **修复**：DDL 改为 `(user_id, platform, job_id, apply_date)` 复合唯一索引；`idempotency_key` 改为由四维度派生的确定性串（或保留为冗余列）；§7.1 校验四维度必填且组合唯一。

#### F-2 心跳阈值与 HLD 不一致（可用性 / 误触发 break-glass）
- **LLD 现状**：§2.2 `heartbeat_timeout=10s`；§6.2 错误码 `AGENT-5001 WorkerHeartbeatLost 心跳超 10s`；§6.4 恢复矩阵将该码归为 **fail-closed（挂起）**。
- **上游真相**：HLD §6.14.1（行 1118）明确"worker 卡死（**无心跳 >30s 或 CPU 持续 100% >60s**）由 supervisor 强制 kill"。
- **矛盾**：LLD 把单次 10s 心跳丢失即判 `AGENT-5001` 并触发 fail-closed（挂起新任务 + 保留现场 + 报用户）。HLD 容忍 3 个心跳周期（30s）且另有 CPU 占用判据。
- **后果**：一次 GC 停顿 / 瞬时调度抖动 / 网络 IPC 毛刺即可误触发 break-glass，造成**用户侧可见的服务中断与误报警**，可用性显著劣化。
- **修复**：LLD 心跳丢失判据对齐 HLD——连续丢失 >30s（或 CPU 100% 持续 >60s）才进 fail-closed；单次/短暂丢失仅记 warning 并重试；§6.2/§6.4 同步更正。

#### F-3 验证码状态语义错挂到 `contacting`（状态语义错乱 / 服务端误报）
- **LLD 现状**：§4.1 守卫写"`autofilling→submitted` 仅当 detect_captcha()==false…否则**进入 contacting（验证码）**或挂起"；§4.3 另设 captcha_session 子状态机含 `awaiting_user`。
- **上游真相**：HLD §3.4（行 352、354-355）明确定义：`autofilling → pending_confirm`（**需人工补验证码后重投**），而 `contacting` 的语义是"**HR 主动沟通**"（`viewed→contacting`，行 354），与验证码无关。
- **矛盾**：LLD 把"验证码挂起"错误映射到 `contacting`。但 `contacting` 在 HLD 中是 HR 沟通态，会被服务端（B08 增强推送、HR 感知通道）解读为"HR 已主动联系候选人"——**把用户过验证码误报成 HR 沟通**，污染状态上报与通知逻辑。
- **后果**：服务端状态机与通知触发逻辑被错误驱动（例如误发"HR 已沟通"增强推送），且回写路径语义断裂。
- **修复**：验证码挂起应映射到 HLD 的 `pending_confirm`（带回验证码标记），或在应用 10 状态机外以 `captcha_session` 子实体独立表达（§4.3 的 `awaiting_user` 方向是对的，但应用级不应写 `contacting`）；§4.1 守卫删除"进入 contacting（验证码）"表述。

### 🟠 应修复（不阻断编码，但属设计偏差 / 标准缺口）

#### F-4 warm-up 模型与 HLD 发散（降速机制不一致）
- LLD §5.1 `account_age_days<7 → 0.3`，为**时间窗**模型；HLD §6.14.3 为"**前 N 份（⚠ 建议 5–10 份）降速至 30–50%**"的**份数**模型，且标 ⚠ 为建议值。
- 二者机制不同（按天 vs 按份），且 LLD 的 0.3/7d 未与 HLD 的 30–50%/5–10 份对齐。需二选一或在 LLD 标注"采用时间窗近似，偏离 HLD 份数模型，待 PoC P1 校准"。

#### F-5 反检测抖动规格弱于 HLD（anti-ban 真实性不足）
- LLD §5.1 `clip(gaussian(μ=5.5s,σ=1.5s), 2s, 12s)` 上限 12s；HLD §6.14.3 为"**2–8s 贝塞尔轨迹 / 随机滚动**"叠加。
- LLD 上限 12s 与 HLD 8s 不符，且**完全省略贝塞尔轨迹 / 随机滚动**这一关键拟人动作。PoC P1 实测前应补齐，否则反封号有效性存疑。

#### F-6 Worker 崩溃时孤儿浏览器进程回收未落地（崩溃恢复缺口）
- HLD §6.14.1 要求"worker 崩溃 → supervisor 强制 kill + **孤儿进程级联回收**"；LLD §2.2 `BrowserPool.release(i)` 仅正常释放路径，类设计未体现**崩溃时的孤儿 Playwright 进程回收**（含 permit/实例状态清理、携幂等键转"执行中断"由服务端清扫，呼应 HLD §3.4 孤儿清扫）。
- 后果：worker 被杀后残留浏览器进程 + 占用实例槽位 → 资源泄漏、实例池耗尽。

#### F-7 本地持久化健壮性规格缺失（与 HLD §6.14.1 脱节）
- HLD §6.14.1 要求本地 SQLite **每 30min `PRAGMA integrity_check` + 每日轻量快照 + corruption 进受限安全模式绝不静默放行**；LLD §6.2 `AGENT-5002 SQLiteCorrupt` 仅提"从最近 checkpoint 恢复"，`LocalStore` 类（§2.2）与 DDL（§8.2）**未体现完整性检查节奏、快照、受限安全模式**。
- 后果：本地损坏场景的 fail-closed 行为未在 LLD 落实，与 HLD 安全哲学脱节。

#### F-8 §8.3 对 §6.15 的呼应属误导（追溯声明不实）
- LLD §8.3 称"主键 user_id/account_id 首列（呼应 HLD §6.15 分片预留）"，但 §8.2 DDL 的 `task` 表主键为 `id`，**无 `user_id` 列**；且 HLD §6.15 的分片预留针对**服务端 `application`/`application_task` 等高增表**，本机 SQLite 为单用户本地库，本就不适用。
- 该呼应语句制造"已遵循 §6.15"的假象。修复：删除该呼应，或明确"本地单用户库 N/A，分片约束仅适用于 HLD §6.15 服务端表"。

#### F-9 IPC 通道规格空白（攻击面 / 协议未定义）
- HLD §6.14.1 规定 supervisor↔worker/gui 经 **UDS/Named Pipe（不监听网络端口）**；LLD §2.1 列了 `IpcChannel` 但**无消息帧格式、鉴权、版本协商**设计。本地 IPC 虽不暴露网络，但仍需防本机其他进程注入。属设计深度缺口。

### 🟡 低（标准合规性 / 文档诚信）

#### F-10 自检清单 §14 虚报"≥5 时序"
- §14 勾选"≥5 时序覆盖关键流程（§3.1–§3.4）"，但 §3 实际只有 **4 条**流程（3.1/3.2/3.3/3.4）。应改为"≥4"或补第 5 条（建议补：**断网补传 / 离线队列消费**独立时序，当前仅 §3.1 第 6 步一句话带过）。

#### F-11 PRD 锚点虚构（§15.x 不存在）
- §11 可追溯性矩阵写"PRD 锚点 §15.x 适配器（待补 PRD 锚点）"。PRD 实际无 §15 适配器章节；适配器契约在 **PRD §494「模块 4：平台适配器系统」/ §496「适配器接口契约」**。应更正锚点为 §494/§496。

#### F-12 关联测试用例为占位（TC-xxx 未撰写）
- §11 矩阵"关联测试用例"列填 `TC-SUP-01` 等占位 ID，尚无对应测试用例文档。可追溯性在"映射"层成立，但"→ 测试"链路未闭环。建议标注"测试用例待撰写"而非暗示已完成。

#### F-13 PoC P1 通过判据属 LLD 自定，未锚定上游
- §10 P1 判据"14 天无封号、验证码率 <20%"中的 **<20% 阈值**是 LLD 提议，HLD/PRD 未规定。应标注"提议值，需 stakeholder 签字确认"，避免被误读为既定标准。

#### F-14 退避 base/cap 未显式回声
- §5.1 `backoff = min(2^n*base, cap)+jitter` 未显式写入 HLD §6.14.3 的 `base 15min ×2ⁿ，上限 6h`。应补参数常量，避免 LLD 实现时拍脑袋。

## 3. 评审肯定（客观优点，非客套）

- **密钥派生（§5.2 / §9.3）** 精确承接 HLD §6.14.8 的 T1–T5 链路（OS 安全区持有 + 平台认证器/Argon2id 在场因子 + HKDF 合成 KEK），无偏差。
- **PoC 验证门（§10）** 把"反封号有效性 / 适配器 DOM 稳定性"前置为可达标闸门，是风险右移的正确工程实践，且判据可测。
- **错误码分类 + 异常层次 + 恢复矩阵（§6）** 与 HLD fail-closed 哲学一致，恢复策略（retry/backoff/fail-closed/break-glass）分层清晰。
- **类设计采用类型化属性 + 方法签名**（而非模糊职责描述），可直接指导编码，符合 LLD 标准核心要求。
- **范围边界（§1.2 In/Out）** 清晰，正确排除 AI 编排 / 服务端状态机持久化 / 通知 / 支付，避免模块越界。

## 5. 评审方法说明

- 非作者自评：逐条将 LLD 声明与 HLD 原文行号（§6.13.2/§3.4/§6.14.1/§6.14.3/§6.14.8）及 PRD 章节（§494/§496）交叉核验，凡"声称遵循"但 DDL/算法/状态机与上游冲突者，记为矛盾而非建议。
- 标准合规：对照 IEEE 1016 设计视图与中文详细设计模板的硬交付物清单（类图签名 / 时序含错误分支 / 状态机守卫 / 算法伪代码 / 错误码 / DDL / 可追溯性 / 测试）逐项核对，虚报项（F-10）单独记。
- 本评审不替代 `check_prd_hld_traceability.py`（仅校验 HLD↔PRD）；LLD↔HLD 自动化校验门尚未实现（见 LLD §11 建议），故本次为人工复核。
