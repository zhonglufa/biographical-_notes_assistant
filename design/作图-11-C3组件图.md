## §3.9 C3 组件图

#### 3.9.1 决策目标

| 问题 | 答案 |
|------|------|
| 支持什么决策 | 某个容器内部由哪些组件构成? 组件之间如何协作? 关键模块的边界在哪? |
| 谁读 | 后端开发、LLD 设计者、code review 评审人 |
| 决策后果 | 组件划分错了 → 模块边界错误,后期重构成本高 |

#### 3.9.2 C4 层级纪律

C3 必须在 C2 容器图的**某个具体容器**的上下文中绘制:

- **只允许出现**: 选中的单个容器内的**组件**(粗粒度的代码模块/包/类簇)、它们的接口和依赖关系
- **禁止出现**:
  - C2 中其他容器的内部细节(其他容器用灰盒表示,只露与本容器交互的接口)
  - 类级细节(类图属于 C4/UML 详细类图,不在 C3 表达)
  - 数据库/中间件的物理细节(用灰盒表示)
- **必选关系**: C3 必须明确**目标容器**是哪个 — 通常图标题或边界框标识
- 违反 = 不合格,直接打回

> **C3 vs C2 关系**: C2 关注"系统由哪些容器组成",C3 关注"这个容器内由哪些组件组成"。C3 总是从 C2 中"放大"一个容器。

#### 3.9.3 与 C2/UML 类图的区别

| 维度 | C3 组件图 | C2 容器图 | UML 类图 |
|------|----------|----------|----------|
| 抽象层级 | 容器 → 组件 | 系统 → 容器 | 类 → 类 |
| 节点 | 组件(代码模块/包) | 容器(部署单元) | 类 |
| 边 | 依赖/调用(关系描述) | 协议:端口 | 关联/依赖/继承/实现 |
| 出现位置 | LLD 阶段 | HLD 阶段 | LLD 阶段 |
| 数量上限 | 1 张/容器 | 1 张/系统 | 按模块 |
| 元素上限 | ≤ 12 组件 | ≤ 12 容器 | ≤ 15 类 |

> **常见错误**: 把 C3 画成"展开的类图"(列出所有类),这是把 C3 降级到 C4/UML 类图层级,违反单一抽象层级原则。

#### 3.9.4 元素完备性

| 元素 | 必须 | 说明 |
|------|------|------|
| 目标容器边界 | ✅ | 虚线圆角矩形,标注 `[Container: 容器名]`,作为 C3 的"画布边界" |
| 组件 | ✅ | 矩形,标注 **组件名 + 主要职责**(1 行说明) |
| 组件接口(可选) | △ | 圆形/棒棒糖(`lollipop`)或半圆(`socket`),表示对外暴露的接口 |
| 外部容器(灰盒) | ✅ | C2 中与本容器交互的其他容器,仅显示名称 + 接口名 |
| 依赖关系 | ✅ | 实线箭头,标注 **关系描述(动词短语)**,不带协议 |
| 实现关系 | △ | 虚线空心三角箭头,组件实现接口 |
| 外部数据源(灰盒) | △ | 数据库/缓存/队列等,用灰盒表示,不展开内部 |
| 图例 | ✅ | 颜色/线型/箭头含义 + "灰盒"含义说明 |

**红线**:
- C3 中**禁止**标注协议:端口(协议属于 C2 层级,C3 不再重复)
- C3 中**禁止**出现具体类名(类级细节属于 UML 类图)

#### 3.9.5 布局规范

**推荐布局**: 上下分层 + 列对齐(类似 C2 但更紧凑)

```
┌─────────────────────────────────────────────┐
│   [Container: Java 后端服务]   (虚线边界)      │
│                                              │
│   ┌─────────┐  ┌─────────┐  ┌─────────┐    │
│   │  Controller│ │  Service │ │  Mapper │    │
│   │  控制层    │  │  业务层  │  │ 数据访问 │    │
│   └─────┬─────┘  └────┬────┘  └────┬────┘    │
│         │             │            │         │
│   ──────┼─────────────┼────────────┼─────    │
│                                              │
└─────────────────────────────────────────────┘
        │              │            │
        ▼              ▼            ▼
   [MySQL 8.0]    [Redis 7.2]   [RabbitMQ]
   (灰盒,外部)     (灰盒,外部)    (灰盒,外部)
```

**布局原则**:

| 参数 | 标准值 | 说明 |
|------|--------|------|
| 目标容器边界 | 虚线,stroke-dasharray="6,4" | 标识 C3 的"画布范围" |
| 组件高度 | 70px | 容纳组件名(13px)+ 职责描述(10px) + [Component] 标签 |
| 组件宽度 | 140-180px | 按组件名字数适配,统一宽度便于对齐 |
| 组件间距 | ≥ 40px | 同一层内两个组件之间的水平间距 |
| 层间距 | ≥ 80px | 控制层 → 业务层 → 数据访问层的垂直间距 |
| 灰盒尺寸 | 100 × 50px | 外部容器/数据源的统一尺寸 |
| 灰盒颜色 | `#F3F4F6` 填充 + `#9CA3AF` 边框 | 明确区别于内部组件 |
| 接口标记(lollipop) | 直径 14px 圆,白底蓝边 | 标识对外暴露的服务/接口 |

> **禁止**: 双列布局 — C3 中双列布局会导致组件间连线交叉,应统一按"控制层 → 业务层 → 数据访问层"垂直分层。

> **例外**: 当业务组件需要按"最近原则"对齐到外部灰盒时,允许业务层用 **2 列布局**(左对齐数据源/存储类灰盒,右对齐消息/缓存类灰盒),详见 [ST-15 灰盒左右二分](#st-15-灰盒左右二分--最近原则)。

#### 3.9.5.1 灰盒对齐:ST-15 灰盒左右二分 + 最近原则

> **新规 (v4.0, 2026-08-15)**: C3 组件图绘制外部灰盒时,必须遵循"职能分组 + 距离最近"双重原则,避免灰盒分散导致连线长、跨图绕行。

**核心规则**:

| 维度 | 规则 | 说明 |
|------|------|------|
| **职能分组** | 灰盒按"数据源/存储" vs "消息/缓存" 二分 | 不按字母序或出现顺序 |
| **左右二分** | 数据源/存储类 → 左列;消息/缓存类 → 右列 | 整个图只有 2 个灰盒列,不再有 3 区或 4 区 |
| **最近对齐** | 灰盒横向中心与对应业务组件的横向中心偏差 ≤ 160px | 距离越近,连线越短 |
| **单段水平** | 业务层 → 灰盒的连线**必须**是单段水平 H (≤ 120px) | 避免 L 形绕行 |
| **水平通道禁令** | 禁止在同高度布置 ≥ 3 条水平连线形成"水平通道" | 通道式布局导致 4 线竞争,视觉乱 |

**布局模板**:

```
┌──────────────────────────────[Container: 目标容器]────────────────────────────┐
│                                                                              │
│  ┌─控制层─┐  ┌─调度层─┐  ┌─监听层─┐      (顶部: 3 个入口)                     │
│                                                                              │
│  ┌─A业务─┐        ┌─B业务─┐      (业务层: 2 列,按最近对齐灰盒)              │
│  │  x=左 │        │  x=右 │                                                  │
│  └───┬───┘        └───┬───┘                                                  │
│      │                │                                                      │
│  ┌─C业务─┐        ┌─D业务─┐      (业务层下半: 2 列)                          │
│  │  x=左 │        │  x=右 │                                                  │
│  └───┬───┘        └───┬───┘                                                  │
│      │                │                                                      │
│  └──── 数据访问层 (合并) ─────┘                                               │
│                                                                              │
└──────────────────────────────────────────────────────────────────────────────┘
       │            │              │              │
       ▼            ▼              ▼              ▼
  [Python]      [MySQL]       [Redis]        [RabbitMQ]
   (左列)       (左列)         (右列)          (右列)
   数据源        存储          消息/缓存         消息/缓存
```

**反例 (v3.0 之前)**:

```
   ❌ 灰盒分散 3 个区:
   [Python]                    [Redis]
        \                       /
         \   中间一条长线        /
          \________  ________/
                   \/
                [数据层]    ← 中间汇聚,线长且乱
                  /
                 /
   [MySQL]                [RabbitMQ]

   ❌ y=380 水平通道 4 线竞争:
   [业务1]──┐
   [业务2]──┼── y=380 水平通道 ──→ [数据层]   ← 4 条线在同一 y 竞争
   [业务3]──┤
   [业务4]──┘
```

**正例 (v4.0)**:

```
   ✅ 灰盒严格左右二分,各自单段水平:
   [简历解析]──[Python]      [状态跟踪]──[Redis]
   [投递调度]──[MySQL]       [发布器]  ──[RabbitMQ]
              ↑                          ↑
         x=左对齐                  x=右对齐
         全部 ≤ 120px 单段
```

**为什么灰盒要左右二分 (而非上下 / 分散)**:

| 分法 | 评估 |
|------|------|
| 全部堆底部 | ❌ 内部组件若也靠底部会重叠,且数据流方向不清 |
| 4 个方向散开 | ❌ 连线从中心向四周辐射,长线交叉 |
| 上下分布 | ❌ 重力感不对(数据库通常与业务平级,而非业务之上) |
| **左右二分** | ✅ 符合"数据源在左、消息/缓存在右"的阅读习惯,自然分两组 |

**ST-15 总结**: 灰盒的"左右二分"是 C3 组件图最重要的布局原则,直接决定图的视觉清爽度。

#### 3.9.8 元素命名约定

C3 中所有元素命名必须与 C2 容器图保持一致:

| C3 元素 | 命名规则 | 示例 |
|---------|---------|------|
| 目标容器 | 与 C2 完全一致 | `Java 后端服务` (与 C2 一致) |
| 组件 | **业务能力名**,不写类名 | `简历解析服务` (✅) vs `ResumeParseService` (❌) |
| 接口 | 业务能力 + 协议关键词 | `投递执行接口` / `状态查询API` |
| 外部容器(灰盒) | 与 C2 完全一致 | `MySQL 8.0` / `Redis 7.2` |
| 关系描述 | 动词短语(3-8 字) | `调用` / `查询数据` / `发送消息` / `异步通知` |

> **关键原则**: C3 的命名要让"不懂代码的产品经理也能看懂"。避免 `Service` / `Manager` / `Util` / `Helper` 等纯技术后缀。

#### 3.9.9 审查清单

```
□ 3.9.1  决策目标: 这张 C3 描绘的是哪个容器? 为什么要展开它?
□ 3.9.2  C4 层级: 是否只有 1 个目标容器被展开? 其他容器用灰盒?
□ 3.9.3  抽象层级: 是否出现了类名/包名/类成员? (出现 = 不合格)
□ 3.9.4  协议信息: C3 中是否标注了协议:端口? (出现 = 越权,应回 C2)
□ 3.9.5  元素完备性: 所有关键组件是否都已画? 是否有遗漏?
□ 3.9.6  命名一致: 组件名/容器名/接口名是否与 C2、类图、时序图一致?
□ 3.9.7  关系方向: 所有依赖关系是否有方向箭头?
□ 3.9.8  关系描述: 每条线是否标注了动词短语?
□ 3.9.9  布局: 是否采用上中下分层布局? 是否有连线交叉?
□ 3.9.10 灰盒规范: 外部容器/数据库是否用统一灰盒样式?
□ 3.9.11 接口标记: 关键对外接口是否用 lollipop 标识?
□ 3.9.12 复杂度: 组件数 ≤ 12? 关系数 ≤ 25?
□ 3.9.13 元数据: 是否完整(作者/日期/版本/源容器/状态)?
□ 3.9.14 可追溯: 每个组件是否对应 LLD 中的某个模块?
□ 3.9.15 跨图一致: 组件名/接口名是否与类图、时序图一致?
□ 3.9.16 [ST-15] 灰盒左右二分: 4 个灰盒是否严格分两列(数据源/存储 左,消息/缓存 右)?
□ 3.9.17 [ST-15] 最近对齐: 灰盒与对应业务组件的横向中心偏差是否 ≤ 160px?

```

#### 3.9.10 反模式

| 反模式 | 错误表现 | 正确做法 |
|--------|----------|----------|
| **C3 降级为类图** | 列出所有类、方法、字段 | C3 只到组件(代码模块)粒度,类级用 UML 类图 |
| **C3 越权标协议** | C3 组件间连线上写 `gRPC:50051` | 协议属于 C2 层级,C3 只标关系描述 |
| **C3 多容器混画** | 一张 C3 画了 Java + Python 两个容器的内部 | C3 必须只展开 1 个容器,多容器分别画多张 C3 |
| **万能 C3** | 一张 C3 画了 20+ 组件,塞满所有信息 | 按子域拆分多张 C3,每张 ≤ 12 组件 |
| **灰盒内部细节** | 把外部数据库也画成有内部组件 | 外部数据源一律用灰盒,只显示名称 |
| **无方向依赖** | 组件间连线没有箭头 | 每个依赖关系必须有方向箭头 |
| **技术后缀命名** | `Service` / `Manager` / `Util` | 用业务能力命名,如 `简历解析` |
| **C3 孤立** | C3 没有标"对应 C2 中的哪个容器" | 图标题或边界框必须标识目标容器 |
| **灰盒分散 3 区** (ST-15) | 4 个灰盒分到左上/右上/中下/右下等 3+ 个区域 | 严格左右二分: 数据源/存储在左,消息/缓存在右 |
| **灰盒长线绕行** (ST-15) | 灰盒与对应业务组件距离 > 200px,连线 5+ 段 L 形 | 灰盒紧邻业务组件,中心偏差 ≤ 160px,连线 ≤ 2 段 L 形或单段 |
| **水平通道多线竞争** (ST-15) | 在同一 y 高度布置 ≥ 3 条水平连线,形成"通道" | 跨列线走独立 y 通道(间隔 ≥ 20px),或用侧边 L 形绕行 |

#### 3.9.12 C3 拆分指引

**何时需要拆分**:
- 目标容器内组件数 > 12 → 按子域拆分为多张 C3
- 同一容器有多个独立业务域(如电商系统有"订单域" + "支付域" + "库存域")→ 按域拆分
- 不同受众(前端/后端/算法)需要关注不同组件 → 按受众拆分

**拆分原则**:
- 拆分后的每张 C3 必须保留**目标容器边界**(虚线)
- 拆分后的 C3 共享同一组灰盒(外部容器)
- 拆分时**不拆分灰盒**,灰盒在所有 C3 中保持一致
