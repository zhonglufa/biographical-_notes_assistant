## §1 作图交付标准(概述)

### 1.1 适用范围

本标准适用于软件工程全生命周期中所有设计图的绘制与交付，覆盖产品工程、需求分析、概要设计、详细设计、接口设计、部署运维六个阶段。所有设计图必须遵循本标准的通用规范及其对应图类型的交付标准，方可进入评审流程。

### 1.2 涵盖图类型

本标准覆盖软件工程全生命周期所有设计图，从方法论来源分为以下体系：

| 方法论 | 体系 | 图类型 | 当前标准状态 |
|--------|------|--------|-------------|
| **C4 模型** | 架构可视化 | C1 系统上下文图、C2 容器图、C3 组件图、C4 代码图 | 已有 C1-C2 标准 |
| **UML 2.5 结构图** | 静态结构 | 类图、组件图、部署图、对象图、包图、组合结构图、画像图 | 已有类图/部署图标准 |
| **UML 2.5 行为图** | 动态行为 | 用例图、活动图、状态机图、时序图、通信图、时序图（Timing）、交互概览图 | 已有时序图/活动图/状态机图标准 |
| **数据建模** | 数据关系 | ER 图（Crow's Foot） | 已有标准 |
| **产品工程** | 需求与体验 | 用户旅程图、业务流程图（BPMN 2.0）、线框图、用户故事地图 | 附录 A 提及，标准待补充 |
| **接口与部署** | 契约与运维 | API 契约图（OpenAPI）、数据流图（DFD）、网络拓扑图、架构演进图 | 附录 A 提及，标准待补充 |

> 当前已建立完整交付标准的图类型（§3 各节）共 **8 种**：C1、C2、时序图、ER 图、部署图、类图、活动图、状态机图。其余图类型的标准将在后续版本逐步补充。全生命周期 16+ 种图类型清单见附录 A。

### 1.3 方法论来源

| 方法论 | 版本/标准 | 核心依据 |
|--------|----------|----------|
| C4 模型 | Simon Brown, c4model.com | 系统上下文 → 容器 → 组件 → 代码（逐层抽象） |
| UML 2.5 | OMG 规范, ISO/IEC 19505-2 | 13 种图类型的语法和语义标准 |
| Crow's Foot | Peter Chen, IDEF1X | 实体关系图的基数符号标准 |
| WCAG 2.1 | W3C 无障碍标准 | 颜色对比度 ≥ 4.5:1，色盲安全 |

### 1.4 21 个通用维度

所有图类型均从以下 21 个维度进行评审，每个维度均有明确的验收方式：

| # | 维度 | 定义 | 验收方式 |
|---|------|------|----------|
| 1 | **决策目标** | 图支持什么设计决策、谁读、为什么读 | 问"这张图解决什么决策问题" |
| 2 | **C4 层级纪律** | 是否遵守单一抽象层级，不越级 | 检查图中元素是否属于该层级 |
| 3 | **UML 语法合规** | 线型、箭头、片段是否符合 UML 2.5 | 逐项对照规范表 |
| 4 | **元素完备性** | 是否包含该层级所有必要元素 | 对照 PRD + 文档列表 |
| 5 | **线条与间距** | 线宽、平行线间距、标签偏移、折角、交叉 | 数值测量 |
| 6 | **颜色系统** | 色板固定、语义不二义、对比度、色盲安全 | 提取 fill/stroke 值核对 |
| 7 | **字体层级** | 字号、字重、对齐、字体回退链 | 检查所有 `<text>` 元素 |
| 8 | **复杂度上限** | 元素数/连接数是否超标 | 计数检查 |
| 9 | **元数据与溯源** | 作者、日期、版本、来源、审查状态、关联图 | 检查 `<desc>` 或图底部文字 |
| 10 | **跨图一致性** | 与其他图是否有矛盾（名称/接口/实体/参与者） | 交叉对比 |
| 11 | **决策可追溯** | 图中元素是否能追溯到 ADR 或 PRD 条款 | 随机抽样 5 个元素 |
| 12 | **4+1 视图覆盖** | 逻辑视图、进程视图、开发视图、物理视图、场景视图 | 检查是否覆盖 HLD 阶段必需的视图 |
| 13 | **审查治理** | 自审/同行审查/架构评审/基线审批各阶段通过标准 | 检查审查记录 |
| 14 | **自动化验证** | 线宽/间距/颜色/字数/元数据可自动检查 | 运行 SVG 检查脚本 |
| 15 | **风险与技术债务** | ⚠️ RISK、🏗️ TBD、💳 DEBT、🔄 MIGRATE、🔒 SEC 标记 | 检查图中是否有标记 |
| 16 | **时间维度与演进** | 分阶段交付的图是否区分 Phase 1/2/Future | 检查多阶段项目 |
| 17 | **利益相关方定制** | 目标受众是否明确，信息密度是否匹配 | 检查元数据中的 audience |
| 18 | **多语言与国际** | 中文/英文/双语场景下的命名一致性 | 检查同一概念是否混用 |
| 19 | **工具链与源文件** | SVG 交付、源文件保留、命名规范、目录结构 | 检查文件系统 |
| 20 | **生命周期状态** | DRAFT/REVIEW/APPROVED/DEPRECATED 标记正确 | 检查状态标记 |
| 21 | **布局与可读性** | 正交路由、元素间距、留白、图例完整性 | 视觉检查 |

## §2 作图基本要求(通用规范)

> 本章定义所有图类型通用的作图规范，适用于本标准涵盖的全部图类型。每张图在绘制前须先过本章通用规范，再过对应图类型的专用规范。

### 2.1 颜色系统

#### 2.1.1 色板总表

| 颜色 | 色值 | 语义 | 用途 |
|------|------|------|------|
| 蓝 | `#1A73E8` | 系统/容器/业务层 | fill |
| 绿 | `#22C55E` | 数据库/数据层 | fill |

| 黄 | `#F59E0B` | 基础设施层 | fill |
| 灰 | `#9CA3AF` | 外部系统 | fill |
| 深灰 | `#333333` | 文字/系统边界框 | fill/stroke |
| 中灰 | `#666666` | 连接线/次要文字 | stroke/fill |
| 浅灰 | `#F8F9FA` | 图例背景/层背景 | fill |
| 浅灰边框 | `#D1D5DB` | 图例/表格边框 | stroke |
| 浅灰背景 | `#F9FAFB` | 图例背景增强 | fill |

| 白 | `#FFFFFF` | 背景/实体字段区 | fill |

#### 2.1.2 颜色使用规则

| 规则 | 标准 | 违反后果 |
|------|------|----------|
| 色板合规 | 所有颜色必须来自色板，禁止使用非色板颜色 | 不合格 |
| 透明合规 | `none` 仅用于 fill/stroke 表示透明，不可用于文字 | 不合格 |
| 语义唯一 | 一个颜色在全文档中只有一种语义 | 读者混淆 |
| 对比度 | 所有文字与背景对比度 ≥ 4.5:1（WCAG AA） | 可读性不合格 |
| 色盲安全 | 红绿不作为唯一区分手段，配合线型或标签 | 无障碍不合格 |

### 2.3 线条与间距通用规范

#### 2.3.1 基本线条参数

| 参数 | 标准值 | 检查方法 |
|------|--------|----------|
| 线宽 — 普通线 | 1.5px | 提取 `stroke-width` |
| 线宽 — 强调线/边界框 | 2.5px | 提取 `stroke-width` |
| 线宽 — 虚线 | 1.5px | 提取 `stroke-width` |
| 箭头大小 | 宽 8px × 高 6px | 箭头路径尺寸 |
| 虚线间距 — 实段 | 6px | `stroke-dasharray` 第一值 |
| 虚线间距 — 空段 | 4px | `stroke-dasharray` 第二值 |

#### 2.3.2 间距标准

##### 形与形之间间隔（核心规范）

**核心原则**：两个图形元素（矩形、圆形、菱形、路径等）之间必须有明确的最小间距，禁止紧贴或重叠。此规范适用于图上所有元素，按元素类型细分为：

| 间距类型 | 标准值 | 检查方法 | 违反后果 |
|----------|--------|----------|----------|
| **矩形与矩形**（水平相邻） | ≥ 30px | 两个 rect 的最近水平距离 | 元素紧贴/重叠 → 不合格 |
| **矩形与矩形**（垂直相邻） | ≥ 20px | 两个 rect 的最近垂直距离 | 元素紧贴/重叠 → 不合格 |
| **矩形与圆/椭圆** | ≥ 20px | rect 边框与 circle 边框的最近距离 | 元素紧贴 → 不合格 |
| **矩形与菱形（决策节点）** | ≥ 25px | rect 边框与 polygon 边框的最近距离 | 决策节点紧贴其他元素 → 不合格 |
| **圆与圆** | ≥ 20px | 两个 circle 边框的最近距离 | 圆元素重叠 → 不合格 |
| **元素与图例** | ≥ 20px | 元素底部与图例顶部垂直距离 | 图例遮挡主图元素 → 不合格 |
| **元素与主图边框** | ≥ 30px | 元素边框与图 viewBox 边界的距离 | 元素紧贴图边缘 → 不合格 |
| **泳道/分区边界** | ≥ 10px | 泳道内元素与泳道边界的间距 | 元素紧贴分区线 → 不合格 |
| **嵌套元素（容器内元素）** | ≥ 12px | 子元素与父容器内边框的间距 | 子元素紧贴/超出父容器 → 不合格 |
| **分组框与内部元素** | ≥ 15px | 分组框边框与组内元素边框的间距 | 分组框紧贴组内元素 → 不合格 |
| **线-容器间距（非连接线段）** | ≥ 20px | 非连接线段（水平/垂直段）与容器边界的最小距离 | 线穿过或紧贴容器 → 不合格 |
| **线穿插容器** | **零容忍** | 检查每条线段的每个途经点是否在非源非目标容器内部 | 线穿过容器 → 不合格，直接打回 |

##### 线与线间距

| 间距类型 | 标准值 | 违反后果 |
|----------|--------|----------|
| 平行线间距 | **最低 ≥ 10px, 推荐 ≥ 14px, 关键线 ≥ 20px** | 线交叉/混淆 → 不合格 |
| 平行线偏移（同向重叠） | **最低 ≥ 10px, 推荐 ≥ 20px**（同一方向的多条平行线垂直偏移） | 线重叠 → 不合格 |
| 线与元素边框间距 | ≥ 12px | 线紧贴元素 → 不合格 |
| 线-容器间距（非连接线段） | ≥ 20px（水平/垂直段距容器边界） | 线穿过或紧贴容器 → 不合格 |
| 线穿插容器 | **零容忍** | 线穿过非源非目标容器 → 不合格，直接打回 |
| 引导线偏移 | ≥ 10px（引导线/辅助线与实线之间保持 10px 间距） | 引导线与实线重叠 → 不合格 |
| 标签偏移（线上方） | 线上方 4px，距线 ≥ 2px | 线穿过标签 → 不合格 |
| 标签两侧留白 | ≥ 6px | 文字被线穿过 → 不合格 |
| 正交折角 | 直角（0px）或圆角（5px，统一） | 斜线 → 不合格 |
| 线端接入 | 齐平（连接线触达容器边界，不悬浮、不缩进） | 线端不齐 → 不合格 |
| 分支线夹角 | 90° T 型分叉 | Y 型/斜向分叉 → 不合格 |
| 线交叉 | **零容忍** | 任何两条线交叉 → 不合格 |
| 网格对齐 | 10px 网格（所有途经点 x/y 坐标对齐 10px 网格） | 坐标不在网格上 → 建议改进 |

> **§2.3.2 间距分级说明**:
> - **最低标准 10px** = 满足零重叠,但视觉上仍可能感觉密集
> - **推荐标准 14-20px** = 视觉舒适,大多数场景应采用
> - **关键线 ≥20px** = 主干、总线层、频繁被引用的线
> - **铁律来源**: 铁律 A.1/C.3 (line 619/727) 已统一为 ≥20px,本表同步

#### 2.3.3 标注与线间距规范

**核心原则**：标注框（含文字标签）与连接线之间必须有明确间距，禁止线穿过标注框。

| 参数 | 标准值 | 检查方法 | 违反后果 |
|------|--------|----------|----------|
| 标签底部与线间距 | ≥ 2px | 标签框底部 y 坐标与线的 y 坐标差值 | 线穿过标签框 → 不合格 |
| 标签顶部与上方元素间距 | ≥ 10px | 标签框顶部与上方最近元素底部的距离 | 标签与上方元素重叠 → 不合格 |
| 标签偏移方向 | 线上方（水平线），线左侧（竖直线） | 检查标签中心是否在线的对应侧 | 标签位置错误 → 不合格 |
| 标签框与线平行 | 标签框底部平行于线 | 标签框矩形边与线段的夹角 | 标签歪斜 → 不合格 |
| 折线处标签位置 | 在水平段上方，非折角处 | 标签 x 坐标在折线水平段范围内 | 标签在折角处 → 建议移至水平段中央 |
| 标签白底矩形宽度 | 刚好包住文字，右边界距箭头标记 ≥ 8px | 矩形右边界 ≤ 箭头尖 x - 8px | 白底遮挡箭头 → 不合格，直接打回 |

**SVG 实现检查**：

```
标签 rect 的底部 y 坐标 ≤ 线 y 坐标 - 2px    ✓ 标签在线之上，有间距
标签 rect 的底部 y 坐标 > 线 y 坐标           ✗ 线穿过标签框，不合格
```

### 2.4 文字间距与防重叠规范

#### 2.4.1 重叠判定标准

| 判定项 | 标准 | 说明 |
|--------|------|------|
| 重叠判定 | 两个文字元素的外包围盒（bounding box）存在交集 → 判定为重叠 | 零容忍，任何重叠即不合格 |
| 文字包围盒宽度 | 中文：字符数 × 字号 × 0.6；英文：字符数 × 字号 × 0.5 | 用于计算文字占据的实际空间 |
| 文字包围盒高度 | 字号 × 1.4 | 含上下留白 |

#### 2.4.2 最小间距标准

| 间距类型 | 标准值 | 检测方法 |
|----------|--------|----------|
| 文字与最近元素边框间距 | ≥ 10px | 计算文字包围盒与元素 rect 的最近距离 |
| 相邻文字标签水平间距 | ≥ 12px | 两个标签包围盒的最近水平距离 |
| 相邻文字标签垂直间距 | ≥ 6px | 两个标签包围盒的最近垂直距离 |
| 连接线标签与线交叉点间距 | ≥ 15px | 标签包围盒与线交叉点坐标的距离 |
| 标签与元素边框间距 | ≥ 10px | 标签包围盒距最近元素 rect 的距离 |
| 多行文字行间距 | 字号 × 0.8 | 前一行文字底部与后一行文字顶部的距离 |
| 图例与主图元素间距 | ≥ 20px | 图例 rect 顶部与主图最低元素底部的垂直距离 |

#### 2.4.3 防重叠预处理流程（作图前必须执行）

```
Step 1: 列出图上所有文字元素，计算每个元素的包围盒（宽 × 高）
Step 2: 逐一检查任意两个包围盒是否存在交集 → 若存在，判定为重叠
Step 3: 检查所有文字包围盒与元素边框（rect）是否存在交集 → 若存在，判定为压框
Step 4: 调整策略（按优先级）：
  a) 优先增大元素间距（拉开元素之间的距离，使文字有足够空间）
  b) 其次缩短文字内容（精简标签文字，减少包围盒宽度）
  c) 最后调整文字位置（移至线上方/左侧/右侧/内部）
Step 5: 重新检查所有包围盒，直到无重叠、无压框
Step 6: 确认图例位置：图例 y 起始坐标 > 所有主图元素 y 结束坐标 + 20px
```

#### 2.4.4 常见重叠场景及解决方案

| 重叠场景 | 错误表现 | 解决方案 |
|----------|----------|----------|
| 连接线标签与相邻元素边框重叠 | 标签文字超出元素边框 | 增大元素间距，或缩短标签文字 |
| 连接线标签与相邻连接线标签重叠 | 两条线标签交叉 | 增大平行线间距 ≥ 14px |
| 连接线标签与线交叉点重叠 | 标签盖住线交叉点 | 标签偏移至远离交叉点一侧 |
| 图例与主图元素重叠 | 图例遮挡外部系统 | 图例 y 起始 > 主图最低元素 y 结束 + 20px |

#### 2.4.5 图例与标签通用 ST 规则 (ST-3, ST-4, ST-5)

> 本节定义图例和标签的通用规则。ST-10~ST-13（文字位置）在下一节单独定义。

**ST-3：图例只画颜色/线型**

| 项目 | 规范 |
|------|------|
| 图例内容 | 仅**颜色色块** + **线型示例** + **简短文字标签** |
| 禁止 | 图例中绘制信息展示文字（如完整协议、动态流向、节点说明）|
| 信息密度 | 颜色/线型/箭头含义 ≤ 8 项 |
| 位置 | 图底部独立区域, y > 主图最低元素 y + 20px |

**反例**：
```
❌ 图例中画 "JDBC :3306 (实线)" 文字段 → 信息展示,违反 ST-3
```

**正例**：
```
✅ 图例: [蓝色方块] 业务  [绿色方块] 数据  [红色方块] 队列  ─→ 同步  - - → 异步
```

**ST-4：标签在垂直段外侧（不压线）**

| 项目 | 规范 |
|------|------|
| 标签 x 位置 | 垂直线 x ± 2px 外（居左/居右） |
| 标签 y 位置 | 垂直段中点 ±10px |
| 压线判定 | 文字 bbox 中心 x 与垂直线 x 重叠 → 压线 |

**ST-5：捆扎段无说明文字**

| 项目 | 规范 |
|------|------|
| 共享段 | 不标任何文字（避免重叠） |
| 协议标注 | 标在每条线的**差异段**（自分叉点到目标段） |
| 视觉判断 | 共享段 y/x 范围内应无 `<text>` 元素 |

**反例**：
```
❌ 共享段 (200, 320)→(600, 320) 上写 "Redis :6379" → 共享段标注,违反 ST-5
```

**正例**：
```
✅ 共享段无文字, Java→Redis 标在差异段 (200, 320)→(600, 320) 水平段中点
   Python→Redis 标在垂直差异段 (600, 260)→(600, 320) 右侧
```

#### 2.4.6 标签白底矩形约束规则 (ST-16)

> 本节定义连接线标签白底矩形的不遮挡规则，是 §2.3.3 标签白底矩形宽度规则的**精确化定义**。

**ST-16：标签白底矩形不遮挡箭头标记**

| 项目 | 规范 |
|------|------|
| 矩形宽度 | 刚好包住文字内容，左右各留 2-3px 内边距 |
| 右边界约束 | 矩形右边界 ≤ 箭头标记起始 x 坐标 - 8px |
| 左边界约束 | 矩形左边界 ≥ 线段起点 x 坐标 + 8px |
| 矩形高度 | 刚好包住文字高度（字号 × 1.4），上下各留 1px 内边距 |
| 颜色 | `fill="#FFFFFF"`（白色），无边框（`stroke="none"`） |

**箭头标记尺寸**：标准箭头标记宽 7px（`markerWidth="7"`），从线段终点向左延伸。因此：

```
矩形右边界 ≤ 线段终点 x - 箭头标记宽 - 1px（安全余量）
           = 线段终点 x - 8px
```

**反例（v1.0 错误）**：
```
❌ REST:8000 标签 rect x=252, w=76 → 右边界 x=328
   线段终点 x=320, 箭头标记宽 7px
   矩形右边界 328 > 320 - 8 = 312 → 白底遮挡箭头 ❌
```

**正例（v1.1 修正）**：
```
✅ REST:8000 标签 rect x=260, w=52 → 右边界 x=312
   线段终点 x=320, 箭头标记宽 7px
   矩形右边界 312 ≤ 320 - 8 = 312 → 白底刚好在箭头外 ✅
```

**检查方式**：对于每条有白底标签的线段，计算：
1. 标签矩形右边界 = rect.x + rect.width
2. 箭头起始 x = 线段终点 x - 7px（箭头标记宽）
3. 验证：矩形右边界 ≤ 箭头起始 x - 1px

#### 2.4.7 文字位置 ST 规则 (ST-10 ~ ST-13)

> 本节是 §2.3.3 文字间距规范的**精确化定义**。审查清单 Q8.1~Q8.4 引用 ST-10~ST-13,本节给出明确定义和正反例。

**ST-10：垂直线文字位置**

| 项目 | 规范 |
|------|------|
| 允许位置 | 居左（线 x - 2px, text-anchor="end"）或 居右（线 x + 2px, text-anchor="start"） |
| **禁止** | **居中（text-anchor="middle"）** — 居中会被垂直线穿过 |
| 字号 | 9-10px |
| 颜色 | 主标签 #1f2937（深灰，加粗） / 副标签 #475569（浅灰） |
| 位置 y | 垂直段中点 ±10px |

**反例**：
```
❌ Java→MySQL: x=200, y=340, text-anchor="middle"  → 文字被 x=200 垂直线穿过
```

**正例**：
```
✅ Java→MySQL: x=190, y=340, text-anchor="end"  → 文字在垂直线 x=200 左侧
✅ Java→MySQL: x=210, y=340, text-anchor="start" → 文字在垂直线 x=200 右侧
```

**ST-11：水平线文字位置**

| 项目 | 规范 |
|------|------|
| 允许位置 | 居中（text-anchor="middle"）|
| 位置 y | 水平段**上方** 4-6px（不压线） |
| 位置 x | 水平段中点（不靠近折角） |

**正例**：
```
✅ Java→Redis 水平段 y=380: 标签 x=415, y=374, text-anchor="middle" → 在 y=380 上方 6px
```

**ST-12：文字之间不重叠**

| 判定 | 标准 |
|------|------|
| 同一 y 的多个文字 | x 范围不能交叉 |
| 不同 y 的文字 | y 范围不能交叉 |
| 处理冲突 | 增大平行线间距 ≥14px / 调整 y 偏移 / 缩短文字 |

**ST-13：文字与所有线不交叉**

| 判定 | 标准 |
|------|------|
| 文字 bbox vs 线段 bbox | 不允许任何交集 |
| 文字背景 | 实线/虚线都不能穿过文字 |
| 例外 | **容器内文字**可被容器边框穿过（属于容器装饰） |

#### 2.4.8 标注类型分类 (实线 vs 虚线)

> 实线和虚线承担的语义不同,标注风格必须区分。

| 线型 | 标注类型 | 示例 | 理由 |
|------|----------|------|------|
| **实线 (实箭头)** | **仅协议标签** (协议 + 端口) | `JDBC :3306` / `Redis :6379` / `HTTPS API` | 实线 = 同步/直接调用,只需说明通信协议 |
| **虚线 (虚箭头)** | **动态流向描述** (动作 + 方向) | `消息同步` / `任务下发` / `JDBC 只读` | 虚线 = 异步/内部/特殊语义,需要说明数据/控制流方向 |
| **混合** | 禁止 | — | 单条线只标一个标签,实线不附加动态流向 |

**ST-14：每条线只有一个标注**
- 禁止在单条线上叠加多个标签（如协议 + 流向）
- 协议信息已通过协议标签表达,流向信息由线型和箭头表达
- 例外: 主标签 + 副标签 = 同一信息的两部分（如"JDBC :3306\n数据写入"）— **禁止**,只保留主标签

**反例（v4.10.1 错误）**：
```
❌ Java→MySQL: 主标签 "JDBC :3306" + 副标签 "数据写入" → 单线双标签,违反 ST-14
```

**正例（v4.11 修正）**：
```
✅ Java→MySQL: 单标签 "JDBC :3306" (10px 加粗 #1f2937) → 协议明确,无重复
```

#### 2.4.8.1 ST-15: 灰盒左右二分与最近原则 (C3 专项)

> **新规 (v4.0, 2026-08-15)**: C3 组件图外部灰盒的布局原则。详见 [作图-11-C3组件图.md §3.9.5.1](./作图-11-C3组件图.md#st-15-灰盒左右二分--最近原则)。

**核心 3 条**:
1. **职能分组**: 灰盒按"数据源/存储" vs "消息/缓存" 二分
2. **左右二分**: 数据源/存储在左列,消息/缓存在右列
3. **最近对齐**: 灰盒与对应业务组件横向中心偏差 ≤ 160px,单段水平连线 ≤ 120px

**禁止**:
- 4 个灰盒分散到 3+ 个区域(左上/右上/中下/右下)
- 同一 y 高度布置 ≥ 3 条水平连线形成"水平通道"

> **适用范围**: C3 组件图专用。C1 系统上下文、C2 容器图不强制(ST-15 是 C3 灰盒布局的针对性规则,其他层级有各自的 ST 规则)。

#### 2.4.9 终点对齐规范 (容器外边框)

> 连接线的**终点（箭头尖）必须落在目标容器的外边框上**,不允许进入容器内部,也不允许悬空。

| 项目 | 规范 |
|------|------|
| 终点位置 | 容器外边框上（rect 的边线像素）|
| 箭头朝向 | 指向容器中心方向（垂直线 → 容器中心 / 水平线 → 容器中心）|
| 终点 y | 容器顶/底 y（垂直进入）或 容器左/右 x（水平进入）|
| 容器内允许 | 仅 **容器内自身的内部连线**（容器内多个矩形之间的连线）|
| 容器内禁止 | **跨容器连线**进入容器内部 → 必须终止在外边框 |

**反例（v4.7~v4.9 错误）**：
```
❌ Python→MySQL 终点 (200, 460): MySQL 范围 x=120~280 y=420~500, (200, 460) 在 MySQL 内部
   → 箭头尖进入容器内部,违反"终点 = 外边框"原则
```

**正例（v4.10 修正）**：
```
✅ Python→MySQL 终点 (120, 460): 正好在 MySQL 左外边框 x=120
   → 箭头尖触到 x=120 边框即停,不入容器
```

**修正原则**：
- 终点 x 必须在容器 x 范围边界上 (顶/底进入 → 容器中心 x, 左/右进入 → 容器左/右 x)
- 终点的最后一段**不穿过**容器内部

#### 2.4.10 容器内不连线

> 容器矩形内部不允许有跨容器连线。起点从容器出发时,第一个折点必须在**容器外**。

| 项目 | 规范 |
|------|------|
| 起点第一段 | 必须先离开容器 (y < 容器顶 y 或 y > 容器底 y) |
| 容器内允许 | 仅 **容器内自身的内部连线**（节点在容器内,连线也在容器内,装饰用）|
| 容器内禁止 | **跨容器连线的起点水平段**在容器内擦底/顶 → 违反"容器外连线"原则 |

**反例（v4.8 错误）**：
```
❌ Java→Redis 起点水平段 y=260, x=200~230: y=260 是 Java 容器底边,水平段擦底边
```

**正例（v4.9 修正）**：
```
✅ Java→Redis 起点水平段 y=266: y=266 在 Java 容器底 y=260 下方 6px,容器外
```

**修正原则**：
- 起点水平段 y = 容器底 y + 6px (或 -6px 从容器顶出发)
- 起点垂直段 x = 容器右边缘 + 10px (向右离开)

### 2.5 布线拓扑规则（多源/多目标场景的连线结构）

> 本节专门解决"一源对多目标"或"多源对一目标"场景下的连线结构混乱问题，是 §2.3 间距规则的**结构性补充**。先有结构（§2.5），再有间距（§2.3），两者配合才能画出无重叠、无穿插的连线。
>
> **核心原则（来自 Sugiyama 框架, 1981）**：节点的层级（rank）决定边的方向，节点的水平对齐决定边是否为直线。**源和目标在同一列/行 = 垂直/水平直线（最简洁）**；不在同一列/行 = L 形/折线/总线束（变复杂）。
>
> **本节规则应用顺序**（先结构后间距）：
> ```
> §2.5.0 节点层级（最高优先级，决定一切）
>   ↓
> §2.5.1 扇出（节点层级内的端口分布）
>   ↓
> §2.5.2 主干（≥3 线汇聚时的合并结构）
>   ↓
> §2.5.3 反向捆扎（共享目标的线段复用）
>   ↓
> §2.5.4 总线层（平行线分层）
>   ↓
> §2.5.5 分支段隔离（主干分支段方向一致 + 不重叠）
>   ↓
> §2.3 间距规则（验证零穿插零交叉）
> ```

#### 2.5.0 节点层级（Node Layering）规则 【最高优先级】

**定义**：在作图前，先将所有节点按"数据/控制流方向"分配到不同层级（rank）。每"跳"（hop）= 一层。**源节点和目标节点在同一列/行 = 直线，是最简洁的连接方式**。

**这是 Sugiyama 框架 1981 年的核心算法**（Graphviz、ELK Layered、Structurizr、C4-PlantUML 等所有主流布局工具的基础）：
1. **层级分配（Layer Assignment）**：用最长路径法将节点分配到不同层级
2. **交叉最小化（Crossing Minimization）**：在每层内重排节点顺序
3. **坐标计算（Node Placement）**：计算具体坐标，**尽量让边变直**（straighten edges）
4. **边路由（Edge Routing）**：为需要弯折的边计算路径

**标准**：

| 参数 | 标准值 | 说明 |
|------|--------|------|
| 层级方向 | TB（Top-to-Bottom，从上到下）或 LR（Left-to-Right） | C4 模型默认 TB |
| 每跳一层 | 源→目标走一条边 = 跨一层 | 不要跳过中间层 |
| 列对齐 | 同层节点在同一行；相邻层节点在同一列 | 产生垂直/水平直线 |
| 跨列代价 | 每跨一列 = 一次 L 形弯折 | 跨列越少越好 |
| 节点密度 | 每层 ≤ 6 个节点 | 超过应拆分到多张图 |

**布局算法（C2 容器图标准布局）**：

```
Level 1 (顶层):     参与者 / 用户（Person）
   ↓
Level 2 (业务层):   业务容器（Java/Python/Node.js 等）
   ↓
Level 3 (数据层):   数据库 / 缓存 / 文件存储
   ↓
Level 4 (共享层):   消息队列 / 网关 / 共享服务
   ↓
Level 5 (外部系统): 外部 API / 第三方服务
```

**关键设计原则**：

1. **列对齐优先**：Level 2/3/4 的容器按列对齐（同一 x 坐标），产生垂直直线
2. **共享资源单独一层**：Redis/MySQL/RabbitMQ 等共享资源放在独立层级，不与业务容器同层
3. **外部系统集中**：5+ 外部系统放在最底层，水平排列
4. **跨列连接限制**：跨列连接只在业务层内部（短水平段），不跨多层

**违反示例（v2.x 的根本问题）**：

```
❌ 错误：业务层和外部系统同列对齐，Java 出发 6 条线
   Java (x=160) ─┬─→ MySQL (x=160, 同列 ✅)
                 ├─→ Redis (x=500, 跨列 340px ❌)
                 ├─→ RabbitMQ (x=350, 跨列 190px ❌)
                 ├─→ OSS (x=650, 跨列 490px ❌)
                 ├─→ LLM (x=200, 同列 ✅)
                 └─→ 外部系统... 全部跨列 ❌
   
   → 必然产生总线束 / 扇出 / 主干等补救措施 → 线条依然乱
```

**正确示例（v3.1+ 的解决方案）**：

```
✅ 正确：业务层/数据层/共享层 3 层列对齐（x=160/500/800）
   Java (x=160) → MySQL (x=160)  垂直直线 ✅
   Python (x=500) → Redis (x=500)  垂直直线 ✅
   Agent (x=800) → 浏览器池 (x=800)  垂直直线 ✅
   Java (x=160) → RabbitMQ (x=160)  垂直直线 ✅
   Agent (x=800) → OSS (x=800)  垂直直线 ✅
   
   → 同列连线全部是垂直直线，无需总线束/主干/扇出
```

**Sugiyama 框架对 C2 的应用**：
- 节点的层级（rank）= 业务层/数据层/共享层/外部系统层
- 节点的水平对齐 = 同列容器 x 坐标相同
- 边 = 源节点 → 目标节点的连接
- **同列节点间的边 = 垂直直线**（最简洁）
- 跨列节点间的边 = L 形（不可避免）
- **布局目标**：让 L 形数量最少，让直线数量最多

**附录：节点对齐的 6 种情况分析**

| 情况 | 源列 | 目标列 | 边形态 | 复杂度 |
|------|------|--------|--------|--------|
| 1. 同列相邻层 | x=160 (Level 2) | x=160 (Level 3) | **垂直直线** | 最简 |
| 2. 同列跨 2 层 | x=160 (Level 2) | x=160 (Level 4) | **垂直长直线** | 简 |
| 3. 跨 1 列相邻层 | x=160 (Level 2) | x=500 (Level 3) | L 形（垂直+水平+垂直） | 中 |
| 4. 同层内部 | x=160 (Level 2) | x=500 (Level 2) | 水平短线 | 简 |
| 5. 跨 2 列相邻层 | x=160 (Level 2) | x=800 (Level 3) | L 形（更长） | 中 |
| 6. 跨列跨层 | x=160 (Level 2) | x=800 (Level 5) | 多段折线 | 复杂 |

**作图原则**：情况 1/2 越多越好（占 ≥ 60%），情况 5/6 越少越好（占 ≤ 10%）。

#### 2.5.0.1 6 种情况的定线公式与铁律

> 本节是 §2.5.0 的**定线操作手册**。每种情况给出：路径公式、"乱"风险、铁律。

**通用术语**：
```
S: 源容器中心 x 坐标
D: 目标容器中心 x 坐标
Y_src_top: 源容器顶部 y
Y_src_bot: 源容器底部 y
Y_dst_top: 目标容器顶部 y
Y_dst_bot: 目标容器底部 y
Δx = |D - S|
Δy = |Y_dst - Y_src|
```

---

**情况 1：同列相邻层（最简）**

```
约束: S == D, |Δy| == 1 层
路径: M S Y_src_bot L S Y_dst_top
段数: 1 段
```

**乱风险**：无

**铁律 1.1**：路径直接连，无 waypoint

---

**情况 2：同列跨 2 层（垂直长直线）**

```
约束: S == D, |Δy| == 2 层
路径: M S Y_src_bot L S Y_dst_top
段数: 1 段
```

**乱风险**：**线穿过中间层容器**
- 例：Java (x=160) → 共享层 RabbitMQ (x=160)，中间数据层 MySQL 也在 x=160 → 垂直线穿过 MySQL ❌
- 例：Java (x=160) → 外部系统 LLM (x=160)，中间数据层 MySQL (x=160)、共享层 RabbitMQ (x=160) → 垂直线穿过 2 个中间层容器 ❌

**铁律 2.1**：**同列跨层时，中间层所有容器的 x 坐标必须与源/目标都不同**（至少错开 1 列）

**铁律 2.2**：如果无法满足铁律 2.1，必须改为跨列 L 形（情况 3）

**反例**：
```
Java (x=160) ──→ 招聘 (x=160), 中间层 MySQL/RabbitMQ 都在 x=160
   垂直线 y=180→720 穿过 MySQL (y=370) 和 RabbitMQ (y=540) ❌
   解决: 招聘平台放在 x=880（不与 Java 同列）
```

---

**情况 3：跨 1 列相邻层（3 段 L 形）**

```
约束: |D - S| == 1 列, |Δy| == 1 层
路径: M S Y_src_bot L S Y_mid L D Y_mid L D Y_dst_top
段数: 3 段
```

**Y_mid 选择公式**（关键！）：

```
Y_mid 必须满足"安全通道"约束:

  条件 1: Y_mid > max(Y_src_bot, Y_dst_top) + 10px
          (水平段在源/目标容器底部之下 10px)
  条件 2: Y_mid < min(中间层容器顶部) - 10px
          (水平段在中间层容器顶部之上 10px)
  条件 3: Y_mid 对齐 10px 网格
```

**乱风险 3.1**：**Y_mid 选错，水平段穿插容器**
```
源 (x=160, y_src_bot=260) ──→ 目标 (x=500, y_dst_top=370)
Y_mid = 200  → 水平段 y=200 在源容器内部 ❌
Y_mid = 320  → 水平段 y=320 在源容器下方 60px, 目标容器上方 50px ✅
Y_mid = 400  → 水平段 y=400 在目标容器内部 ❌
Y_mid = 350  → 水平段 y=350 在目标容器上方 20px, 10px 网格 ✅
```

**乱风险 3.2**：**多条跨列连接的水平段重叠**
```
Java→Redis 水平段 y=320
Python→MySQL 水平段 y=320 (相同 y)
→ 完全重叠 ❌
```

**铁律 3.1**：**Y_mid 必须在源/目标容器之间的"安全通道"**（条件 1+2）

**铁律 3.2**：**同一层内的所有跨列水平段必须 y 偏移 ≥ 20px**（10px 是最低，20px 更安全）

**铁律 3.3**：**跨列水平段不能在任何容器的 y 范围内**

**正例**（v3.1 中的 Java→Redis）：
```
Java (x=160, y_src_bot=260) → Redis (x=500, y_dst_top=370)
Y_mid = 320 满足:
  - 条件 1: 320 > 260 + 10 = 270 ✅
  - 条件 2: 320 < 370 - 10 = 360 ✅ (目标容器在 y=370~450, 320 < 370-10)
  - 条件 3: 320 % 10 == 0 ✅
  - 不在任何容器 y 范围内 ✅
路径: M 160 260 L 160 320 L 500 320 L 500 370 ✅
```

---

**情况 4：同层内部（水平短线）**

```
约束: Y_src == Y_dst, |Δx| ≥ 1 列
路径: M (S + 容器半宽 + 10) Y L (D - 容器半宽 - 10) Y
段数: 1 段
```

**起点/终点 x 公式**：
```
起点 x = S + W_src/2 + 10  (源容器右边缘 + 10px)
终点 x = D - W_dst/2 - 10  (目标容器左边缘 - 10px)
```

**乱风险 4.1**：**箭头方向错**
```
Python→Java: 源在右, 目标在左, 箭头应该向左
Java→Python: 源在左, 目标在右, 箭头应该向右
```

**铁律 4.1**：**箭头方向 = 数据/控制流方向**

**乱风险 4.2**：**多源汇入同一目标时多条水平线重叠**
```
Java→Python, Agent→Python (2 条线汇入 Python)
如果都从 Python 左侧进入, 重叠 ❌
```

**铁律 4.2**：**多源汇入同层目标用反向捆扎（§2.5.3）或扇出到不同入口点**

---

**情况 5：跨 2 列相邻层（更长 L 形）**

```
约束: |D - S| == 2 列, |Δy| == 1 层
路径: M S Y_src_bot L S Y_mid L D Y_mid L D Y_dst_top
段数: 3 段
水平段长度 = 2 × 列间距（典型 320px）
```

**Y_mid 选择**（同情况 3）：

**乱风险 5.1**：**水平段穿过中间列的容器**
```
Java (x=160) → 浏览器池 (x=800), 中间列 x=500 有 Python 容器
Y_mid = 220 (业务层 y=180~260) → 水平段 y=220 穿过 Python 容器 ❌
Y_mid = 320 → 水平段 y=320 在 Python 容器下方 60px ✅
```

**铁律 5.1**：**跨 2 列时，Y_mid 必须在中间列容器的 y 范围之外**

**乱风险 5.2**：**长水平段与其他线水平段重叠**
```
Java (x=160) → 浏览器池 (x=800), Y_mid=320
RabbitMQ (x=160) → 浏览器池 (x=800), Y_mid=320 (异步任务线)
→ 两条水平段完全重叠 (x=160~800, y=320) ❌
```

**铁律 5.2**：**避免长水平段（≥ 2 列）与其他线水平段重叠**

**铁律 5.3**：**跨 2 列应考虑用主干（§2.5.2）替代长 L 形**

---

**情况 6：跨列跨层（多段折线 / 必用主干）**

```
约束: |D - S| ≥ 2 列 且 |Δy| ≥ 2 层
```

**乱风险 6.1**：**单条 L 形不够，Y_mid 无法同时满足安全通道**
```
Java (x=160, y=180) → 招聘 (x=880, y=720)
|Δx| = 720px (2.25 列), |Δy| = 540px (3 层)
单一 Y_mid 选 y=450 (数据层 y=370~450) → 水平段 y=450 穿过浏览器池 ❌
```

**铁律 6.1**：**跨列跨层（M ≥ 2 或 N ≥ 2）必须用主干（§2.5.2）**

**主干 + 分支定线公式**：
```
源 → 主干起点: M S Y_src_bot L S Y_trunk_top  (垂直到主干顶部)
主干: M S Y_trunk_top L S Y_branch  (垂直主干, 长)
分支: M S Y_branch L D Y_branch L D Y_dst_top  (水平 + 垂直)

总段数: 5 段
```

**示例**（Java → 招聘平台，用 RabbitMQ 共享层做主干）：
```
Java (x=160, y=180) → 招聘 (x=880, y=720)
主干: x=160 (Java 同列), y=180~720 (跨 3 层)
但这违反"主干在中间"原则, 实际应改用外部系统级主干

正确方案: 拆 2 步
  Step 1: Java → RabbitMQ (情况 1, 垂直直线 x=160)
  Step 2: RabbitMQ → 招聘 (用 Trunk-R x=800, 5 段)
```

#### 2.5.0.2 捆扎场景定线公式

**场景 A：扇出（N 条线从同一源出发到不同目标）**

```
源容器宽度 W, 中心 x=S_center
N 条线, 目标 x 坐标: D_1 < D_2 < ... < D_N
```

**扇出端口位置公式**：
```
第 i 个端口 x_i = S_center - (N-1)/2 × step + (i-1) × step
                = S_center + (i - (N+1)/2) × step
其中 step = 10px
```

**约束**：
```
约束 1: 端口必须在源容器宽度内
  第一个端口 x_1 ≥ S_center - W/2 + 10
  最后一个端口 x_N ≤ S_center + W/2 - 10

约束 2: 端口总数限制
  N ≤ (W - 20) / step + 1
  Java 宽 160px: N ≤ 15 (实际常用 ≤ 6)
```

**示例**（Java 出发 5 条线，center=160, W=160）：
```
N=5, step=10
x_1 = 160 + (1 - 3) × 10 = 140
x_2 = 160 + (2 - 3) × 10 = 150
x_3 = 160 + (3 - 3) × 10 = 160
x_4 = 160 + (4 - 3) × 10 = 170
x_5 = 160 + (5 - 3) × 10 = 180
端口范围: 140~180 (50px), 容器宽 160, 边界 140 ≥ 80+10=90 ✅
```

**每条线路径**（第 i 条线到目标 D_i, Y_mid 在安全通道）：
```
path: M x_i Y_src_bot L x_i Y_mid L D_i Y_mid L D_i Y_dst_top
```

**乱风险**：**5 条线的水平段 y 都相同会重叠**
```
Java 5 条线都 Y_mid=320 → 5 条水平段都 y=320, x=140~880 → 相互重叠 ❌
```

**铁律 A.1**：**扇出 N 条线的 Y_mid 必须递增/递减，间距 ≥ 20px**
```
Y_mid_i = Y_mid_base + (i-1) × 20
例: Y_mid_1=320, Y_mid_2=340, Y_mid_3=360, Y_mid_4=380, Y_mid_5=400
```

**铁律 A.2**：**N > 5 时应改用主干（§2.5.2），不用扇出**

---

**场景 B：反向捆扎（N 条线汇入同一目标）**

```
N 条线, 源: (S_i, Y_i), 目标: (D, Y_target)
所有源必须在同一行/列
```

**共享段位置公式**：
```
共享段起点: (D, Y_shared_start)
共享段终点: (D, Y_target_top)

Y_shared_start = max(源容器底部) + 10px
                = max(Y_i_bot) + 10px

如果源在同一层 (Y_i 相同):
  Y_shared_start = Y_src_bot + 10
```

**每条线路径**（第 i 条线）：
```
差异段: M S_i Y_i_bot L S_i Y_shared_start L D Y_shared_start
共享段: M D Y_shared_start L D Y_target_top
合并: M S_i Y_i_bot L S_i Y_shared_start L D Y_shared_start L D Y_target_top
```

**乱风险 B.1**：**差异段水平段重叠**
```
Java (x=160) → MySQL:  M 160 270 L 160 320 L 160 370  (差异段 0)
Python (x=500) → MySQL:  M 500 270 L 500 320 L 160 320 L 160 370
Agent (x=800) → MySQL:   M 800 270 L 800 320 L 160 320 L 160 370

Python 和 Agent 的水平段都 y=320, x=160~500 / x=160~800 → 重叠 ❌
```

**铁律 B.1**：**反向捆扎 N 条线的水平段 Y_mid 必须递增，间距 ≥ 20px**
```
Y_mid_i = Y_shared_start + (i-1) × 20
但这导致 Y_mid_i 不同, 共享段变成 N 条独立段, 不是捆扎 ❌
```

**真正正确的反向捆扎（共享段 1 段）**：
```
所有线的 Y_shared_start 必须相同, 共享段才成立
→ 水平段必然重叠
→ 解决: 让 N ≤ 2 (Java/Python 各 1 条, 共享段 50px)
       或 N=1 (不需要捆扎)
```

**铁律 B.2**：**反向捆扎只用于 N ≤ 2**（2 条线共享 1 段）

**铁律 B.3**：**N > 2 不用反向捆扎，改为每条线独立路径或合并到主干**

---

**场景 C：主干 + 分支（N 条线从同源/区域汇聚）**

```
源/汇聚点: (S, Y_root)
N 个目标: (D_1, Y_1), ..., (D_N, Y_N)
```

**主干位置公式**：
```
主干 x 坐标: S_trunk = 中位数(D_1, ..., D_N)  (当所有目标同层)
            或 S_trunk = 满足距离均衡比 ≤ 3:1 的位置
```

**分支点 y 公式**：
```
Y_branch_i = Y_branch_base + (i-1) × 20
Y_branch_base = max(Y_root, min(Y_i)) + 10
```

**每条分支路径**：
```
path: M S Y_root L S Y_branch_i L D_i Y_branch_i L D_i Y_i_top
```

**乱风险 C.1**：**分支方向不一致**
```
Trunk x=550, 推送 (x=525 向左), 邮件/支付 (x=715/905 向右)
推送水平段向左, 邮件/支付水平段向右 → 视觉分叉感 ❌
```

**铁律 C.1**：**所有分支方向一致**（全部向左或全部向右）

**铁律 C.2**：**目标分布在 Trunk 两侧时，拆 2 个主干**
```
Trunk-L (x=440) 路由 2 个左侧目标
Trunk-R (x=810) 路由 2 个右侧目标
```

**乱风险 C.2**：**分支水平段重叠**
```
LLM 水平段 y=620, x=440~335
邮件 水平段 y=620, x=440~715
→ LLM 水平段 (440~335, 100px) 与邮件水平段 (440~715, 270px) 在 x=335~440 区间重叠 ❌
```

**铁律 C.3**：**同一主干的所有分支水平段 Y 必须递增，间距 ≥ 20px**
```
Y_branch_1 = 680
Y_branch_2 = 700
Y_branch_3 = 720
Y_branch_4 = 740
```

**乱风险 C.3**：**分支点 y 错位**
```
分支点 y=680, 700, 720, 740 (10px 步进) → 10px 间距是最低, 但 20px 更安全
```

**铁律 C.4**：**分支点 y 间距 ≥ 20px**（10px 是最低，违反 §2.3.2 风险）

#### 2.5.1 扇出（Fan-Out）规则

**定义**：当同一源容器出发 N 条线时，将各出口端口沿源容器边缘**按 10px 等距分布**，避免多条线从同一端口出发造成视觉重叠。

**前置条件**：必须先满足 §2.5.0 节点层级。**如果源和目标在同一列，应优先走垂直直线，不要用扇出**。

**标准**：

| 参数 | 标准值 | 说明 |
|------|--------|------|
| 端口间距 | 10px | 相邻出口端口的水平或垂直距离 |
| 端口分布方向 | 沿源容器边缘（左侧/右侧/顶部/底部） | 与线的主方向垂直 |
| 端口顺序 | 按目标容器 x 坐标从左到右排列 | 视觉对称、便于阅读 |
| 端口边界 | 第一个端口 ≥ 源容器边缘 10px | 避免端口紧贴容器边框 |
| 最大扇出数 | ≤ 6 条 | 超过应拆分层级或合并目标 |

**应用判断**：

| 场景 | 是否用扇出 | 替代方案 |
|------|----------|----------|
| 源和目标在同一列 | ❌ 不用 | 垂直直线 |
| 源和目标在不同列但同层 | ✅ 用 | 短水平段，端口沿顶部/底部边缘 |
| 源出发 6+ 条线到不同层 | ⚠️ 慎用 | 重新设计层级（§2.5.0），用主干（§2.5.2） |

**示例（Java 出发 2 条线到不同列，center=160）**：

```
源容器底部（y=250）出口端口分布：

  x=160 → Line A (MySQL, 直下 x=160)
  x=180 → Line B (Redis, 跨列 x=500)

仅 2 条线时，端口间距 20px，扇出有限，不需总线束
```

**反例（违反 §2.5.0 优先用节点层级）**：

```
源容器底部出发 6 条线，端口 x=160/170/180/190/200/210（50px 宽）

问题：6 条线垂直段紧贴在一起（50px 宽内），
     水平段必然长距离跨越到不同列目标
     → 必然要总线束补救 → 线条混乱
     
正解：先重新设计节点层级，让目标和源同列
     → 同列垂直直线，无总线束
```

#### 2.5.2 主干（Trunk）规则

**定义**：当 3 条或以上的线汇聚到同一区域时，必须先合并到一条**主干（trunk）**，再从主干分支出去，避免多条平行线直接进入目标区造成视觉混乱。

**前置条件**：必须先满足 §2.5.0 节点层级。**如果可以通过列对齐避免汇聚，优先用列对齐**。

**标准**：

| 参数 | 标准值 | 说明 |
|------|--------|------|
| 触发条件 | ≥ 3 条线汇聚到同一区域 | 区域指 y 跨度 ≥ 40px 的连续空间 |
| 主干位置 | 所有目标中心 x 的中位数 | 主干与各目标的水平距离尽量均匀 |
| 主干方向 | 垂直（当目标在源下方）或水平（当目标在源右侧） | 与分支方向垂直 |
| 主干线宽 | 1.5px（与普通线同） | 不加粗，靠位置识别 |
| 主干颜色 | `#666666`（与普通线同） | 不变色，靠结构识别 |
| 分支点 | 主干上的 (x主干, y分支) | 分支点 y 值按目标 x 排序递增或递减 |
| **距离均衡比** | **最大距离 / 最小距离 ≤ 3:1** | **修正：之前文档允许 14:1 是错误的** |

**示例（4 个外部系统路由，正确的主干位置）**：

```
外部系统中心: LLM=160, 推送=340, 邮件=520, 支付=700

主干位置选择:
  选项 A: Trunk x=430 (中位数)
    - LLM 距离 270, 推送 90, 邮件 90, 支付 270
    - 最大/最小 = 270/90 = 3:1 ✅ 通过
    - 推荐
    
  选项 B: Trunk x=340 (首末中点)
    - LLM 距离 180, 推送 0, 邮件 180, 支付 360
    - 最大/最小 = 360/0 → 推送在主干上 ✅
    
  选项 C: Trunk x=550 (中位数偏右)
    - LLM 距离 390, 推送 210, 邮件 30, 支付 150
    - 最大/最小 = 390/30 = 13:1 ❌ 违反 3:1
```

**分支点分布**（y 递增，与目标 x 排序一致）：

```
  y=680 → LLM (中心 x=160，最左)
  y=700 → 推送 (中心 x=340)
  y=720 → 邮件 (中心 x=520)
  y=740 → 支付 (中心 x=700，最右)
  
  分支点间距: 20px（满足 10px 网格 + 留白）
  分支方向: 全部向右（方向一致，避免交叉）
```

**反例（违反 3:1 距离均衡比）**：

```
Trunk x=550，4 个目标中心: LLM=335, 推送=525, 邮件=715, 支付=905
距离: 215/25/165/355, 最大/最小 = 14:1 ❌ 极端不平衡
正解: 主干应选 x=620 (中位数)，距离 285/95/95/285 = 3:1
```

#### 2.5.3 捆扎分类（Bundling Classification）规则

**核心区分**：

| 类别 | 场景 | 共享方向 | 典型例子 |
|------|------|----------|----------|
| **正向捆扎**（Forward Bundling）| **1 源 → N 目标** | N 条线从源出发，**共享走线段**（水平段）| 用户→Java/Python/Agent（1 源 3 目标）|
| **反向捆扎**（Reverse Bundling）| **N 源 → 1 目标** | N 条线**共享进入目标**（垂直段）| Java→Redis + Python→Redis（2 源 1 目标）|

**两种捆扎不是同一概念，应用场景完全不同**。

---

##### 2.5.3.1 正向捆扎（1 源 → N 目标）

**定义**：当 1 个源容器连接 N 个目标容器时，N 条线**从源出发后共享一段水平走线**，然后在每个目标 x 位置分叉下走。

**典型路径**（用户→Java/Python/Agent）：

```
源中心 x=600
  ├─ 用户→Java:    M 600 80 L 600 130 L 200 130 L 200 180
  ├─ 用户→Python:  M 600 80 L 600 180  (垂直直线, 因为 Python 在中心)
  └─ 用户→Agent:   M 600 80 L 600 130 L 1000 130 L 1000 180

共享水平段: (200, 130) → (1000, 130) 长度 800px
3 条线在此水平段上
```

**标注规则**：
- 标签放**水平段上方**（y=125），不压线
- 每条线独立标注协议
- 源端 3 个端口紧贴（4px 步进）

**判断规则**：
- **1 个源 + N 个目标** = 正向捆扎
- 适合**多目标但目标分布广**的场景

---

##### 2.5.3.2 反向捆扎（N 源 → 1 目标）

**定义**：当 N 个源容器连接 1 个目标容器时，N 条线**共享进入目标的一段垂直线**，在进入目标之前分叉。

**典型路径**（Java→Redis + Python→Redis）：

```
源 1 Java 中心 x=200, 源 2 Python 中心 x=600, 目标 Redis 中心 x=600
  ├─ Java→Redis:    M 200 260 L 200 290 L 500 290 L 500 370
  └─ Python→Redis:  M 600 260 L 500 260 L 500 370

共享段: (500, 260) → (500, 370) 垂直段 110px
```

**前置条件**：**只有当多源共享同一目标是不可避免的业务关系时才使用**。如果可以重新设计节点层级让共享目标独占一列，应优先用列对齐。

**标准**：

| 参数 | 标准值 | 说明 |
|------|--------|------|
| 共享条件 | 两条线终点相同 | 目标容器 B 相同 |
| 共享线段 | 从最早进入源的位置到最晚进入目标的位置 | 共享段必须对两端可见 |
| 共享方向 | 同向（两条线都从外侧进入目标） | 异向时不允许共享 |
| 视觉区分 | 共享线段上每条线单独标注协议 | 不靠位置区分，靠标签 |
| 共享段数 | ≤ 1 段 | 共享段过长应拆分 |
| N 上限 | N ≤ 2 | N > 2 不用反向捆扎 |

**示例（Java 和 Python 都连 Redis）**：

```
正确用法:
  Line 6 (Java→Redis):    M 160 260 L 160 290 L 500 290 L 500 370
  Line 8 (Python→Redis):  M 500 260 L 500 290 L 500 370
  共享段: (500, 290) → (500, 370) 垂直段 80px
  共享段数: 1 段 ✅

错误用法:
  Line 6 共享段: (160, 290)→(500, 290)→(500, 370) 水平+垂直 320px+80px
  → 共享段过长，应改为 Java 直接连到 Redis 列（x=500）
```

**标注规则**（共享段上每条线单独标注）：

```
Line 6 标签: x=200, y=286 "Redis :6379"  (在 Java 差异段上)
Line 8 标签: x=520, y=316 "Redis :6379"  (在 Python 差异段上)
垂直共享段不标注（避免重叠）
```

**判断规则**：
- **N 个源 + 1 个目标** = 反向捆扎
- 适合**多源共享同一资源**的场景（如多个服务共享同一数据库）

##### 2.5.3.3 捆扎的线型一致规则 (ST-8)

> 捆扎的主干上**所有线必须同线型**,不允许实线和虚线混捆扎。

| 捆扎类型 | 允许组合 | 禁止 |
|----------|----------|------|
| 正向捆扎 (1 源 → N 目标) | 全部实线 OR 全部虚线 | 实线+虚线混捆 |
| 反向捆扎 (N 源 → 1 目标) | 全部实线 OR 全部虚线 | 实线+虚线混捆 |

**反例（v4.3 错误）**：
```
❌ Java→MySQL (实线) + Python→MySQL (虚线) 共用 y=320 水平段
   → 实线+虚线混捆,违反 ST-8
```

**正例（v4.9 修正）**：
```
✅ Python→Agent (虚线) + Python→MySQL (虚线) 共起点 (690, 220) → 双虚线正向捆扎
   → 同虚线类型,符合 ST-8
```

**ST-9：每个分叉独立标注协议**
- 共享段不标协议（避免重叠）
- 协议标在每个连接的差异段（自分叉点到目标段）
- 同源同目标的反向捆扎,每条线单独标注

**正例**：
```
✅ RabbitMQ→外部系统正向捆扎: 5 个分叉各标 1 个协议 (HTTPS API / SMTP :465 / ...)
✅ Java→Redis + Python→Redis 反向捆扎: 共享段不标,差异段各标 "Redis :6379"
```

#### 2.5.4 总线层（Bus Layer）规则

**定义**：平行但起点不同的线段必须在 y 方向（水平平行线）或 x 方向（垂直平行线）偏移 ≥10px，形成"总线层"。

**前置条件**：**总线层是"补救措施"，不是首选**。如果通过 §2.5.0 节点层级让所有同列连接都是垂直直线，则不需要总线层。

**何时用总线层**：
- 业务层和外部系统层无法同列对齐（如 5 个外部系统位置固定）
- 业务层出发 ≥ 4 条线到不同列的同一层目标
- **应优先评估是否能用主干（§2.5.2）替代**

**标准**：

| 参数 | 标准值 | 说明 |
|------|--------|------|
| 总线层偏移 | 10px | 相邻总线层间距 |
| 总线层最大数 | ≤ 5 层 | 超过应拆分到多张图或用主干 |
| 总线层起点 | 第一个层 y = 源容器底部 y + 10px | 避免层贴源容器 |
| 总线层方向 | 与源容器边缘垂直 | 源在顶部 → 总线层在源下方水平走 |
| 引导线 | 总线层 y 减 10px 处画一条 0.5px 虚线 | 视觉锚定，不与实线重叠 |
| **总线层数 vs 节点层级** | **总线层数 ≤ 节点层数** | 超过说明应该用层级结构 |

**反例（违反 §2.5.0，依赖总线层补救）**：

```
Java 出发 6 条线到 6 个不同列目标
→ 需要 6 个总线层 (y=250, 260, 270, 280, 290, 310)
→ 总线层数 = 6，超过节点层数 2 (业务层+外部系统层)
→ 这说明节点层级设计错误，应重新分层

正解: 把 6 个目标按列对齐到 Java 同列 (x=160)
     → 6 条垂直直线，0 个总线层
```

#### 2.5.5 分支段隔离（Branch Isolation）规则

**定义**：同一主干上分出的水平分支段必须沿 y 方向偏移 ≥10px，且分支段之间**不重叠**（水平跨度不交叉）。

**前置条件**：**分支方向应一致**（全部向右或全部向左），避免反向分支。

**标准**：

| 参数 | 标准值 | 说明 |
|------|--------|------|
| 分支段 y 间距 | ≥ 10px | 满足 10px 网格 |
| 分支段 x 跨度 | 不重叠 | 分支段之间的 x 范围无交集 |
| **分支方向** | **全部一致**（同左或同右） | **修正：之前允许推送向左邮件向右是错误的** |
| 分支段标签 | 在分支段上方 4px 居中 | 避免标签压线 |
| 分支段箭头 | 触达目标容器边界 | 齐平接入 |
| 分支段长度 | ≤ 400px | 超过应考虑拉近主干 |

**正例（分支方向一致 + 不重叠）**：

```
从 Trunk (x=430) 向右分出:

  y=680 → LLM:    M 430 680 L 160 680 (向左分支 270px)
  y=700 → 推送:   M 430 700 L 340 700 (向左分支 90px)
  y=720 → 邮件:   M 430 720 L 520 720 (向右分支 90px)  ← 方向不一致 ❌
  y=740 → 支付:   M 430 740 L 700 740 (向右分支 270px)

问题: 推送向左，邮件向右，方向不一致
正解: 全部向左或全部向右

全部向右（推荐，贴近左→右阅读方向）:
  y=680 → LLM:    M 430 680 L 160 680 ❌ LLM 在 Trunk 左侧，向右也到达不了
  改为: Trunk 移到 x=160，主干在 LLM 同列

  实际方案: 
  - 4 个目标都在 Trunk 右侧 → 主干放最左 (x=160)，全部向右分支
  - 4 个目标都在 Trunk 左侧 → 主干放最右 (x=700)，全部向左分支
  - 目标分布在 Trunk 两侧 → 拆成 2 个主干
```

**反例（方向不一致）**：

```
Trunk x=550, 4 个目标: 推送=525 (左), 邮件=715 (右), 支付=905 (右)
推送向左, 邮件/支付向右

问题: 推送的水平段 (550→525, 25px 向左) 与邮件的水平段 (550→715, 165px 向右)
     虽然方向相反，但视觉上在主干附近有"分叉"感
     
正解: 拆分主干
  主干 A (x=520) 路由推送 (距离 5px)
  主干 B (x=810) 路由邮件 (距离 95px) 和支付 (距离 95px)
```

#### 2.5.5.1 边缘起跳（Edge Take-off）规则 【ST-6】

**问题定义**：跨列 L 形的水平段即使 y 坐标在容器 y 范围**外**，仍可能**擦顶**（tangent）容器。

**根因**：当源/目标容器在 L 形经过的 x 列上，水平段从容器中心 x 经过时，箭头进入容器时会与容器顶部**视觉上相切**，看起来像"擦顶"。

**示例（v3.7 → v3.8 修复）**：

```
v3.7 Java→Redis: M 200 260 L 200 320 L 600 320 L 600 420
  水平段 x=200→600, 在 x=200 (MySQL 中心) 处擦 MySQL 顶部 ❌
  
v3.8 修复:  M 200 260 L 290 260 L 290 320 L 510 320 L 510 420 L 600 420
  水平段 x=290→510, 完全在 MySQL x=120~280 外 ✅
```

**ST-6 边缘起跳标准**：

| 参数 | 标准值 | 说明 |
|------|--------|------|
| 水平段起点 x | ≥ 源容器右边缘 + 10px | 容器外 10px 起跳 |
| 水平段终点 x | ≤ 目标容器左边缘 - 10px | 容器外 10px 终止 |
| 绕行容器 | 水平段不能经过任何中间容器的 x 范围 | 完全避让 |
| 代价 | L 形段数从 3 段增到 4-5 段 | 段数增加是必要的 |

**Java 容器 (x=120~280) 应用 ST-6**：

```
水平段起点 x ≥ 290
水平段终点 x ≤ 510 (Redis 容器左边缘 -10)
```

**Redis 容器 (x=520~680) 应用 ST-6**：

```
水平段起点 x ≥ 300 (MySQL 右边缘 +20)
水平段终点 x ≤ 510 (Redis 左边缘 -10)
```

**反例（v3.7 错误）**：

```
水平段: M 200 320 L 600 320
经过 x=200 (MySQL 中心) → 擦 MySQL 顶部 ❌
```

**正例（v3.8 正确）**：

```
水平段: M 290 320 L 510 320
起点 x=290 (Java/MySQL 右边缘外 10px)
终点 x=510 (Redis 左边缘外 10px)
完全不经过 MySQL x=120~280 ✅
```

**与 ST-1 关系**：
- ST-1 解决 y 方向穿插（水平段 y 不在容器 y 范围内）
- ST-6 解决 x 方向擦顶（水平段 x 不经过中间容器 x 范围）
- ST-1 + ST-6 = 水平段完全绕开所有容器

##### 2.5.5.2 水平段 Y 避让规则 【ST-1】

**定义**：跨列 L 形连接的水平段 y 坐标不能落在任何非源非目标容器的 y 范围内。

| 参数 | 标准值 | 说明 |
|------|--------|------|
| 水平段 y | 不在容器 y=[Y_top, Y_bot] 内 | y < Y_top 或 y > Y_bot |
| 距容器 y 边界 | ≥ 20px | 留出安全余量 |
| 与 ST-6 关系 | ST-6 解决 x 方向, ST-1 解决 y 方向 | 两者配对使用 |

**反例**：
```
❌ 水平段 y=440, 经过 x=300 垂直段, 容器 y=420~500
   → y=440 在容器 y 范围内, 水平段擦容器顶
```

**正例**：
```
✅ 水平段 y=380 (在容器 y=420~500 上方 40px)
✅ 水平段 y=540 (在容器 y=420~500 下方 40px)
```

##### 2.5.5.3 跨列 L 形起跳规则 【ST-7】

**定义**：跨列 L 形连接的水平段起点/终点必须在源/目标容器的 x 范围外,且水平段要"先离开源容器 → 再水平 → 再接近目标"。

| 参数 | 标准值 | 说明 |
|------|--------|------|
| 起点离开源容器 | 水平段起点 x 在源容器 x 范围外 10px | 避免擦源容器边 |
| 终点接近目标容器 | 水平段终点 x 在目标容器 x 范围外 10px | 避免擦目标容器边 |
| 起跳方向 | 优先垂直先于水平 | 减少水平段长度 |
| 垂直段长度 | 30~60px | 太短视觉突兀,太长浪费空间 |

**反例**：
```
❌ 水平段直接擦源容器右侧: M 200 320 L 600 320
   → 起点 x=200 在 Java 中心,擦 Java 右边缘
```

**正例**：
```
✅ 先垂直离开源: M 200 260 L 200 320 L 600 320 L 600 420
   垂直段 60px, 水平段在 y=320 (容器外)
```

#### 2.5.6 拓扑规则优先级（修正后）

**正确的优先级**：先 §2.5.0 节点层级（结构），再 §2.5.1-§2.5.5 拓扑规则（局部补救），最后 §2.3 间距（验证）。

```
1. 【最高】§2.5.0 节点层级（决定一切）
   → 源和目标同列 = 垂直直线
   → 源和目标同行 = 水平直线
   → 跨列不可避免时 = L 形

2. §2.5.1 扇出（节点层级内的端口分布）
   → 同列连接不需要扇出
   → 跨列短水平段需要扇出

3. §2.5.2 主干（≥3 线汇聚）
   → 列对齐后还汇聚的少数情况才用

4. §2.5.3 反向捆扎（共享目标）
   → 业务必然的共享关系才用

5. §2.5.4 总线层（补救措施，不是首选）
   → 节点层级设计错误时才需要

6. §2.5.5 分支段隔离（主干分支）
   → 主干的细节规则

7. §2.3 间距（验证阶段）
   → 检查零穿插零交叉
   → 检查 10px 网格
   → 检查标签间距

8. 10px 网格对齐（全局约束）
```

**核心原则**：§2.5.0-§2.5.5 是"结构设计"（如何让线条自然简洁），§2.3 是"验证"（线条是否合规）。**先设计后验证**。

#### 2.5.7 布线检查清单（修正后）

每张图完成后，逐项检查。**Q0 是最高优先级，必须先过 Q0 再过 Q1-Q7**：

```
□ Q0【最高】源节点和目标节点是否在同一列/行？
       同列 = 垂直直线
       同行 = 水平直线
       跨列不可避免 = L 形（接受）
       跨列可避免但没避免 → ❌ 重新设计节点层级

□ Q1  所有源容器出口是否按扇出规则分布（§2.5.1）？
       前提: Q0 通过，跨列连接无法避免时才用扇出
□ Q2  ≥3 条线汇聚处是否有主干（§2.5.2）？
       距离均衡比 ≤ 3:1
       分支方向一致
□ Q3  多源共享目标是否使用反向捆扎（§2.5.3）？
       共享段 ≤ 1 段
□ Q4  平行线段是否在总线层 y/x 上偏移 ≥10px（§2.5.4）？
       总线层数 ≤ 节点层数
□ Q5  主干分支水平段是否在 y 上隔离且方向一致不重叠（§2.5.5）？
       分支方向全部向左或全部向右
□ Q6  所有途经点是否对齐 10px 网格（§2.3.2）？
□ Q6.1 【ST-6】跨列 L 形水平段 x 起点/终点是否在源/目标容器 x 范围外 10px？
       水平段不能经过任何中间容器的 x 范围（避免擦顶）
□ Q7  引导线是否在总线层偏移 10px 处（§2.5.4）？
□ Q8  标签是否在垂直段外侧（不压线）（ST-4）？
□ Q8.1 【ST-10】垂直线文字是否居左或居右（不居中）？
       居中会被线穿过，必须居左（anchor=end, dx<0）或居右（anchor=start, dx>0）
□ Q8.2 【ST-11】水平线文字是否居中（不被线穿过）？
       水平线文字居中 OK, 垂直线文字禁止居中
□ Q8.3 【ST-12】文字与文字是否互不重叠？
       同一 y 上的多个文字 x 范围不交叉
       不同 y 上的文字 y 范围不交叉
□ Q8.4 【ST-13】文字与所有线是否不交叉？
       文字 bbox 与任何线段 bbox 都不重叠
       不允许文字被线穿过
□ Q9  图例是否只画颜色/线型（不画信息展示文字）（ST-3）？
□ Q10 捆扎段是否没有说明文字（ST-5）？
□ Q11 【ST-8】主干上所有线是否同线型（实线捆实线/虚线捆虚线）？
       实线+虚线不能混捆,共起点或共终点的多线必须同线型
□ Q12 【ST-9】每个分叉是否独立标注协议？
       共享段不标协议（避免重叠），协议标在每个连接的差异段
□ Q12.1 【ST-14】每条线是否只有一个标注（无主+副双标签）？
       实线只标协议,虚线只标动态流向
□ Q12.2 【终点对齐】连接线终点是否在容器外边框（不进入容器内部,不悬空）？
       顶/底进入 → 容器中心 x, 左/右进入 → 容器左/右 x
       终点的最后一段不穿过容器内部
□ Q12.3 【容器内不连线】起点水平段是否在容器外（不擦容器底/顶）？
       起点水平段 y = 容器底 y + 6px (或 顶 y - 6px)
□ Q12.4 【ST-16】标签白底矩形是否遮挡箭头标记？
       矩形右边界 ≤ 箭头尖 x - 8px（白底刚好在箭头外）
       矩形左边界 ≥ 线段起点 x + 8px
```

**关键更新**：
- **新增 Q0 节点层级检查**（最高优先级）
- Q2 距离均衡比修正为 ≤ 3:1
- Q5 分支方向一致修正
- 强调"Q0 通过后才检查 Q1-Q5"

### 2.6 信息密度与空间分配

#### 2.6.1 信息密度与元素比例

**核心原则**：每个元素在图上占据的面积应与其承载的信息量成正比。

| 元素类型 | 信息量评估 | 建议面积占比 | 错误做法 |
|----------|-----------|-------------|----------|
| 主系统框 | 最多（名称 + 内部容器 + 状态 + 技术栈） | 占图总面积的 25-35% | 画成跟外部系统一样大 |
| 参与者 | 中等（名称 + 角色说明 + 频次） | 每个占 5-8% | 画得比系统框还大 |
| 外部系统 | 少（名称 + 简要描述） | 每个占 3-5% | 画得跟主系统一样大 |
| 连接线标注 | 变化大（协议 + 动态信息） | 总计占 10-15% | 标注框超过元素本身 |
| 图例 | 固定（颜色/线型/符号说明） | 占 8-10% | 迷你图例看不清 |
| 留白/空白 | 无信息 | ≥ 15% | 图挤满，没有呼吸空间 |

**最小尺寸约束**：

| 信息量 | 最小矩形尺寸 | 可容纳内容 |
|--------|-------------|-----------|
| 1 行文字 + 背景 | 100×40px | 简单标签 |
| 2-3 行文字 + 背景 | 150×60px | 外部系统 |
| 4-6 行文字 + 标题 + 背景 | 170×80px | 参与者 |
| 7+ 行文字 + 标题 + 技术栈 + 状态 | 350×180px | 主系统框 |

**检查方法**：计算每个元素面积与图总面积的比例，如果外部系统面积 > 主系统面积的 50%，说明比例失调。

#### 2.5.2 空间分配策略（内容驱动）

**核心原则**：空间分配由图的**内容量**决定，而非固定模板。每张图先评估内容，再决定空间分配方案。

**分配流程（作图前执行）**：

```
Step 1: 列出图上所有元素，评估每个元素的内容量（文字行数、字段数、连接线数）
Step 2: 按内容量从大到小排序，确定视觉权重
Step 3: 内容量最大的元素居中，其余元素围绕分布
Step 4: 确认图例位置（底部独立区域，不与主图元素重叠）
Step 5: 确认元数据位置（图底部，图例下方）
Step 6: 检查整体留白是否充足（四边 ≥ 30px，元素间 ≥ 20px）
```

**排版规则**：

| 规则 | 标准 | 违反后果 |
|------|------|----------|
| 主系统居中 | 水平/垂直居中于主图区 | 读者视觉焦点偏移 |
| 参与者左置 | 参与者位于系统左侧 | 交互方向不直观（从左到右） |
| 外部系统右置 | 外部系统位于系统右侧 | 同上 |
| 图例不挤占主图 | 图例在底部独立区域 | 图例挤压主图空间 |
| 连接线标注不压元素 | 标注与最近元素间距 ≥ 20px | 标注遮挡元素内容 |
| 留白不小于 15% | 图四边留白 ≥ 30px | 图显得拥挤、不专业 |

#### 2.5.3 紧凑标注格式

**连接线标注仅保留触发事件信息，禁止展示协议/端口/时限/异常策略等无关信息。** 协议属于 C2 容器图专属标注，时限和异常策略属于时序图。

**触发事件标注格式**：

```
触发:[事件名称]
```

**示例**：

```
触发:用户操作
触发:简历更新事件
触发:定时任务 08:00
触发:投递状态变更
```

**字符数限制**：

| 标注类型 | 最大字符数 | 说明 |
|----------|-----------|------|
| 触发事件 | ≤ 20 字符 | 如 `用户操作`、`定时任务 08:00` |

### 2.6 复杂度上限

| 指标 | 通用上限 | 超标处理 |
|------|----------|----------|
| 元素数 | C1 ≤ 10，C2 ≤ 12，时序 ≤ 8 lifeline，ER ≤ 15 实体，部署 ≤ 10 节点 | 按业务域/场景/环境拆分 |
| 连接线数 | C1 ≤ 15，C2 ≤ 18，时序 ≤ 30，ER ≤ 20，部署 ≤ 15 | 按子系统/阶段分组 |
| 嵌套深度 | 时序 ≤ 3 层 | 提取子流程 |
| 组合片段数 | 时序 ≤ 5 | 简化分支逻辑 |
| 每实体字段数 | ER ≤ 20 | 超出说明实体粒度过粗 |
| 每节点部署单元数 | 部署 ≤ 5 | 超出说明节点粒度过粗 |

### 2.7 图幅选择与内容量关系

**选择合适的 viewBox 尺寸**：

| 信息量 | 建议 viewBox | 适用场景 |
|--------|-------------|---------|
| 简单（3-5 个元素） | 800×500 | 简单 C1，只有 1-2 个外部系统 |
| 中等（5-8 个元素） | 1000×700 | 标准 C1/C2，4 个左右外部系统 |
| 复杂（8-12 个元素） | 1100×850 | 大型 C2，或含图例+元数据的完整图 |

**宽高比**：推荐 3:2 或 4:3，禁止 1:1 正方形或过于狭长的比例。

### 2.9 图类型信息展示清单（通用总表）

**作图前必读**：每张图在绘制前，必须明确该图类型可以展示什么信息、禁止展示什么信息。以下按 C4 模型标准和 UML 2.5 规范定义各图类型的信息展示边界。

| 图类型 | 必须展示（Must Show） | 可选展示（May Show） | 禁止展示（Must Not Show） |
|--------|----------------------|---------------------|--------------------------|
| **C1 系统上下文图** | 待建系统（1个）、外部系统（≤8个）、参与者（≤3个）、关系描述标注（动词短语）、图例、系统边界框 | 技术栈概要（系统内部）、系统名称版本号、PRD 来源引用 | 协议/端口信息（如 `HTTPS:443`、`gRPC:50051`）、内部容器/数据库/组件、类名/接口名、API 路径、非 PRD 角色 |
| **C2 容器图** | 所有容器（名称+技术栈+版本）、通信路径（协议:端口）、数据库（类型+版本）、消息队列（类型+版本）、图例、三层布局 | 外部系统（与 C1 一致）、数据方向（请求/响应）、容器内部状态、部署环境标识 | 类名/接口名/包名、C1 级别的参与者（除边界参与者）、组件内部实现细节、API 具体路径 |
| **UML 时序图** | 生命线（实例名:类名）、同步/异步消息线、返回消息、激活条、组合片段（alt/opt/loop/break）、监护条件、时间约束（NFR 关键路径） | 频次/量级标注（如 `~每日50次`）、数据量标注（如 `~2KB`）、异常策略描述、消息序号 | 类属性/方法签名、部署拓扑信息、数据库表结构、协议:端口标签（属部署图） |
| **ER 图** | 所有实体矩形（名称+全部字段）、PK 标记（下划线）、FK 标记（斜体）、关系线+基数（Crow's Foot）、关系动词 | 字段类型（如 `varchar(255)`）、字段默认值、唯一索引（UQ）、非空约束（NN） | 时序/流程信息、部署拓扑、API 接口、类方法、技术栈版本 |
| **UML 部署图** | 物理/虚拟节点（3D 立方体）、节点内部署单元、通信路径（协议:端口）、部署环境标识（dev/staging/prod）、图例 | 外部系统节点、网络拓扑（防火墙/负载均衡器）、节点规格（CPU/内存） | 业务流程时序、数据实体字段、类接口签名、组件内部细节 |
| **UML 类图** | 类名、属性（可见性+名称+类型）、方法（可见性+名称+参数+返回类型）、关系（泛化/实现/关联/依赖/聚合/组合） | 属性默认值、方法参数默认值、接口定义、模板参数 | 部署拓扑、时序流程、数据实体实例、配置文件 |
| **UML 活动图** | 泳道（参与者/系统）、活动节点、控制流箭头、决策节点（菱形）、开始/结束节点 | 对象流、异常处理、时间事件、中断区域 | 数据库表结构、类属性、部署信息、协议端口 |
| **UML 状态机图** | 状态（圆角矩形）、事件（转换标签）、起始状态（实心圆）、终止状态（牛眼）、复合状态 | 进入/退出动作（entry/exit）、内部活动、延迟事件、历史状态 | 类方法签名、数据表字段、时序消息序列、部署配置 |

### 2.10 信息展示决策流程

**作图前，逐项回答以下问题**：

```
□ Q1  这张图属于哪种类型？（C1/C2/时序/ER/部署/类/活动/状态机）
□ Q2  这种图类型必须展示哪些信息？（对照 §2.9 清单）
□ Q3  计划展示的信息中，是否有属于"禁止展示"类别的？（如有，删除）
□ Q4  计划展示的信息中，是否有属于"可选展示"类别的？（如有，确认保留还是删除）
□ Q5  连接线/关系线上标注的信息，是否与图类型匹配？
□ Q6  "禁止展示"的信息，是否已在其他图类型中正确表达？（如 C1 的协议信息已在 C2 表达）
□ Q7  所有信息的总量是否超过复杂度上限？（如超过，拆分）
```

### 2.11 图类型与信息匹配（红线规则）

**核心原则**：连接线的标注内容由软件工程作图方法论定义（C4 模型、UML 2.5），非主观决定。以下红线规则是评审的一票否决项：

| 红线规则 | 违反后果 | 依据 |
|----------|----------|------|
| C1 连接线未标注关系描述 | 不合格 | C4 模型：每条线必须标注 |
| C1 连接线标注了协议/技术/端口信息 | 不合格 | C1 为纯拓扑关系图，协议信息应在 C2 表达 |
| C1 标注单字如"使用"不够具体 | 建议改进，非强制 | C4 建议避免单字 |
| C2 连接线未标注协议 | 不合格 | C4 模型硬性要求 |
| 动态信息未使用时序图/状态机图表达 | 不合格 | 静态图不承载动态行为 |
| 时序图遗漏异常处理路径（break 片段） | 不合格 | UML 2.5 要求覆盖异常路径 |

### 2.12 复杂图拆分规则

**触发拆分的条件**（满足任意一条即应拆分）：

| 条件 | 阈值 | 示例 |
|------|------|------|
| 连接线数超标 | > 8 条 | C1 图有 10 个外部系统 |
| 单条标注超字数 | > 50 字符 | 动态信息超过 3 个维度 |
| 信息维度冲突 | 静态拓扑 + 动态行为混合后混乱 | 读者分不清"这是拓扑还是时序" |
| 元素数超标 | C1 > 10 个，C2 > 12 个 | 见 §2.6 复杂度上限 |
| 目标受众冲突 | 同一张图有多个不同受众 | 架构师和测试看同一张图 |

**拆分模式**：

| 模式 | 适用场景 | 做法 |
|------|----------|------|
| **拓扑 + 行为** | 动态信息过多 | 图 A：静态拓扑（只画连接和协议）<br>图 B：动态行为（只画触发/数据/时限/异常） |
| **主图 + 参考表** | 标注信息太长 | 主图：用编号引用（① ② ③）<br>参考表：图底部详细说明 |
| **按连接分组** | 连接数过多 | 图 A：用户侧连接（求职者→系统）<br>图 B：外部侧连接（系统→平台/AI/推送） |
| **按环境拆分** | 部署图 | 图 A：dev 环境部署<br>图 B：prod 环境部署 |
| **按阶段拆分** | 演进路线 | 图 A：Phase 1 MVP<br>图 B：Phase 2 完整版 |

**拆分后关联**：拆分后的图必须在元数据中标注"关联图"字段，并在图标题中注明序号（如 `图 C1-a`、`图 C1-b`）。

### 2.13 布局预检清单（作图前必须执行）

```
□ P01  图类型选择：这张图属于哪种类型（C1/C2/时序/ER/部署）？动态信息是否使用了正确的图类型？
□ P02  信息匹配：连接线/关系线上标注的信息类型是否与图类型匹配？（如 C1 只标注关系描述，禁止标注协议/触发条件）
□ P03  元素数量：所有元素是否已列出？数量是否在复杂度上限内？
□ P04  元素大小：每个元素的大小是否与信息量成正比？（主系统 25-35%，外部系统 3-5% 各）
□ P05  元素位置：参与者左置、系统居中、外部系统右置？垂直方向是否均匀分布？
□ P06  元素间距：所有元素之间是否有足够间距？最小间距是否满足标准？
□ P07  文字包围盒：是否已计算所有文字元素的包围盒？是否与相邻元素或文字重叠？
□ P08  文字间距：相邻文字标签间距是否 ≥ 12px（水平）和 ≥ 6px（垂直）？
□ P09  Z 轴顺序：图例、参考表、标注框是否可能遮挡任何主图元素？legend 是否与外部系统重叠？
□ P10  图例位置：图例是否在底部独立区域？图例 y 起始 > 主图最低元素 y 结束 + 20px？
□ P11  连接线路径：所有连接线是否使用正交路由？是否有不必要的折角或交叉？
□ P12  连接线间距：平行线间距是否 ≥ 14px？线与元素边框间距 ≥ 12px？
□ P13  整体留白：图四边留白 ≥ 30px？元素间留白 ≥ 20px？留白总面积 ≥ 15%？
□ P14  宽高比：viewBox 宽高比是否在 3:2 ~ 4:3 之间？
□ P15  图幅选择：viewBox 尺寸是否与内容量匹配？（简单 800×500，中等 1000×700，复杂 1100×850）
```

### 2.14 通用反模式

```
AP01 万能图：一张图试图表达所有信息 → 谁也看不懂
AP02 装饰图：图很漂亮但没有决策价值 → 浪费评审时间
AP03 断层图：C1→C2→C3 跳跃太大 → 缺中间层
AP04 僵尸图：文档修改后图没更新 → 误导读者
AP05 自解释图：图没有文字说明 → 不同人理解不同
AP06 完美图：过度追求视觉完美 → 过犹不及
AP07 孤岛图：图与图之间没有引用关系 → 无法导航
AP08 无源图：图的内容来源不明 → 无法验证
AP09 幸福路径：只画正常流程，没有异常路径 → 线上故障
AP10 无风险标记：设计图没有任何风险/债务标记 → 自欺欺人
```
