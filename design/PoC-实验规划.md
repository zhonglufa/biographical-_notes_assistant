# PoC 实验规划（反封号有效性 + 适配器 DOM 稳定性）

> 文档版本：2026-08-15 · v0.1（草案，待 stakeholder 评审签字后生效）
> 上游依据：LLD v1.2 §10（PoC 验证门，权威定义）、HLD §6.14.3（反封禁策略）/ §6.14.5（适配器热更）、HLD §3.4 / LLD §4.4（单平台降级状态机）、PRD §494 模块 4：平台适配器系统 / §496 适配器接口契约
> 对应任务：#100 PoC 双实验（P1 + P2）

## 1. 实验概览与 Gate 定义

本产品进入全量开发前必须过两道验证闸门，任一不过则回到设计/参数层重审，不进全量编码。两道闸门由 LLD §10 定义，本规划将其细化为可执行的实验方案，并补充环境、指标口径、时间线与决策规则。

| 实验 | 验证的假设 | 未验证的风险 |
|------|-----------|-------------|
| **P1 反封号有效性** | 速率整形 + 行为模拟 + ≤3 实例能在主流平台长期不被风控 | 用户账号被封禁，产品无法成立 |
| **P2 适配器 DOM 稳定性** | SelectorBundle 在平台改版周期内可稳定解析 | 选择器失效导致投递失败且不可及时发现 |

**Gate 出口（LLD §10 原文）**：P1 + P2 均 pass，且 R-09（适配器失效 SLA + 单平台降级）已在本模块收口，方可启动全量编码。任一不过 → 回到设计/参数层，不进全量。

## 2. P1 反封号有效性实验

### 2.1 实验目标与假设

验证 RateShaper（令牌桶匀速放出 + 高斯裁剪抖动 + 退避）与行为模拟（贝塞尔轨迹 + 随机滚动）组合下，单账号连续 14 天真实投递不被平台风控识别 [Hypothesis, 无法事前验证，必须实跑]。

实验回答三个问题：

1. 当前参数（§2.3）在真实平台下验证码触发率是否低于 20%？
2. 是否出现异常限流（非验证码触发的 429 / blocked）？
3. 14 天窗口内账号是否从正常态滑向风控态？

### 2.2 实验环境

| 项 | 规格 | 说明 |
|----|------|------|
| 测试账号 | 低频使用的主流光测账号，每平台 1 个 | 来源限定：用户自备或亲友闲置的本人实名账号（调研结论见 §7.1）；明确排除接码/租号渠道；优先注册 ≥7 天、有少量正常使用记录的账号（对齐 `warmup_factor` 时间窗语义） |
| 运行环境 | 独立虚拟机或专用机器，固定网络出口 | 与日常开发环境隔离；避免频繁切换 IP/设备指纹 [Expert judgment] |
| 浏览器 | Playwright + Chromium（真实可测指纹形态） | 按 HLD §6.14.1 走本地浏览器，不使用 headless 简化形态 |
| 实例数 | ≤3（`max_browser_instances=3`） | 对齐 LLD §9.1 配置 |
| 日志 | 结构化日志落盘，不落明文 Cookie | PII 最小化原则，见 §7 |

### 2.3 实验参数（对齐 LLD §5.1，禁止实验内改参）

| 参数 | 值 | 来源 |
|------|-----|------|
| 投递间隔 | 高斯裁剪 μ=5.5s σ=1.5s，clip 至 [2s, 8s] | LLD §5.1 `jitter_interval()` |
| 行为模拟 | 贝塞尔轨迹鼠标移动 + 随机滚动，动作前随机等待 | LLD §5.1（F-5 落地项） |
| 新号暖机 | `account_age_days < 7` 时速率乘以 0.3 | LLD §5.1 `warmup_factor()` |
| 失败退避 | `min(2^n × 15min, 6h) + jitter`，base=15min, cap=6h | LLD §5.1 `backoff()` |
| 验证码等待 | 超时 30min → 回滚任务，不硬闯 | LLD §9.1 `captcha_timeout` |
| 日投放上限 | 按 PRD §6.2 投放频率/上限执行 | `[To be confirmed — 以 PRD 数值为准]` |
| 账号降速 | 24h 内验证码 ≥3 次 → 该平台降速/暂停 | LLD §5.1 `degrade_if_needed()` |

> 实验期间参数冻结。任何参数修改视为一次失败迭代，重新累计 14 天样本。

### 2.4 执行计划（14 天实跑）

| 阶段 | 时间 | 动作 |
|------|------|------|
| 预热 | D-2 ~ D-1 | 环境搭建、账号登录、Cookie 入库（DeviceVault）、首次冒烟投递 5 条 |
| 常态投递 | D1 ~ D7 | 按日额度正常投递，监控验证码率与限流率；新号按 `warmup_factor` 前 7 天降速 |
| 稳态投递 | D8 ~ D14 | 恢复全速（若账号龄已过 7 天），观察参数在无暖机因子下的表现 |
| 判定期 | D15 | 汇总 14 天样本，对照 §2.6 判据出结论 |

每日投递量按目标岗位池随机抽取，投递时间覆盖工作时段（10:00-11:30 / 14:00-17:00）[Expert judgment]，避免均匀固定节奏被识别为机器行为。

### 2.5 监控指标与采集口径

| 指标 | 口径 | 数据源 |
|------|------|--------|
| 账号状态 | 每日记录 `normal / risk_warn / captcha_hold / banned` | 页面探测 + 人工月度复核 |
| 验证码率 | 验证码触发次数 ÷ 投递次数，按日累计 | CaptchaLoop 事件日志 |
| 限流率 | 429 / blocked / 风控提示 次数 ÷ 请求次数 | 平台响应码 + RateShaper 事件 |
| 退避触发 | 触发退避的次数与层级（n=1..N） | RateShaper 事件日志 |
| 投递成功率 | 成功 submit ÷ 尝试投递 | 投递单状态机事件 |

验证码率按「验证码出现次数 / 当日投递请求数」口径统计；人工识别类验证码（滑块/点选）与短信验证码分开记录，但计算入同一分母 [Expert judgment]。

### 2.6 Pass 判据与决策规则

| 判据 | 阈值 | 判定 |
|------|------|------|
| 封号 | 14 天内 0 次 | 任一平台封号 → FAIL |
| 验证码率 | <20%（14 天累计） | **<20% 为 LLD §10 提议值，需 stakeholder 签字确认后才生效（F-13）**；达到即 PASS，未达到进入复测 |
| 异常限流 | 无风控信号（非验证码触发的 429/blocked） | 出现 → 记录上下文，按失败处置 |
| 账号状态 | 14 天终态必须为 `normal`（或 captcha_hold 但未升级） | 终态 `banned` / `risk_warn` → FAIL |

**决策规则**：

- FAIL → 依据限流/验证码上下文调参（间隔分布、暖机因子、日额度），重跑 14 天；累计 2 轮失败 → 回到设计层重审反封禁模型（LLD §10 失败处置原文）。
- PASS → 进入 Gate 汇总，与 P2 结果合并判定。

### 2.7 风险与应急预案

| 风险 | 概率 | 影响 | 预案 |
|------|------|------|------|
| 测试账号被永久封禁 | 中 | 高 | 用低频闲置账号；封禁即终止该平台实验并记录信号，不申诉、不硬闯 |
| 投递任务引发误投 | 低 | 中 | 仅用测试账号 + 低活跃岗位池；投递即撤回需人工，实验账号不用于真实求职 [Expert judgment] |
| 实验污染日常网络 | 低 | 低 | 独立虚拟机，与开发/办公网络隔离 |
| 平台临时风控升级 | 中 | 低 | 单平台降级（LLD §4.4），不干扰其他平台实验 |

## 3. P2 适配器 DOM 稳定性实验

### 3.1 实验目标与假设

验证 SelectorBundle 在平台改版周期内可稳定解析 [Hypothesis]。通过录制真实页面 DOM 快照建立回放 fixture，每周回放校验选择器命中率，模拟「平台改版后是否仍能解析」这一连续性问题。

### 3.2 fixture 录制方案（3 平台 × 5 页面）

平台范围取投递主链路 3 家：**BOSS直聘 / 猎聘 / 智联招聘**（对应 PRD §494 适配器首期范围，其余 2 家平台在 P2 后覆盖 [Expert judgment]）。

关键页面按投递业务流程选取 5 类（推导自 LLD §3.1 时序：navigate → fill_form → submit → detect_captcha）：

| # | 页面 | 覆盖动作 | 代表性 SelectorBundle 项 |
|---|------|----------|--------------------------|
| 1 | 登录态首页/工作台 | 登录态探测 | 账号入口、工作台容器 |
| 2 | 职位搜索页（含筛选） | 搜索 + 筛选 | 搜索框、筛选面板 |
| 3 | 职位列表页 | 列表解析 | 职位卡片、下一页 |
| 4 | 职位详情页 | 详情读取 | 职位标题、投递按钮 |
| 5 | 投递确认（弹窗/表单） | 投递动作 | 投递按钮、确认弹窗、验证码容器 |

**录制规则**：

- 每平台每页录制 ≥3 份独立 DOM 快照（不同会话/不同关键词），避免单次快照偶然性 [Expert judgment]。
- 快照同时记录：URL、响应时间、平台版本特征（页面 meta/指纹 DOM）、录制时间戳。
- fixture 存版本化目录，与 SelectorBundle 版本一一对应；Bundle 修订后重录基线。

### 3.3 回放校验机制

| 项 | 规则 |
|----|------|
| 频率 | 每周 1 次，固定于周五（平台改版通常在工作日灰度）[Expert judgment] |
| 方式 | 离线回放：将 fixture DOM 注入解析器，运行每个 `SelectorBundle.match(name, dom)`，统计命中/未命中 |
| 样本 | 全量 fixture（当前基线的全部快照）+ 当周新增快照 |
| 输出 | 每平台每页面命中率 + 未命中选择器明细（含 DOM 上下文） |

**与 R-09 的衔接**：回放发现命中率低于阈值时，`detect_selector_miss()` 须在 ≤60s 内判定并标 `pending_fix`（LLD §3.3 失效检测 SLA）；该平台立即进入单平台降级，其余平台不受影响。

### 3.4 指标与 Pass 判据

| 指标 | 阈值 | 判定 |
|------|------|------|
| 选择器命中率 | ≥95%（连续 2 周） | 连续 2 周达标 → PASS |
| 失效检测 SLA | 判定 ≤60s | 回放校验中抽样计时 |
| 单平台降级 | `pending_fix → fixed \| retired` 状态机闭环 | 有降级事件时须观测闭环 |

P2 至少运行 2 周（满足「连续 2 周」语义），与 P1 的 14 天窗口并行安排，Gate 判定取两者中较晚者。

### 3.5 失败处置与升级路径

| 情形 | 处置 |
|------|------|
| 单平台命中率 <95% | 触发 Bundle 修订 + 灰度热更（LLD §2.2 `hot_update(gray_pct)`），修订后重录基线再回放 |
| 命中率 <95% 连续 2 周 | 升级 R-09 为阻断（LLD §3.3），告警 + 人工介入，暂停该平台投递 |
| 平台废弃/结构性改版 | 按 LLD §4.4 `pending_fix → retired`，退出该平台投递并登记 |

- 实验日志落本地 SQLite（LLD §2.2 LocalStore 最小集）：任务事件、验证码事件、退避事件、selector miss 事件。

- 测试账号 Cookie 存 DeviceVault 派生密钥加密，明文仅驻 worker 内存（LLD §3.4）。
- 所有行为限定在隔离虚拟机；实验期间账号不参与真实投递结果（不追求真实 offer）。
- 超出本实验范围的操作（申诉、刷量、绕过验证码）一律禁止。

### 7.1 测试账号来源调研备忘

调研时间 2026-08-15，三路证据综合如下。

**平台注册与实名要求**：求职端注册 = 手机号 + 短信验证码；实名认证（身份证 + 人脸）为账号安全增强项（BOSS直聘官方指引），平台依《网络安全法》第 24 条有权核验真实身份，智联招聘隐私政策同样要求手机号验证。口径统一为「本人实名手机号注册」。

**平台风控基线**：BOSS直聘 2026 年 3 月封禁虚假引流账号 1.3 万个、约 90% 由 AI 风控在举报前主动拦截，黑灰产账号存活周期已缩至小时级；2025 全年封禁账号中 80% 由 AI 主动拦截。风控在注册阶段即比对黑灰产库，号段或设备指纹命中即冻结。

**渠道评估结论**：

| 渠道 | 合规性 | 风控基线 | 对 P1 的适配度 | 结论 |
|------|--------|----------|----------------|------|
| 自备闲置实名账号 | 合法（本人名下） | 正常 | 高：结果可代表真实用户 | 推荐 |
| 亲友闲置实名账号 | 合法（需本人知情同意） | 正常 | 高，账号有被封风险 | 备选 |
| 虚拟运营商新号段 | 合法但号段常被风控标记 | 偏高 | 低：注册即高风险，新号需暖机 | 不推荐 |
| 接码平台/黑卡/租号 | 违法（非本人实名，涉黑灰产） | 极差：已被风控库标记 | 低：实验失真，无法代表真实用户 | 明确排除 |

排除接码渠道的两条硬理由。一是法律层面：虚拟号与实卡均来自黑灰产链条，使用非本人实名手机号注册违反实名要求，并可能触及侵犯公民个人信息相关法规。二是技术层面：号段已被平台 AI 风控前置标记，账号往往一注册即冻结，以此为实验对象得出的验证码率与封禁结论不具代表性，与 P1「验证真实用户场景下反封号有效性」的命题直接冲突。

**落地动作**：请将军提供或指定每平台 1 个闲置实名账号（注册 ≥7 天、无近期高频投递记录），登记至 §2.2 后 P1 可启动。
