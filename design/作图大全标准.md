# 软件设计作图大全标准 v1.4

> 本文件是软件团队所有设计图的作图交付标准与使用规范，按 **作图交付标准（概述）→ 作图基本要求（通用规范）→ 不同类型作图的交付标准（各图类型独立节）→ 附录** 四层结构组织，可直接用于评审。

---

## 1. 作图交付标准（概述）

### 1.1 适用范围

本标准适用于软件工程全生命周期中所有设计图的绘制与交付，覆盖产品工程、需求分析、概要设计、详细设计、接口设计、部署运维六个阶段。所有设计图必须遵循本标准的通用规范及其对应图类型的交付标准，方可进入评审流程。

### 1.2 涵盖图类型

本标准覆盖软件工程全生命周期所有设计图，从方法论来源分为以下体系：

| 方法论 | 体系 | 图类型 | 当前标准状态 |
|--------|------|--------|-------------|
| **C4 模型** | 架构可视化 | C1 系统上下文图、C2 容器图、C3 组件图、C4 代码图 | 已有 C1-C2 标准 |
| **UML 2.5 结构图** | 静态结构 | 类图、组件图、部署图、对象图、包图、组合结构图、画像图 | 已有类图/部署图标准 |
| **UML 2.5 行为图** | 动态行为 | 用例图、活动图、状态机图、时序图、通信图、时序图（Timing）、交互概览图 | 已有时序图/活动图/状态机图标准 |
| **数据建模** | 数据关系 | ER 图（Crow's Foot） | 已有标准 |
| **产品工程** | 需求与体验 | 用户旅程图、业务流程图（BPMN 2.0）、线框图、用户故事地图 | 附录 A 提及，标准待补充 |
| **接口与部署** | 契约与运维 | API 契约图（OpenAPI）、数据流图（DFD）、网络拓扑图、架构演进图 | 附录 A 提及，标准待补充 |

> 当前已建立完整交付标准的图类型（§3 各节）共 **8 种**：C1、C2、时序图、ER 图、部署图、类图、活动图、状态机图。其余图类型的标准将在后续版本逐步补充。全生命周期 16+ 种图类型清单见附录 A。

### 1.3 方法论来源

| 方法论 | 版本/标准 | 核心依据 |
|--------|----------|----------|
| C4 模型 | Simon Brown, c4model.com | 系统上下文 → 容器 → 组件 → 代码（逐层抽象） |
| UML 2.5 | OMG 规范, ISO/IEC 19505-2 | 13 种图类型的语法和语义标准 |
| Crow's Foot | Peter Chen, IDEF1X | 实体关系图的基数符号标准 |
| WCAG 2.1 | W3C 无障碍标准 | 颜色对比度 ≥ 4.5:1，色盲安全 |

### 1.4 21 个通用维度

所有图类型均从以下 21 个维度进行评审，每个维度均有明确的验收方式：

| # | 维度 | 定义 | 验收方式 |
|---|------|------|----------|
| 1 | **决策目标** | 图支持什么设计决策、谁读、为什么读 | 问"这张图解决什么决策问题" |
| 2 | **C4 层级纪律** | 是否遵守单一抽象层级，不越级 | 检查图中元素是否属于该层级 |
| 3 | **UML 语法合规** | 线型、箭头、片段是否符合 UML 2.5 | 逐项对照规范表 |
| 4 | **元素完备性** | 是否包含该层级所有必要元素 | 对照 PRD + 文档列表 |
| 5 | **线条与间距** | 线宽、平行线间距、标签偏移、折角、交叉 | 数值测量 |
| 6 | **颜色系统** | 色板固定、语义不二义、对比度、色盲安全 | 提取 fill/stroke 值核对 |
| 7 | **字体层级** | 字号、字重、对齐、字体回退链 | 检查所有 `<text>` 元素 |
| 8 | **复杂度上限** | 元素数/连接数是否超标 | 计数检查 |
| 9 | **元数据与溯源** | 作者、日期、版本、来源、审查状态、关联图 | 检查 `<desc>` 或图底部文字 |
| 10 | **跨图一致性** | 与其他图是否有矛盾（名称/接口/实体/参与者） | 交叉对比 |
| 11 | **决策可追溯** | 图中元素是否能追溯到 ADR 或 PRD 条款 | 随机抽样 5 个元素 |
| 12 | **4+1 视图覆盖** | 逻辑视图、进程视图、开发视图、物理视图、场景视图 | 检查是否覆盖 HLD 阶段必需的视图 |
| 13 | **审查治理** | 自审/同行审查/架构评审/基线审批各阶段通过标准 | 检查审查记录 |
| 14 | **自动化验证** | 线宽/间距/颜色/字数/元数据可自动检查 | 运行 SVG 检查脚本 |
| 15 | **风险与技术债务** | ⚠️ RISK、🏗️ TBD、💳 DEBT、🔄 MIGRATE、🔒 SEC 标记 | 检查图中是否有标记 |
| 16 | **时间维度与演进** | 分阶段交付的图是否区分 Phase 1/2/Future | 检查多阶段项目 |
| 17 | **利益相关方定制** | 目标受众是否明确，信息密度是否匹配 | 检查元数据中的 audience |
| 18 | **多语言与国际** | 中文/英文/双语场景下的命名一致性 | 检查同一概念是否混用 |
| 19 | **工具链与源文件** | SVG 交付、源文件保留、命名规范、目录结构 | 检查文件系统 |
| 20 | **生命周期状态** | DRAFT/REVIEW/APPROVED/DEPRECATED 标记正确 | 检查状态标记 |
| 21 | **布局与可读性** | 正交路由、元素间距、留白、图例完整性 | 视觉检查 |

### 1.5 版本与维护

## 2. 作图基本要求（通用规范）

> 本章定义所有图类型通用的作图规范，适用于本标准涵盖的全部图类型。每张图在绘制前须先过本章通用规范，再过对应图类型的专用规范。

| 颜色 | 色值 | 语义 | 用途 |
|------|------|------|------|
| 蓝 | `#1A73E8` | 系统/容器/业务层 | fill |
| 绿 | `#22C55E` | 数据库/数据层 | fill |
| 红 | `#EF4444` | 消息队列/时间约束/风险 | fill/stroke |
| 琥珀 | `#E8A317` | 参与者 | fill |
| 黄 | `#F59E0B` | 基础设施层 | fill |
| 灰 | `#9CA3AF` | 外部系统 | fill |
| 深灰 | `#333333` | 文字/系统边界框 | fill/stroke |
| 中灰 | `#666666` | 连接线/次要文字 | stroke/fill |
| 浅灰 | `#F8F9FA` | 图例背景/层背景 | fill |
| 浅蓝 | `#DBEAFE` | 激活条填充 | fill |
| 白 | `#FFFFFF` | 背景/实体字段区 | fill |

#### 2.1.2 颜色使用规则

| 规则 | 标准 | 违反后果 |
|------|------|----------|
| 色板合规 | 所有颜色必须来自色板，禁止使用非色板颜色 | 不合格 |
| 语义唯一 | 一个颜色在全文档中只有一种语义 | 读者混淆 |
| 对比度 | 所有文字与背景对比度 ≥ 4.5:1（WCAG AA） | 可读性不合格 |
| 色盲安全 | 红绿不作为唯一区分手段，配合线型或标签 | 无障碍不合格 |

### 2.3 线条与间距通用规范

#### 2.3.1 基本线条参数

| 参数 | 标准值 | 检查方法 |
|------|--------|----------|
| 线宽 — 普通线 | 1.5px | 提取 `stroke-width` |
| 线宽 — 强调线/边界框 | 2.5px | 提取 `stroke-width` |
| 线宽 — 虚线 | 1.5px | 提取 `stroke-width` |
| 箭头大小 | 宽 8px × 高 6px | 箭头路径尺寸 |
| 虚线间距 — 实段 | 6px | `stroke-dasharray` 第一值 |
| 虚线间距 — 空段 | 4px | `stroke-dasharray` 第二值 |

#### 2.3.2 间距标准

##### 形与形之间间隔（核心规范）

**核心原则**：两个图形元素（矩形、圆形、菱形、路径等）之间必须有明确的最小间距，禁止紧贴或重叠。此规范适用于图上所有元素，按元素类型细分为：

| 间距类型 | 标准值 | 检查方法 | 违反后果 |
|----------|--------|----------|----------|
| **矩形与矩形**（水平相邻） | ≥ 30px | 两个 rect 的最近水平距离 | 元素紧贴/重叠 → 不合格 |
| **矩形与矩形**（垂直相邻） | ≥ 20px | 两个 rect 的最近垂直距离 | 元素紧贴/重叠 → 不合格 |
| **矩形与圆/椭圆** | ≥ 20px | rect 边框与 circle 边框的最近距离 | 元素紧贴 → 不合格 |
| **矩形与菱形（决策节点）** | ≥ 25px | rect 边框与 polygon 边框的最近距离 | 决策节点紧贴其他元素 → 不合格 |
| **圆与圆** | ≥ 20px | 两个 circle 边框的最近距离 | 圆元素重叠 → 不合格 |
| **元素与图例** | ≥ 20px | 元素底部与图例顶部垂直距离 | 图例遮挡主图元素 → 不合格 |
| **元素与主图边框** | ≥ 30px | 元素边框与图 viewBox 边界的距离 | 元素紧贴图边缘 → 不合格 |
| **泳道/分区边界** | ≥ 10px | 泳道内元素与泳道边界的间距 | 元素紧贴分区线 → 不合格 |
| **嵌套元素（容器内元素）** | ≥ 12px | 子元素与父容器内边框的间距 | 子元素紧贴/超出父容器 → 不合格 |
| **分组框与内部元素** | ≥ 15px | 分组框边框与组内元素边框的间距 | 分组框紧贴组内元素 → 不合格 |

##### 线与线间距

| 间距类型 | 标准值 | 违反后果 |
|----------|--------|----------|
| 平行线间距 | ≥ 14px | 线交叉/混淆 → 不合格 |
| 线与元素边框间距 | ≥ 12px | 线紧贴元素 → 不合格 |
| 标签偏移（线上方） | 线上方 4px，距线 ≥ 2px | 线穿过标签 → 不合格 |
| 标签两侧留白 | ≥ 6px | 文字被线穿过 → 不合格 |
| 正交折角 | 直角（0px）或圆角（5px，统一） | 斜线 → 不合格 |
| 线端接入 | 齐平（0px 间隙） | 线端不齐 → 不合格 |
| 分支线夹角 | 90° T 型分叉 | Y 型/斜向分叉 → 不合格 |
| 线交叉 | **零容忍** | 任何两条线交叉 → 不合格 |

#### 2.3.3 标注与线间距规范

**核心原则**：标注框（含文字标签）与连接线之间必须有明确间距，禁止线穿过标注框。

| 参数 | 标准值 | 检查方法 | 违反后果 |
|------|--------|----------|----------|
| 标签底部与线间距 | ≥ 2px | 标签框底部 y 坐标与线的 y 坐标差值 | 线穿过标签框 → 不合格 |
| 标签顶部与上方元素间距 | ≥ 10px | 标签框顶部与上方最近元素底部的距离 | 标签与上方元素重叠 → 不合格 |
| 标签偏移方向 | 线上方（水平线），线左侧（竖直线） | 检查标签中心是否在线的对应侧 | 标签位置错误 → 不合格 |
| 标签框与线平行 | 标签框底部平行于线 | 标签框矩形边与线段的夹角 | 标签歪斜 → 不合格 |
| 折线处标签位置 | 在水平段上方，非折角处 | 标签 x 坐标在折线水平段范围内 | 标签在折角处 → 建议移至水平段中央 |

**SVG 实现检查**：

```
标签 rect 的底部 y 坐标 ≤ 线 y 坐标 - 2px    ✓ 标签在线之上，有间距
标签 rect 的底部 y 坐标 > 线 y 坐标           ✗ 线穿过标签框，不合格
```

### 2.4 文字间距与防重叠规范

#### 2.4.1 重叠判定标准

| 判定项 | 标准 | 说明 |
|--------|------|------|
| 重叠判定 | 两个文字元素的外包围盒（bounding box）存在交集 → 判定为重叠 | 零容忍，任何重叠即不合格 |
| 文字包围盒宽度 | 中文：字符数 × 字号 × 0.6；英文：字符数 × 字号 × 0.5 | 用于计算文字占据的实际空间 |
| 文字包围盒高度 | 字号 × 1.4 | 含上下留白 |

#### 2.4.2 最小间距标准

| 间距类型 | 标准值 | 检测方法 |
|----------|--------|----------|
| 文字与最近元素边框间距 | ≥ 10px | 计算文字包围盒与元素 rect 的最近距离 |
| 相邻文字标签水平间距 | ≥ 12px | 两个标签包围盒的最近水平距离 |
| 相邻文字标签垂直间距 | ≥ 6px | 两个标签包围盒的最近垂直距离 |
| 连接线标签与线交叉点间距 | ≥ 15px | 标签包围盒与线交叉点坐标的距离 |
| 标签与元素边框间距 | ≥ 10px | 标签包围盒距最近元素 rect 的距离 |
| 多行文字行间距 | 字号 × 0.8 | 前一行文字底部与后一行文字顶部的距离 |
| 图例与主图元素间距 | ≥ 20px | 图例 rect 顶部与主图最低元素底部的垂直距离 |

#### 2.4.3 防重叠预处理流程（作图前必须执行）

```
Step 1: 列出图上所有文字元素，计算每个元素的包围盒（宽 × 高）
Step 2: 逐一检查任意两个包围盒是否存在交集 → 若存在，判定为重叠
Step 3: 检查所有文字包围盒与元素边框（rect）是否存在交集 → 若存在，判定为压框
Step 4: 调整策略（按优先级）：
  a) 优先增大元素间距（拉开元素之间的距离，使文字有足够空间）
  b) 其次缩短文字内容（精简标签文字，减少包围盒宽度）
  c) 最后调整文字位置（移至线上方/左侧/右侧/内部）
Step 5: 重新检查所有包围盒，直到无重叠、无压框
Step 6: 确认图例位置：图例 y 起始坐标 > 所有主图元素 y 结束坐标 + 20px
```

#### 2.4.4 常见重叠场景及解决方案

| 重叠场景 | 错误表现 | 解决方案 |
|----------|----------|----------|
| 连接线标签与相邻元素边框重叠 | 标签文字超出元素边框 | 增大元素间距，或缩短标签文字 |
| 连接线标签与相邻连接线标签重叠 | 两条线标签交叉 | 增大平行线间距 ≥ 14px |
| 连接线标签与线交叉点重叠 | 标签盖住线交叉点 | 标签偏移至远离交叉点一侧 |
| 图例与主图元素重叠 | 图例遮挡外部系统 | 图例 y 起始 > 主图最低元素 y 结束 + 20px |

### 2.5 信息密度与空间分配

#### 2.5.1 信息密度与元素比例

**核心原则**：每个元素在图上占据的面积应与其承载的信息量成正比。

| 元素类型 | 信息量评估 | 建议面积占比 | 错误做法 |
|----------|-----------|-------------|----------|
| 主系统框 | 最多（名称 + 内部容器 + 状态 + 技术栈） | 占图总面积的 25-35% | 画成跟外部系统一样大 |
| 参与者 | 中等（名称 + 角色说明 + 频次） | 每个占 5-8% | 画得比系统框还大 |
| 外部系统 | 少（名称 + 简要描述） | 每个占 3-5% | 画得跟主系统一样大 |
| 连接线标注 | 变化大（协议 + 动态信息） | 总计占 10-15% | 标注框超过元素本身 |
| 图例 | 固定（颜色/线型/符号说明） | 占 8-10% | 迷你图例看不清 |
| 留白/空白 | 无信息 | ≥ 15% | 图挤满，没有呼吸空间 |

**最小尺寸约束**：

| 信息量 | 最小矩形尺寸 | 可容纳内容 |
|--------|-------------|-----------|
| 1 行文字 + 背景 | 100×40px | 简单标签 |
| 2-3 行文字 + 背景 | 150×60px | 外部系统 |
| 4-6 行文字 + 标题 + 背景 | 170×80px | 参与者 |
| 7+ 行文字 + 标题 + 技术栈 + 状态 | 350×180px | 主系统框 |

**检查方法**：计算每个元素面积与图总面积的比例，如果外部系统面积 > 主系统面积的 50%，说明比例失调。

#### 2.5.2 空间分配策略（内容驱动）

**核心原则**：空间分配由图的**内容量**决定，而非固定模板。每张图先评估内容，再决定空间分配方案。

**分配流程（作图前执行）**：

```
Step 1: 列出图上所有元素，评估每个元素的内容量（文字行数、字段数、连接线数）
Step 2: 按内容量从大到小排序，确定视觉权重
Step 3: 内容量最大的元素居中，其余元素围绕分布
Step 4: 确认图例位置（底部独立区域，不与主图元素重叠）
Step 5: 确认元数据位置（图底部，图例下方）
Step 6: 检查整体留白是否充足（四边 ≥ 30px，元素间 ≥ 20px）
```

**排版规则**：

| 规则 | 标准 | 违反后果 |
|------|------|----------|
| 主系统居中 | 水平/垂直居中于主图区 | 读者视觉焦点偏移 |
| 参与者左置 | 参与者位于系统左侧 | 交互方向不直观（从左到右） |
| 外部系统右置 | 外部系统位于系统右侧 | 同上 |
| 图例不挤占主图 | 图例在底部独立区域 | 图例挤压主图空间 |
| 连接线标注不压元素 | 标注与最近元素间距 ≥ 20px | 标注遮挡元素内容 |
| 留白不小于 15% | 图四边留白 ≥ 30px | 图显得拥挤、不专业 |

#### 2.5.3 紧凑标注格式

**连接线标注仅保留触发事件信息，禁止展示协议/端口/时限/异常策略等无关信息。** 协议属于 C2 容器图专属标注，时限和异常策略属于时序图。

**触发事件标注格式**：

```
触发:[事件名称]
```

**示例**：

```
触发:用户操作
触发:简历更新事件
触发:定时任务 08:00
触发:投递状态变更
```

**字符数限制**：

| 标注类型 | 最大字符数 | 说明 |
|----------|-----------|------|
| 触发事件 | ≤ 20 字符 | 如 `用户操作`、`定时任务 08:00` |

### 2.9 图类型信息展示清单（通用总表）

**作图前必读**：每张图在绘制前，必须明确该图类型可以展示什么信息、禁止展示什么信息。以下按 C4 模型标准和 UML 2.5 规范定义各图类型的信息展示边界。

| 图类型 | 必须展示（Must Show） | 可选展示（May Show） | 禁止展示（Must Not Show） |
|--------|----------------------|---------------------|--------------------------|
| **C1 系统上下文图** | 待建系统（1个）、外部系统（≤8个）、参与者（≤3个）、关系描述标注（动词短语）、图例、系统边界框 | 技术栈概要（系统内部）、系统名称版本号、PRD 来源引用 | 协议/端口信息（如 `HTTPS:443`、`gRPC:50051`）、内部容器/数据库/组件、类名/接口名、API 路径、非 PRD 角色 |
| **C2 容器图** | 所有容器（名称+技术栈+版本）、通信路径（协议:端口）、数据库（类型+版本）、消息队列（类型+版本）、图例、三层布局 | 外部系统（与 C1 一致）、数据方向（请求/响应）、容器内部状态、部署环境标识 | 类名/接口名/包名、C1 级别的参与者（除边界参与者）、组件内部实现细节、API 具体路径 |
| **UML 时序图** | 生命线（实例名:类名）、同步/异步消息线、返回消息、激活条、组合片段（alt/opt/loop/break）、监护条件、时间约束（NFR 关键路径） | 频次/量级标注（如 `~每日50次`）、数据量标注（如 `~2KB`）、异常策略描述、消息序号 | 类属性/方法签名、部署拓扑信息、数据库表结构、协议:端口标签（属部署图） |
| **ER 图** | 所有实体矩形（名称+全部字段）、PK 标记（下划线）、FK 标记（斜体）、关系线+基数（Crow's Foot）、关系动词 | 字段类型（如 `varchar(255)`）、字段默认值、唯一索引（UQ）、非空约束（NN） | 时序/流程信息、部署拓扑、API 接口、类方法、技术栈版本 |
| **UML 部署图** | 物理/虚拟节点（3D 立方体）、节点内部署单元、通信路径（协议:端口）、部署环境标识（dev/staging/prod）、图例 | 外部系统节点、网络拓扑（防火墙/负载均衡器）、节点规格（CPU/内存） | 业务流程时序、数据实体字段、类接口签名、组件内部细节 |
| **UML 类图** | 类名、属性（可见性+名称+类型）、方法（可见性+名称+参数+返回类型）、关系（泛化/实现/关联/依赖/聚合/组合） | 属性默认值、方法参数默认值、接口定义、模板参数 | 部署拓扑、时序流程、数据实体实例、配置文件 |
| **UML 活动图** | 泳道（参与者/系统）、活动节点、控制流箭头、决策节点（菱形）、开始/结束节点 | 对象流、异常处理、时间事件、中断区域 | 数据库表结构、类属性、部署信息、协议端口 |
| **UML 状态机图** | 状态（圆角矩形）、事件（转换标签）、起始状态（实心圆）、终止状态（牛眼）、复合状态 | 进入/退出动作（entry/exit）、内部活动、延迟事件、历史状态 | 类方法签名、数据表字段、时序消息序列、部署配置 |

### 2.10 信息展示决策流程

**作图前，逐项回答以下问题**：

```
□ Q1  这张图属于哪种类型？（C1/C2/时序/ER/部署/类/活动/状态机）
□ Q2  这种图类型必须展示哪些信息？（对照 §2.9 清单）
□ Q3  计划展示的信息中，是否有属于"禁止展示"类别的？（如有，删除）
□ Q4  计划展示的信息中，是否有属于"可选展示"类别的？（如有，确认保留还是删除）
□ Q5  连接线/关系线上标注的信息，是否与图类型匹配？
□ Q6  "禁止展示"的信息，是否已在其他图类型中正确表达？（如 C1 的协议信息已在 C2 表达）
□ Q7  所有信息的总量是否超过复杂度上限？（如超过，拆分）
```

### 2.11 图类型与信息匹配（红线规则）

**核心原则**：连接线的标注内容由软件工程作图方法论定义（C4 模型、UML 2.5），非主观决定。以下红线规则是评审的一票否决项：

| 红线规则 | 违反后果 | 依据 |
|----------|----------|------|
| C1 连接线未标注关系描述 | 不合格 | C4 模型：每条线必须标注 |
| C1 连接线标注了协议/技术/端口信息 | 不合格 | C1 为纯拓扑关系图，协议信息应在 C2 表达 |
| C1 标注单字如"使用"不够具体 | 建议改进，非强制 | C4 建议避免单字 |
| C2 连接线未标注协议 | 不合格 | C4 模型硬性要求 |
| 动态信息未使用时序图/状态机图表达 | 不合格 | 静态图不承载动态行为 |
| 时序图遗漏异常处理路径（break 片段） | 不合格 | UML 2.5 要求覆盖异常路径 |

### 2.12 复杂图拆分规则

**触发拆分的条件**（满足任意一条即应拆分）：

| 条件 | 阈值 | 示例 |
|------|------|------|
| 连接线数超标 | > 8 条 | C1 图有 10 个外部系统 |
| 单条标注超字数 | > 50 字符 | 动态信息超过 3 个维度 |
| 信息维度冲突 | 静态拓扑 + 动态行为混合后混乱 | 读者分不清"这是拓扑还是时序" |
| 元素数超标 | C1 > 10 个，C2 > 12 个 | 见 §2.6 复杂度上限 |
| 目标受众冲突 | 同一张图有多个不同受众 | 架构师和测试看同一张图 |

**拆分模式**：

| 模式 | 适用场景 | 做法 |
|------|----------|------|
| **拓扑 + 行为** | 动态信息过多 | 图 A：静态拓扑（只画连接和协议）<br>图 B：动态行为（只画触发/数据/时限/异常） |
| **主图 + 参考表** | 标注信息太长 | 主图：用编号引用（① ② ③）<br>参考表：图底部详细说明 |
| **按连接分组** | 连接数过多 | 图 A：用户侧连接（求职者→系统）<br>图 B：外部侧连接（系统→平台/AI/推送） |
| **按环境拆分** | 部署图 | 图 A：dev 环境部署<br>图 B：prod 环境部署 |
| **按阶段拆分** | 演进路线 | 图 A：Phase 1 MVP<br>图 B：Phase 2 完整版 |

**拆分后关联**：拆分后的图必须在元数据中标注"关联图"字段，并在图标题中注明序号（如 `图 C1-a`、`图 C1-b`）。

### 2.13 布局预检清单（作图前必须执行）

```
□ P01  图类型选择：这张图属于哪种类型（C1/C2/时序/ER/部署）？动态信息是否使用了正确的图类型？
□ P02  信息匹配：连接线/关系线上标注的信息类型是否与图类型匹配？（如 C1 只标注关系描述，禁止标注协议/触发条件）
□ P03  元素数量：所有元素是否已列出？数量是否在复杂度上限内？
□ P04  元素大小：每个元素的大小是否与信息量成正比？（主系统 25-35%，外部系统 3-5% 各）
□ P05  元素位置：参与者左置、系统居中、外部系统右置？垂直方向是否均匀分布？
□ P06  元素间距：所有元素之间是否有足够间距？最小间距是否满足标准？
□ P07  文字包围盒：是否已计算所有文字元素的包围盒？是否与相邻元素或文字重叠？
□ P08  文字间距：相邻文字标签间距是否 ≥ 12px（水平）和 ≥ 6px（垂直）？
□ P09  Z 轴顺序：图例、参考表、标注框是否可能遮挡任何主图元素？legend 是否与外部系统重叠？
□ P10  图例位置：图例是否在底部独立区域？图例 y 起始 > 主图最低元素 y 结束 + 20px？
□ P11  连接线路径：所有连接线是否使用正交路由？是否有不必要的折角或交叉？
□ P12  连接线间距：平行线间距是否 ≥ 14px？线与元素边框间距 ≥ 12px？
□ P13  整体留白：图四边留白 ≥ 30px？元素间留白 ≥ 20px？留白总面积 ≥ 15%？
□ P14  宽高比：viewBox 宽高比是否在 3:2 ~ 4:3 之间？
□ P15  图幅选择：viewBox 尺寸是否与内容量匹配？（简单 800×500，中等 1000×700，复杂 1100×850）
```

### 2.14 通用反模式

```
AP01 万能图：一张图试图表达所有信息 → 谁也看不懂
AP02 装饰图：图很漂亮但没有决策价值 → 浪费评审时间
AP03 断层图：C1→C2→C3 跳跃太大 → 缺中间层
AP04 僵尸图：文档修改后图没更新 → 误导读者
AP05 自解释图：图没有文字说明 → 不同人理解不同
AP06 完美图：过度追求视觉完美 → 过犹不及
AP07 孤岛图：图与图之间没有引用关系 → 无法导航
AP08 无源图：图的内容来源不明 → 无法验证
AP09 幸福路径：只画正常流程，没有异常路径 → 线上故障
AP10 无风险标记：设计图没有任何风险/债务标记 → 自欺欺人
```

## 3. 不同类型作图的交付标准

### 3.1 C1 系统上下文图

#### 3.1.1 决策目标

| 问题 | 答案 |
|------|------|
| 支持什么决策 | 系统边界在哪？依赖哪些外部系统？谁与系统交互？ |
| 谁读 | 产品经理、业务方、架构师、新成员 onboarding |
| 决策后果 | 边界画错了 → 后续所有设计都会错 |

#### 3.1.2 C4 层级纪律

- **只允许出现**：待建系统（1个）、外部系统（最多 8 个）、参与者（最多 3 个）
- **禁止出现**：任何内部容器、数据库、组件、类名
- **边界框**：待建系统内部不可出现任何子元素
- 违反 = 不合格，直接打回

#### 3.1.3 元素完备性

| 元素 | 必须 | 说明 |
|------|------|------|
| 待建系统 | ✅ | 居中，名称 = `[系统名]` |
| 外部系统 | ✅ | 所有被依赖的外部系统，标注名称 |
| 参与者 | ✅ | **仅限系统用户**，必须与 PRD 用户画像一一对应 |
| 连接线 | ✅ | 每条线标注：**关系描述（动词短语）** |
| 图例 | ✅ | 颜色/线型/箭头含义 |
| 边界框 | ✅ | 实线矩形框，标注"系统边界" |

**红线**：C1 中出现非用户角色（如"招聘者"而 PRD 无此画像）→ 不合格。

#### 3.1.4 连接线标注规范

C1 为纯拓扑关系图，依据 C4 模型标准（c4model.com）：

- 每条线必须标注关系描述（动词短语）
- **禁止标注**协议/技术/端口信息（如 `HTTPS:443`、`gRPC:50051`）
- 协议信息属于 C2 容器图的硬性要求，在 C2 中表达

**标注示例**：

```
正确：求职者 ──使用──► 系统
正确：系统 ──获取投递状态──► 招聘平台
正确：系统 ──分析匹配质量──► AI 匹配服务
正确：系统 ──推送通知──► 推送服务
错误：系统 ──获取投递状态──► 招聘平台  (HTTPS:443)   ← 协议信息不应出现在 C1
错误：系统 ──gRPC:50051──► AI 匹配服务              ← 协议方式不应出现在 C1
```

#### 3.1.5 颜色与字体

| 元素 | 色值 | 字号 | 字重 |
|------|------|------|------|
| 参与者 | `#E8A317`（琥珀） | 13px | Bold |
| 待建系统 | `#1A73E8`（蓝） | 13px | Bold |
| 外部系统 | `#9CA3AF`（灰） | 13px | Bold |
| 系统边界框 | `#333333`（深灰）stroke | — | — |
| 连接线 | `#666666`（中灰）stroke | — | — |
| 连接线标签 | `#333333` | 11px | Regular |
| 图例背景 | `#F8F9FA`（浅灰） | 11px | Regular |

#### 3.1.6 审查清单

```
□ 1.1  决策目标：能否一句话说清这张图支持什么决策？
□ 1.2  C4 层级：是否出现了内部元素（数据库/组件）？
□ 1.3  参与者：是否与 PRD 用户画像一一对应，无多余角色？
□ 1.4  外部系统：是否覆盖了所有外部依赖？
□ 1.5  连接线：每条线是否有关系描述（动词短语）标注？是否无协议信息？
□ 1.6  线条规范：平行线间距 ≥ 14px？无交叉？标注-线间距 ≥ 2px？
□ 1.7  颜色系统：所有颜色来自色板？对比度达标？
□ 1.8  字体规范：字号/字重/对齐正确？
□ 1.9  复杂度：元素数 ≤ 10？连接线 ≤ 15？
□ 1.10 元数据：是否完整（作者/日期/版本/来源/状态/受众）？
□ 1.11 可追溯：随机选 3 个元素，能否追溯到 PRD 或 ADR？
□ 1.12 跨图一致：参与者/外部系统/协议与其他图一致？
□ 1.13 图例：是否完整，颜色/线型/箭头均有解释？
□ 1.14 风险标记：是否有 ⚠️ RISK / 🏗️ TBD 标记（如有风险）？
□ 1.15 生命周期状态：DRAFT/REVIEW/APPROVED 标记是否正确？
```

#### 3.1.7 反模式

| 反模式 | 错误表现 | 正确做法 |
|--------|----------|----------|
| 内部暴露 | C1 中出现数据库图标 | 移到 C2 |
| 信息过载 | 连接线上标注了协议或完整 API 路径 | 只标注关系描述（动词短语），协议信息不应出现在 C1 |
| 用户幻觉 | 画了非系统用户的角色 | 只画 PRD 中定义的参与者 |
| 僵尸外部系统 | 外部系统画了但从未被使用 | 删除无用外部系统 |
| 无方向线 | 连接线没有箭头 | 必须标注方向 |
| 完美主义 | 花大量时间美化 C1 的视觉细节 | 清晰即可，重点是边界正确 |

### 3.2 C2 容器图

#### 3.2.1 决策目标

| 问题 | 答案 |
|------|------|
| 支持什么决策 | 系统由哪些部署单元（容器）组成？容器间如何通信？技术栈选型？ |
| 谁读 | 架构师、后端开发、DevOps |
| 决策后果 | 容器划分错了 → 模块边界错误，部署模型错误 |

#### 3.2.2 C4 层级纪律

- **只允许出现**：容器（进程/服务/数据库/消息队列），以及它们之间的通信路径
- **禁止出现**：类名、接口名、包名、组件内部实现细节
- **禁止出现**：C1 级别的参与者（除非是边界参与者，如浏览器）
- 违反 = 不合格，直接打回

#### 3.2.3 元素完备性

| 元素 | 必须 | 说明 |
|------|------|------|
| 所有容器 | ✅ | 每个容器 = 一个部署单元，标注名称 + 技术栈 |
| 通信路径 | ✅ | 每条线标注 **协议 : 端口**（如 `JDBC:3306`） |
| 数据库 | ✅ | 标注类型 + 版本（如 `PostgreSQL 16`） |
| 消息队列 | ✅ | 标注类型 + 版本（如 `RabbitMQ 3.13`） |
| 外部系统 | ✅ | 如果 C2 中涉及外部系统交互，需出现 |
| 图例 | ✅ | 颜色/线型/箭头含义 |

#### 3.2.4 布局规范

**推荐布局**：三层垂直布局（从上到下）：

```
┌─────────────────────────────────┐
│         业务层（Business）        │
│  ┌──────────┐  ┌──────────┐     │
│  │ 后端服务  │  │ 客户端 Agent│   │
│  └────┬─────┘  └──────────┘     │
│       │                          │
├───────┼─────────────────────────┤
│ 数据层（Data）                    │
│  ┌────┴─────┐  ┌──────────┐     │
│  │ PostgreSQL│  │  Redis   │     │
│  └──────────┘  └──────────┘     │
├─────────────────────────────────┤
│     基础设施层（Infrastructure）  │
│  ┌──────────┐  ┌──────────┐     │
│  │ RabbitMQ  │  │  MinIO   │     │
│  └──────────┘  └──────────┘     │
└─────────────────────────────────┘
```

**禁止**：双列布局（左右排列）—— 容易导致连线交叉。

#### 3.3.2 UML 2.5 语法合规

| 要素 | UML 2.5 规范 | SVG 实现 | 常见错误 |
|------|-------------|----------|----------|
| **同步消息** | 实线 + 实心三角箭头 `──▶` | `stroke="black"` + `marker-end="url(#arrowSync)"` | 用开放箭头 |
| **异步消息** | 实线 + 开放箭头 `──▷` | `stroke="black"` + `marker-end="url(#arrowAsync)"` | 用实心箭头 |
| **返回消息** | 虚线 + 开放箭头 `- - ▷` | `stroke-dasharray="6,4"` + `marker-end="url(#arrowReturn)"` | 用实线 |
| **自调用** | 消息线回到自身 lifeline | 环状路径：右→下→左→上 | 直接横线指向自己 |
| **激活条** | 矩形条，长度 = 执行时间 | `<rect>` 宽度 = 4px，y 坐标对应开始/结束 | 整条 lifeline 画满 |
| **嵌套激活** | 激活条内嵌套更小的激活条 | 外层宽 4px，内层宽 6px 偏移 2px | 平铺排列 |
| **alt 片段** | 虚线分隔多个操作数，有监护条件 | `<path>` 虚线 + `<text>` 监护条件 | 用注释代替 |
| **opt 片段** | 可选路径，一个操作数 | 同 alt 但只有一个分区 | 用 alt 代替 |
| **loop 片段** | 循环边界，标注 min/max | `<path>` + `<text>` 如 `loop [1..3]` | 不标注循环次数 |
| **break 片段** | 异常中断，覆盖剩余交互 | `<path>` + `<text>` 如 `break [错误]` | 用注释代替 |
| **生命线** | 虚线 + 头部 `实例名:类名` | `stroke-dasharray="8,4"` + `<rect>`+`<text>` | 只写类名不写实例名 |
| **时间约束** | 标注在消息旁 | `<text>` 如 `{≤200ms}` | 不标注时间约束 |

SVG 图应支持以下自动化检查，检查脚本输出格式为 JSON。

```json
{
  "diagram": "fig-c2-container.svg",
  "checks": [
    { "id": "line-width", "passed": true, "value": "1.5px" },
    { "id": "parallel-spacing", "passed": true, "min_gap": "16px" },
```

**检查通过标准**：
