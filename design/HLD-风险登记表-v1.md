# HLD 风险登记表 v1

> 文档版本：2026-08-15 · v1 · 依据 HLD v3.8（对齐 PRD v4.5）

> ⚠ **复评提示**：本表登记基准为 HLD v3.8。HLD 现已演进至 **v3.14**（接口完整性补全等多轮），下表部分状态已滞后（如 R-09 在 LLD v1.2 自称已收口但本表仍标 [闭环-模块前]；R-04 支付细节经 v3.14 §4.10 已补签约层面但模块级 LLD 仍缺）。建议在下一阶段门统一复评，并以 HLD 当前版本为基准刷新处置标签。新增 R-15 见下。
> 编制视角：资深架构师 / 设计评审风险视角
> 目的：将 HLD 评审与多轮审计中识别的残余缺口，从"待办清单"升级为**可管理的风险登记**。本表不声称覆盖所有风险（见 §0），而是把"未覆盖项"显式登记、定级、指定处置与责任人，使不全面之处被管理，而非被掩盖。

## 0. 关于"我无法考虑全面"的方法论说明

设计文档无法保证零缺陷。本登记表的价值在于：

- 把每个已知缺口转化为"最坏事故 / 触发条件 / 现有缓解 / 残余缺口 / 责任人 / 处置"六要素；
- 对每个风险给出明确 disposition：必须在某阶段前闭环、LLD 细化、或**显性风险接受**；
- 用户已决策的延后项（法务三块等）**不作为"已解决"静默处理**，而登记为 R-14 显性风险接受；
- 本表为活文档，应在每个阶段门（LLD 启动、各模块 LLD、上线前）复评。

**本产品天然约束事故半径的设计前提**（非保险，而是风险基线）：半自动 + 用户逐单确认模型使 Agent 不会在用户未显式确认时大规模自主投递；反封禁 fail-closed + break-glass 使异常即挂起等人工而非硬推；Cookie 本地加密不上云使凭证泄露半径锁本机。这些是设计已定死的，下表评估均在此基线上进行。

## 1. 风险评级方法

- **严重度 S（1–5）**：1 轻微 / 2 一般 / 3 较重 / 4 严重 / 5 灾难
- **可能性 L（1–5）**：1 罕见 / 2 低 / 3 中 / 4 高 / 5 极高
- **风险值 = S × L**
- **等级**：≥16 致命 / 10–15 高 / 5–9 中 / ≤4 低
- **处置类型**：
  - **[闭环-启动前]** LLD 启动前必须闭环
  - **[闭环-模块前]** 对应模块 LLD 前必须闭环
  - **[LLD 细化]** LLD 阶段细化，不阻塞其他模块
  - **[顺手]** 低成本顺手修改
  - **[接受]** 用户决策延后，显性风险接受
  - **[已缓解]** 已闭环，持续监测

## 6. 架构师行动建议（基于 HLD v3.10 + 本登记表 v1）

### 6.1 五大职责

1. **守门（gate）**：任何模块进入 LLD / 编码前，先查本表处置列。R-01 / R-02 文档债已于 v3.10 全部闭环，HLD 已无 LLD 启动前阻断项；后续新模块启动前仅需确认无新增 [闭环-启动前] 项。
2. **驱动决策（decide）**：对标 ⚠ 的开放项亲自给推荐并推进拍板，尤其 R-03（最高严重度）。不把安全关键决策遗留给 LLD 工程师各自拍脑袋。
3. **排程（sequence）**：LLD 从风险最高、最中心的模块切入（本机 Agent + 投递执行），并在其内设 PoC 验证门（反封号有效性、适配器 DOM 稳定性）通过后再扩。
4. **活文档（live）**：本表随每次阶段门复评；新增风险沿用 R-XX + 六要素；已闭环项保留标 `[已缓解]`，保审计链。
5. **合规良心（conscience）**：R-14 延后是用户决策，但架构师须显式提醒——DSAR 与威胁模型与 R-03 / R-12 强相关，建议上线前补，不作为沉默接受。
