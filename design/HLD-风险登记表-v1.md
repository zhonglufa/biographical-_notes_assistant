## 0. 关于"我无法考虑全面"的方法论说明

设计文档无法保证零缺陷。本登记表的价值在于：

- 把每个已知缺口转化为"最坏事故 / 触发条件 / 现有缓解 / 残余缺口 / 责任人 / 处置"六要素；
- 对每个风险给出明确 disposition：必须在某阶段前闭环、LLD 细化、或**显性风险接受**；
- 用户已决策的延后项（法务三块等）**不作为"已解决"静默处理**，而登记为 R-14 显性风险接受；
- 本表为活文档，应在每个阶段门（LLD 启动、各模块 LLD、上线前）复评。

**本产品天然约束事故半径的设计前提**（非保险，而是风险基线）：半自动 + 用户逐单确认模型使 Agent 不会在用户未显式确认时大规模自主投递；反封禁 fail-closed + break-glass 使异常即挂起等人工而非硬推；Cookie 本地加密不上云使凭证泄露半径锁本机。这些是设计已定死的，下表评估均在此基线上进行。

## 1. 风险评级方法

- **严重度 S（1–5）**：1 轻微 / 2 一般 / 3 较重 / 4 严重 / 5 灾难
- **可能性 L（1–5）**：1 罕见 / 2 低 / 3 中 / 4 高 / 5 极高
- **风险值 = S × L**
- **等级**：≥16 致命 / 10–15 高 / 5–9 中 / ≤4 低
- **处置类型**：
  - **[闭环-启动前]** LLD 启动前必须闭环
  - **[闭环-模块前]** 对应模块 LLD 前必须闭环
  - **[LLD 细化]** LLD 阶段细化，不阻塞其他模块
  - **[顺手]** 低成本顺手修改
  - **[接受]** 用户决策延后，显性风险接受
  - **[已缓解]** 已闭环，持续监测
