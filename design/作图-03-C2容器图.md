## §3.2 C2 容器图

#### 3.2.1 决策目标

| 问题 | 答案 |
|------|------|
| 支持什么决策 | 系统由哪些部署单元（容器）组成？容器间如何通信？技术栈选型？ |
| 谁读 | 架构师、后端开发、DevOps |
| 决策后果 | 容器划分错了 → 模块边界错误，部署模型错误 |

#### 3.2.2 C4 层级纪律

- **只允许出现**：容器（进程/服务/数据库/消息队列），以及它们之间的通信路径
- **禁止出现**：类名、接口名、包名、组件内部实现细节
- **禁止出现**：C1 级别的参与者（除非是边界参与者，如浏览器）
- 违反 = 不合格，直接打回

#### 3.2.3 元素完备性

| 元素 | 必须 | 说明 |
|------|------|------|
| 所有容器 | ✅ | 每个容器 = 一个部署单元，标注名称 + 技术栈 |
| 通信路径 | ✅ | 每条线标注 **协议 : 端口**（如 `JDBC:3306`） |
| 数据库 | ✅ | 标注类型 + 版本（如 `PostgreSQL 16`） |
| 消息队列 | ✅ | 标注类型 + 版本（如 `RabbitMQ 3.13`） |
| 外部系统 | ✅ | 如果 C2 中涉及外部系统交互，需出现 |
| 图例 | ✅ | 颜色/线型/箭头含义 |

#### 3.2.4 布局规范

**推荐布局**：三层垂直布局（从上到下）：

```
┌─────────────────────────────────┐
│         业务层（Business）        │
│  ┌──────────┐  ┌──────────┐     │
│  │ 后端服务  │  │ 客户端 Agent│   │
│  └────┬─────┘  └──────────┘     │
│       │                          │
├───────┼─────────────────────────┤
│ 数据层（Data）                    │
│  ┌────┴─────┐  ┌──────────┐     │
│  │ PostgreSQL│  │  Redis   │     │
│  └──────────┘  └──────────┘     │
├─────────────────────────────────┤
│     基础设施层（Infrastructure）  │
│  ┌──────────┐  ┌──────────┐     │
│  │ RabbitMQ  │  │  MinIO   │     │
│  └──────────┘  └──────────┘     │
└─────────────────────────────────┘
```

**禁止**：双列布局（左右排列）—— 容易导致连线交叉。

#### 3.2.4.1 ST-15 为什么不适用于 C2 容器图

> **关键澄清 (v4.0, 2026-08-15)**: 虽然 ST-15（灰盒左右二分 + 最近原则）是基于 C3 组件图重构提炼的,但它**不适用于 C2 容器图**。本节说明原因,防止误用。

**C2 与 C3 的本质差异**:

| 维度 | C2 容器图 | C3 组件图 |
|------|----------|----------|
| 抽象层级 | 系统 → 容器（部署单元） | 容器 → 组件（代码模块） |
| 节点性质 | 独立部署边界（进程/服务/数据库） | 容器内部的代码模块 |
| 主要价值 | 表达"系统由哪些部署单元组成 + 通信关系" | 表达"某容器内部模块构成 + 协作关系" |
| 灰盒性质 | 外部系统（真正的外部服务,不可控） | C2 中的其他容器（受控,只是不展开） |
| 布局逻辑 | **3 层 × N 列**（业务/数据/共享层 + 多个并列容器） | **目标容器 + 周边灰盒**（灰盒可分组） |

**为什么 ST-15 的"左右二分"在 C2 中行不通**:

| ST-15 核心 | C3 中可行 | C2 中不可行的原因 |
|-----------|----------|------------------|
| **职能分组**(数据/消息) | ✅ 4 个灰盒可清晰分两组 | ❌ C2 通常有 3+ 类别（业务/数据/基础设施/外部）,2 组不够 |
| **左右二分** | ✅ 4 灰盒整齐分两列 | ❌ C2 是 3 列 Java/Python/Agent 独立技术栈,合并会丢失"独立部署"语义 |
| **最近对齐 ≤ 160px** | ✅ 业务组件与灰盒同列,单段水平 | ❌ C2 同列垂直（Java↔MySQL 偏差 0px,跨列 Java↔Redis 偏差 400px 是合理的） |
| **单段水平 ≤ 120px** | ✅ 业务层 → 灰盒无阻挡 | ❌ C2 跨层线必经数据层/共享层,无法单段水平 |
| **水平通道禁令** | ✅ 业务层 → 数据层可侧边绕 | ❌ C2 依赖 y=250 总线 + 垂直干线实现"先汇聚后分发",水平通道是核心模式 |

**C2 自己的布局原则（不依赖 ST-15）**:

1. **3 层垂直布局**（业务/数据/基础设施）—— 表达层次结构
2. **N 列水平并列**（按技术栈分组）—— 表达独立部署单元
3. **总线 + 干线**（y=250 水平总线 + x=475/680 垂直干线）—— 集中管理多容器通信
4. **层间间隙分支**（数据层线在 y=280 分支）—— 避免穿透容器
5. **协议:端口标注**（每条线 `JDBC:3306`）—— C2 强调技术栈,C3 不强调

**ST-15 的"思想"可借鉴,但"形式"不可硬套**:

| 思想 | C2 借鉴方式 |
|------|------------|
| 最近原则 | ✅ Java 容器 ↔ MySQL 容器严格同列（x=200）,不偏移 |
| 避免长线 | ✅ 跨列通信走总线 + 干线,避免直接对角连线 |
| 职能聚合 | ✅ 数据层容器（MySQL/Redis）同层分组,共享层（RabbitMQ）单独一层 |

**反面案例**（如果硬套 ST-15 会发生什么）:

```
❌ C2 硬套 ST-15 后:
  ┌──────── 业务层 ────────┐
  │ [Java][Python]│[Agent] │   ← 强行分 2 列,Agent 单独突出
  └─────────────────────────┘
  ┌──────── 数据层 ────────┐
  │ [MySQL]│[Redis]        │   ← 强行分 2 列
  └─────────────────────────┘
  
  问题: 丢失了"业务层 3 个独立技术栈"的语义,Java/Python/Agent 三个并列容器
        表达"三种独立部署/独立扩展能力",合并会误导读者。
```

**正确做法**（C2 维持现状）:

```
✅ C2 维持 3 列 × 3 层结构:
  业务层:  [Java  ] [Python] [Agent  ]   ← 3 个独立技术栈
  数据层:  [MySQL ] [Redis ] [Browser]   ← 各对应一个业务容器
  共享层:  [RabbitMQ]                      ← 集中消息总线
```

**结论**:
- **C3 组件图**：必须遵循 ST-15（详见 [作图-11-C3组件图.md §3.9.5.1](./作图-11-C3组件图.md#st-15-灰盒左右二分--最近原则)）
- **C2 容器图**：维持 §3.2.4 的 3 层 × N 列布局,**不应用 ST-15**
- **思想可借鉴**：最近原则（避免长线绕行）在 C2 同样有效,但实现方式是"总线 + 干线"而非"左右二分"

#### 3.2.5 线条与间距

同通用规范（§2.3），额外增加：

| 参数 | 标准值 | 说明 |
|------|--------|------|
| 层间间距 | ≥ 90px | 总线层 y=250 到容器层 y=340，预留 90px 间隙供线分支通过 |
| 层内容器间距 | ≥ 30px | 同一层内两个容器之间的水平间距 |
| 连接线跨层 | 仅允许垂直下行 | 业务层 → 数据层，数据层 → 基础设施层 |
| 跨层回线 | 走右侧通道 | 数据层 → 业务层的返回路径走右侧边距 |
| 协议标签 | 线中间，不压线 | 标签位于线的中点上方 4px，配白色背景 |
| 总线层（Bus Bar） | y=250 | 所有线从业务层容器底部出发，汇聚到 y=250 水平总线，向右到达各自垂直干线 |
| 垂直干线（Trunk） | 共用垂直通道 | 线沿干线垂直下行，逐级分支（先近后远），避免交叉 |
| 干线 A（数据层） | x=475 | 线 7/8/9 共用，y=280 分支（层间间隙，≥ 20px 距容器） |
| 干线 B（外部系统） | x=680 | 线 10/13/14/15/16 共用，逐级分支（y=290/430/470/510/550） |
| 分支点 | 层间间隙，不穿插容器 | 分支点在层间间隙（如 y=280），水平段距容器 ≥ 20px |
| 分支顺序 | 从近到远 | 先分支到最近的目标，再到较远的目标（y 值递增） |
| 连接线终点 | 容器边界 | 线终点 y=340（容器上边界），不悬浮、不缩进 |
| 对称扇出 | 均匀分布 | 多条线汇聚到同一目标时，从干线分支的位置对称均匀分布 |
| 引导线 | 偏移 ≥ 10px | 辅助视觉引导线偏移实线 10px，不与实线重叠 |
| 网格对齐 | 10px 网格 | 所有途经点、容器边界、标签位置对齐 10px 网格 |

> **布线方法论（C2 Container 图专用）：**
> 1. 所有线从业务层容器底部（y=250）水平向右，汇聚到总线
> 2. 线在总线层水平向右，到达各自垂直干线
> 3. 线沿干线垂直下行
> 4. 数据层线在 y=280（层间间隙）水平分支，进入各自容器顶部
> 5. 外部系统线在干线 B 上逐级分支（y=290/430/470/510/550），从近到远
> 6. 所有连接线终点与容器边界齐平（y=340），不悬浮

#### 3.2.7 审查清单

```
□ 2.1  决策目标：能否说清容器划分的依据？
□ 2.2  C4 层级：是否出现了容器内部细节（类、组件）？
□ 2.3  容器完备性：所有容器是否覆盖了全部模块？
□ 2.4  技术栈：每个容器是否标注了技术栈 + 版本？
□ 2.5  通信协议：每条连接线是否标注了协议 : 端口？
□ 2.6  布局：是否采用三层垂直布局？有无跨层线交叉？
□ 2.7  颜色系统：层颜色是否区分？业务/数据/基础设施一目了然？
□ 2.8  线条规范：平行线间距 ≥ 14px？无交叉？标注-线间距 ≥ 2px？
□ 2.9  复杂度：容器数 ≤ 12？连接线 ≤ 18？
□ 2.10 元数据：是否完整？
□ 2.11 可追溯：技术栈/数据库/协议是否对应 ADR？
□ 2.12 跨图一致：容器/数据库/协议是否与部署图、ER 图一致？
□ 2.13 图例：是否包含颜色/线型/箭头/协议格式说明？
□ 2.14 数据库：是否标注了类型 + 版本？
□ 2.15 生命周期状态：是否正确？
□ 2.16 [ST-15 边界] 是否避免了硬套 ST-15（左右二分、灰盒 ≤ 4 个、4 段 L 形）？C2 维持 3 层 × N 列
```

#### 3.2.8 反模式

| 反模式 | 错误表现 | 正确做法 |
|--------|----------|----------|
| 技术栈缺失 | 容器框只写了"后端服务"，没写 Java/Spring Boot | 必须标注技术栈 + 版本 |
| 无协议线 | 连接线没有 `JDBC:3306` 或 `gRPC:50051` | 每条线标注协议和端口 |
| 容器粒度过细 | 把每个微服务都画成独立容器，超过 12 个 | 按业务域聚合 |
| 容器粒度过粗 | 整个系统画成一个容器 | 按部署单元拆分 |
| 数据库无版本 | 只写"PostgreSQL"不写版本号 | 必须写 `PostgreSQL 16` |
| 跨层线交叉 | 业务层 → 数据层的线和数据层 → 基础设施层的线交叉 | 用三层垂直布局消除 |
| **硬套 ST-15** | 把 C2 画成"左右二分"的 2 列布局,丢掉了独立技术栈语义 | 维持 3 层 × N 列,详见 §3.2.4.1 |
