# 交付前设计自检清单（Pre-Delivery Design Self-Audit）

> 建立日期：2026-08-16 · 触发：用户指出"交付前是否做 review"——发现双闸门（自动）只查 PRD↔HLD 与契约自洽，对 HLD 内部一致性、图 vs 文 truth、验收标准可测试性等盲区无覆盖。本清单作为**人工逻辑走查**的固化，每次交付（提交 / 合入 / 发布评审）前必过。
> 配套：双闸门脚本 `design/contracts/validate_contracts.py` + `design/check_prd_hld_traceability.py`（pre-commit + CI 双闸门）。

## 0. 双闸门（自动，门禁必过）
- [ ] `validate_contracts.py` 全绿：schema 自洽 + 注册表自洽 + 错误码唯一。
- [ ] `check_prd_hld_traceability.py` 全绿：MUST_TRACE 章节全覆盖 + PRD 版本 4.5 一致。

## 1. 版本与一致性卫生（盲区①：双闸门不查 HLD 内部）
- [ ] HLD **头 / 脚「文档版本」/ §10 交付表 / §9.x 修订记录** 四处版本戳一致。
  - 史实例：2026-08-16 发现脚注「文档版本」停在 v3.33，而头 / §10 已 v3.35（变更日志文字却已写到 v3.35）——前缀标签漏升。已修，此后交付前必核。
- [ ] 本次改动是否在 HLD §9.x 修订记录登记（版本戳同步）。
- [ ] 评审清单 / 颗粒度报告是否需 re-base 到当前版本（曾滞后：评审清单基线 v3.32、契约数写 65 实际 66）。

## 2. 图 vs 文 truth（盲区②：双闸门不查图）
- [ ] `design/figures/` 实际 SVG 与 HLD 文字声明一致：grep 残留 `服务端|沙箱|Docker|浏览器实例`，确认无"服务端跑浏览器自动化"。
- [ ] HLD 声明"已重绘"的图，实际文件时间戳 + 内容是否印证（**不要只信文字**）。
  - 史实例：项目记忆曾记"6 张图仍待重绘、旧图错绘服务端沙箱"，但实测 SVG 已正确（本机 Agent 承载浏览器自动化、服务端无浏览器算力）——记忆错、文档对，以实测为准。

## 3. 三方追溯（双闸门只查 PRD↔HLD，漏 LLD）
- [ ] PRD 需求 ↔ HLD 设计 ↔ LLD 实现 三向可追溯，无单向孤儿。
- [ ] 契约 schema 数量与 registry / 设计文字陈述一致（如叙述"65 schema"而实际 66，需同步）。

## 4. 逻辑自洽（红线与未证假设）
- [ ] **本机 Agent vs 服务端边界无越界**：浏览器自动化只在用户本机，服务端无浏览器算力（图 + 文双重核对）。
- [ ] **"半自动 / 用户确认"能否真规避 PIPL §24**：该假设**未经律师验证**，不得在设计里当作"已豁免"——评审清单已标 🔴 上线前阻断。
- [ ] 状态机 / 时序 / 事件 跨模块一致，无前后矛盾（如某处 at-least-once、另处 exactly-once）。

## 5. 验收标准可测试性（"命中需求高"可量化的前提）
- [ ] PRD 每条验收标准可映射为自动化测试；无"高效 / 兼容 / 良好 / 支持"等含混措辞无法测。
- [ ] 需求命中率 = 验收测试通过数 ÷ PRD 总需求数，本次发布能否出数、是否达发布门槛（建议 <95% 不准上线）。

## 6. 缺口登记纪律
- [ ] 所有未覆盖项显式登记为 `延后 / 待决 / 编码期`，**无静默标记"已覆盖"**。
- [ ] 延后项标注责任方与时机（如 PIPL 律师版延至灰度发布）。

## 7. 交付前灵魂三问（对应"不偏离 / bug 最低 / 命中高"）
- [ ] **不偏离需求？** 本次改动是否让某条 PRD 需求失去对账目标。
- [ ] **bug 最低？** 脏数据 / 错接口能否在最早处被契约校验 / 测试拦下。
- [ ] **命中高？** 能否量化本次发布的需求命中率。

## 使用方式
- 提交前：0 项由 pre-commit 自动跑；1–7 由人工逐项打勾，发现 ✗ 立即修或登记为风险，不静默放过。
- 发布评审前：把 5 / 7 两节结果写成一行"命中率 + 阻断项"附在发布说明。
