## 0. 通用绘图规范（先读）

- **分层方法**：采用 C4 模型（Context → Container → Component → Code），一图一层次，禁止多层混合。
- **格式**：全部手绘 SVG，白底 `#ffffff`，不依赖 Mermaid 等自动布局工具。
- **质量**：连线不穿卡、标注带底板、虚线加粗对比、命名一目了然；每张图必须带**编号标题 + 逐层/逐步说明文字**。
- **配色约定**（C2 / 2-3 等结构性图通用）：
  - 蓝色 = 应用容器（服务端）
  - 绿色 = 数据存储
  - 黄色 = 本机 Agent 层（用户侧）
  - 红色 = 消息中间件
  - 灰色 = 基础设施
- **核心架构红线（所有图通用）**：
  - 浏览器自动化（Playwright）**只存在于用户本机 Agent**，服务端容器内**不得再画浏览器沙箱 / Docker**。
  - 用户平台 Cookie **不落服务端数据库**，只在本机 Agent 本地加密。
  - 不存在「HR→系统」的主动回推箭头（HR 状态是"系统→招聘平台"的尽力轮询感知）。

## 图 C2 — 容器图（C4 Container）

- **文件**：`figures/fig-c2-container.svg`
- **类型**：C4 第 2 层 Container（系统内部可部署单元 + 通信方式）
- **目的**：展示内部容器（服务/数据/中间件/Agent）及其通信协议。

**必须画的容器（4 类）**

1. **业务层（服务端，蓝色）**
   - Java 后端服务（Spring Boot）：REST API + 业务逻辑编排。
   - Python LLM 编排服务（FastAPI）：**仅** AI/LLM 网关（调外部大模型 API），**不含浏览器自动化**。
2. **数据层（绿色）**
   - MySQL 8.0（主从）：主业务数据，**仅 Java 业务侧直连读写**。
   - Redis 7：缓存 / 分布式锁 / 幂等令牌（**不承载任务队列**）。
   - 标注：**用户平台 Cookie 不落此层**（本地加密存于本机 Agent）。
3. **本机 Agent 层（用户 PC，黄色）** ⚠ 重绘重点
   - 独立桌面守护进程；持有本地加密 Cookie；运行 Playwright 浏览器实例池（≤3）；执行投递/采集/面试模拟浏览器动作；经长连接/推送从服务端拉任务，本地执行后回写状态。
4. **基础设施层（灰色）**
   - RabbitMQ（红色）：异步消息总线，解耦服务端与本机 Agent。
   - 标注：**服务端不再部署浏览器沙箱**（原 Docker 方案废弃）。

**连线要点**
- Java ↔ Python：REST `/internal/*` + 事件（遵守 ADR-002 双语言解耦，Python 不直连业务库）。
- 服务端 → RabbitMQ → 本机 Agent：任务下发与状态回写通道。
- 本机 Agent → 招聘平台：本地实例 + 本地 Cookie 执行（在用户侧，不在服务端）。

**⚠ 红线（必须改对）**
- **把"Python 自动化引擎承载浏览器自动化"和"浏览器沙箱 Docker"从服务端容器里删掉**，改到黄色"本机 Agent 层（用户侧）"承载浏览器实例池。

**对应章节**：PRD §15.1 / §C.1 / §C.5；HLD §2.2 C2、§3.6–§3.9、ADR-002/003/004。

## 图 2-2 — 批量投递闭环时序图（UML 时序）

- **文件**：`figures/fig-2-2-apply-flow.svg`
- **类型**：UML 2.5 时序图（激活条 + 同步/异步箭头区分）
- **目的**：展示一次批量投递从用户确认到结果回写、通知的完整闭环。

**生命线（Participants，自上而下）**
1. 用户（PC/移动端）
2. Java 状态机（调度服务）
3. 任务通道（任务表 / RabbitMQ）
4. **本机 Agent**（拉取任务）⚠ 注意归属
5. 本地浏览器实例池（≤3，加载本地加密 Cookie）
6. 招聘平台（目标站点）

**步骤（10 步）**
1. 用户确认投递队列（批量选岗）。
2. Java 状态机自查：角色权益、当日限额、幂等键合法性 → 不满足直接拒绝。
3. 校验通过 → 写投递任务（携带全局唯一 `idempotency_key`）入任务表，通知本机 Agent（长连接/推送；Agent 离线则入队，上线后拉取）。
4. **本机 Agent** 从任务通道**拉取**任务（不是服务端消费执行）。
5. 本机 Agent 从**本地**实例池分配空闲实例（≤3），加载**本地加密 Cookie**。
6. 实例在用户机器上执行表单填充与提交（行为模拟，防检测）。
7. 实例返回结果：成功 / 失败 / 验证码（验证码触发暂停）。
8. 结果经 Agent 回写调度服务（状态事件）。
9. 调度服务推进 10 状态机并触发联动（如面试题生成）。
10. 用户侧收到状态与通知（WebSocket/邮件/短信）。

**⚠ 红线（必须改对）**
- 步骤 4–6 旧图错绘为"Python 调度中心从队列消费并分配**服务端浏览器实例**执行" → 必须改为 **「本机 Agent 拉取任务 → 本地实例池 + 本地 Cookie 执行」**。

**对应章节**：PRD §7 / §15.1；HLD §2.2 流程一、§3.4、§3.7、§4.5 B 层契约。

## 图 2-3 — 部署架构图（运行时视图）

- **文件**：`figures/fig-2-3-deployment.svg`
- **类型**：部署 / 运行时视图（自上而下分层）
- **目的**：展示单机起步部署拓扑，及浏览器自动化已下沉到用户侧。

**分层（自上而下 ④ 层 + 演进路径 ⑤）**

① **入口层**：Nginx（TLS 终止 + 反向代理）；H5 静态走 OSS，业务 API 走 Nginx。
② **应用层（服务端）**：Java 服务（事务/状态机/支付）+ Python 服务（LLM 编排网关），同机双进程，经 Host 内部总线互调（REST `/internal/*` + 事件）。**浏览器自动化不在此层。**
③ **Host 内数据**：Redis 7（缓存/分布式锁/幂等令牌，只存可重建数据）；Java 与 Python 共享访问。
④ **云服务**：MySQL 主从（**仅 Java 经 JDBC 直连**，Python 不直接连业务库）、RabbitMQ（投递/对账任务 + 事件，AMQP 含延迟与死信）、OSS（简历导出 + 证据快照，Python 直连；本地 MinIO 自托管替代，契约不变）。
⑤ **演进路径**：用户过万 → 先拆 Python LLM 独立集群（AI 横向扩展）→ 再拆 Java 热点（通知/支付）；**浏览器自动化始终随用户本机 Agent 横向扩展，服务端无浏览器算力瓶颈**。

**⚠ 红线（必须改对）**
- 在 ②/③ 层**删掉"Python 服务（Playwright 自动化）+ 浏览器沙箱（Docker）"** → 改为"浏览器实例池仅存在于用户侧本机 Agent，服务端仅 Java + Python(LLM 网关)"。

**标注要点**
- 单用户自用 / 极早期小范围定位（非多租户 SaaS）；"500 DAU"是**架构演进上限目标**，非上线初始承诺。
- 浏览器实例池"≤3 并发"是**单 Agent 进程（单用户/单节点）**约束，非系统总量。

**对应章节**：PRD §15.1；HLD §2.6、§1.3（容量基线修正 H3）、ADR-001（模块化单体）。

## 图 2-4 — HR 状态感知时序图（UML 时序，Best-Effort 轮询）

- **文件**：`figures/fig-2-4-hr-status.svg`
- **类型**：UML 时序图（强调"轮询非硬依赖"）
- **目的**：展示 HR 状态如何被尽力感知，且轮询失败不阻塞任何流程。

**生命线**
1. Java 状态机
2. 内部契约（B08 轮询指令下发）
3. **本机 Agent**（平台适配器）
4. 本地浏览器实例（加载本地加密 Cookie）
5. 招聘平台页面
6. 状态事件回写通道

**步骤**
1. Java 状态机按平台配置触发轮询（默认 6h/次，高频平台可配置 2–4h，见 §4.5 B08），**经内部契约下发轮询指令至本机 Agent**（规避"HR→系统"反模式）。
2. 本机 Agent 适配器以浏览器会话（**加载本地加密 Cookie**）查询平台"投递记录/沟通过"页面（行为模拟防检测，感知通道 1）。
3. 解析状态：viewed（已查看）/ contacting（沟通中）/ unknown（平台未展示或无法确认）。
4. 本机 Agent 将状态码 + 证据快照（页面截图等，供人工复核）经状态事件回写服务端。
5. 分支 A：感知到 viewed/contacting → 状态机推进（viewed→contacting），触发增强型推送（WebSocket/邮件/短信）。
6. 分支 B：unknown/失败 → 保持原状态，记日志静默跳过，**不阻塞任何流程**。

**标注要点**
- 轮询不构成硬依赖：超时/异常一律记日志静默跳过，状态机允许 `unknown`，面试题生成完成时直接标记"可查看"。

**⚠ 红线（必须改对）**
- 旧图若画"Java 直连 Python 适配器（服务端）执行查询" → 必须改绘为 **「服务端经 B08 下发轮询 → 本机 Agent 适配器加载本地 Cookie 查询平台页面 → 回写」**。

**对应章节**：PRD §7.3；HLD §2.2 流程二、§4.5 B08、§7.3。

## 图 2-5 — AI 匹配与降级时序图（UML 时序，含 LLM 主备 failover）

- **文件**：`figures/fig-2-5-ai-match.svg`
- **类型**：UML 时序图（三级降级链）
- **目的**：展示匹配请求从主 LLM 到备用 LLM 到规则引擎的完整降级，调用方无感。

**生命线**
1. Java 岗位模块
2. Python AI 编排（配额/超时检查 + prompt 适配层）
3. 主 LLM（境内合规大模型，如 DeepSeek）
4. 备用 LLM（1 主 + 1–2 备用）
5. 规则引擎（关键词匹配兜底）

**步骤**
1. Java 发起同步匹配 `POST /internal/ai/match`（≤5s 预算，见 §4.5 B01）。
2. Python 先做配额/超时检查，超预算直接走降级链。
3. 调用**主 LLM** 匹配打分。
4. **主模型不可达（超时 / 5xx 比例超阈值）→ 自动切备用 LLM**（prompt 适配层做供应商差异归一，并跑 golden set 质量回归确认评分一致性，κ 容差内）。⚠ 这一级是重绘必须补的。
5. 分支 A：主/备 5s 内成功 → 返回分数 + 理由。
6. 分支 B：主备均不可用 / 质量回归偏差超 κ 容差 → 降级 1，调用规则引擎关键词匹配。
7. 规则引擎返回分数 + 理由（基于 JD 关键词与简历文本）。
8. Python 统一响应结构返回 Java：`match_score`、`reason`、`model`（**deepseek | backup | rule**）、`elapsed_ms`；前端与调用方不感知降级/切换路径。

**⚠ 红线（必须改对）**
- 旧图若只有"主 LLM → 规则引擎"两级 → 必须**补「主 LLM 不可达 → 自动切备用 LLM（golden set 回归）」这一级**（§34.2）。

**对应章节**：PRD §7.5（匹配度模型）、§34.2（LLM 主备 failover）、§26.1（供应商差异归一）；HLD §2.2 流程三、§6.11 B5/B1、§7.2。
